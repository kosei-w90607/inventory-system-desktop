# 棚卸しと後着売上の時点を、観測できた証拠で分ける

## Status

proposed — 2026-09-18、owner の「設計を任せる」を受けた Codex の統合案。2026-09-23 に owner 決定（2026-09-23 / 2026-09-24）と独立レビューを受けて改訂した。改訂で外したものと理由、次の design lane が決めることは[適用範囲の但し書き](#適用範囲の但し書き)、後続の実装 lane の担当は[㉘ への引継ぎ](#㉘-への引継ぎ)に置く。

対象は REQ-205 / REQ-401。実装済みの契約ではない。㉗の Design Phase の出力として、[packet](../archive/plans/2026-09-16-stocktake-count-baseline.md) の D-D4 / D-D8 / D-D9 / D-D10 と、その派生する実装指示を置き換える案をここに集約する。D-D1〜D-D3 の snapshot 補正、商品ごとの即保存、売上と在庫の分離、確定済み評価額の非遡及は維持する。実装開始には source docs の詳細同期と独立 Plan Gate が必要。

### 適用範囲の但し書き

2026-09-23 の改訂で、次のものを本ADRから外した。以下の本文は改訂後の契約だけを書いており、この節で本文を差し引いて読む箇所はない。

- 計数中にOSの通知（スリープからの復帰・時刻の変更）を受ける監視と、その通知で進めるPC時計の世代番号。アプリの時計と経過時間の時計の差の検査。監視が成り立たないときの計数停止、Windows以外での計数不可、そのための実機probeとL3の項目。㉘の判定は受領上限・商品revision・ledger_cursorだけで決まり計数の時刻を使わないので、監視は安全性に寄与せず、通知の登録失敗で計数を止める可用性のriskだけを持ち込む。
- PC時計による比較。実測側のPC時計の識別子、POSの時刻の基準を認定する表とそのgate、資料ごとの時刻の境界とその導出・昇格・失効の伝播、因果矛盾の検査と信用失効の証拠TX、準備照会の時計のissue、精算時刻の精度の保存、判定表の時刻による2行、EJの時刻による分割。PC時計による比較は同じ起動中にしか成り立たず、アプリを開き直す日常の運用では使えない。ownerは2026-09-23にこの比較を捨てると決めた。
- 旧記録（legacy）の取消のための専用の復旧。専用のbegin用途・再実測の理由・回復action、進行中の明細を再実測の値へ付け替える処理と、その内部request ID。店は初導入で本番の旧履歴がなく、専用の状態機械は開発・試験DBのためだけのものになる。取消の保留は通常の実測で解除できる（D6）。
- 判定不能を最新の実測の所属で通常適用とfile全体の保留へ分ける規則。保留集合を永続しない設計が迂回路とJAN変更の受容riskを生み、時刻による判定がなければ確定済みの商品を含む日次資料が毎日file全体の保留になる。所属によらず通常適用して要再確認を残しても、数え直しの補正N-Lが差を吸収する（D4）。

運用の約束で安全を担保する案は採らない（owner決定 2026-09-23）。

次のdesign lane「実測とPOS系列の対応を取得・保存する」が決めること: 判定不能を実測前・実測後へ分ける方法（番号印字とEJの取引順による取引単位の前後判定。番号印字は実機未検証の候補）、精算系列の意味と精算同一性guardの比較方法（byte hashか正規化した内容か、previewの時点の受領で衝突させるか）、レジ入替・番号resetの系列、計数の作業のまとまりの境界の残し方（棚卸し画面の開閉を記録する案を含む）、時刻区間の合成モデルの扱い。これらが入っても判定不能の範囲が狭まるだけで、D4の出口（通常適用と要再確認）は変わらない。

## Context

販売の発生、精算、ファイルの受領、実測、入力の保存は異なる出来事である。日付だけの比較、保存時刻だけの比較、任意の過去60分、初回の仮時刻では、どの増減が現物数に含まれるかを証明できない。

目的は、観測できる変化を保存前に止め、判定できない後着売上を再確認へ回し、誤った実測も後から訂正できること。実際に数えた商品・数量をアプリが直接観測した、と偽装しない。

非目的は、棚卸し確定の取消、過去評価額の自動再計算、部門売りの商品への推測配賦、実POSデータの保存形式変更、汎用イベント基盤の導入。EJ parser の実装は別laneだが、下記の証拠条件と実行拒否はそのlaneの必須契約とする。

店の前提とownerの判断の要旨（原文は公開repositoryに置かない）:

- 棚卸しは、いつ数えても年末時点へ数量を繰り越せることを中心に設計する。商品別に記録できた入出庫は自動で反映し、記録できない分だけ店の訂正を受け、二つを重ねて減算しない。古い実測数のままの評価額は年末時点の要求と別物になる（owner判断 2026-09-16。D1のsnapshot補正と確定後評価額の根拠）。
- 確定はsnapshot方式で、数えた時点の帳簿と現物の差だけを現在庫へ加減する。例: 帳簿10・実測8、その後入庫5・販売2なら確定時は11（owner判断 2026-09-16）。
- 実測に反映済みの販売を、後から来るZ004で再び引かない。対象はZ004で、在庫を動かさない日報とは分けてよい（owner判断 2026-09-16）。
- PCの時計は電波と同期しているだろうというownerの見立て（推測）があり、レジの時計の管理は分からない（取扱説明書では月差±40秒・手動設定）。PC時計による比較を捨てた経緯の一部である（2026-09-18）。
- 「今から数える」を押してから棚へ行って数え、机へ戻って保存する流れは成り立つというownerの見立て（2026-09-24）。ノートPCは机に置いて使うので、1商品ごとに机と棚を1往復する順序になり、棚で数えてから机で入力する今のExcelの運用とは逆になる。この順序はD1の外部前提として残る。

## Decision

### SPEC-STK-TIME-D1: 実測には開始と保存、アプリ内の順序には単調な番号を使う

商品を選択しただけでは計数を開始しない。「今から数える」の操作で BIZ が計数contextを発行する。context は商品、対象の棚卸し明細、開始時刻 S、商品状態の版、受領済み資料の上限ID（source_cursor）、DB世代を保持する。数量欄は新しいcontextでは空にする。紙の古い値を新contextへ自動転記しない。

「数を保存」で現在時刻 E を採る。S / E はアプリの時計で記録する操作の時刻であり、物理的な計数時刻を証明するものではない。本ADRはS / Eを前後判定にもcontextの失効にも使わず、記録詳細の表示と次のdesign laneの入力として保存する。「開始してから数える、数量が動いたらやり直す」は残る外部前提である。

- `products.stock_revision` は商品単位の単調増加整数。既存商品の数量更新は `inventory_repo::update_stock_quantity` に限定し、同関数内で数量と版のchecked増分を不可分に更新する。呼出し側へ増分責任を分散させない。共通入出庫・取込み取消の戻し・棚卸し確定補正・`fix_integrity` の全経路に適用し、同じ数量への更新も版を進める。汎用 `ProductUpdates.stock_quantity` とそのSQL分岐はruntimeで除き、迂回路を残さない。新商品INSERT時の初期数量・版0は別で、既存商品の更新に流用しない。
- 数量を変えない実測基準・snapshot・要再確認flag・`pos_stock_sync` の更新、純量0の取消、差0の確定でも、同じTXで共通のchecked版更新処理を呼ぶ。数量更新済みでも追加で版が進むことは許す。履歴上の更新を最終数量の一致で省かず、減算と加算が相殺するABAも検出する。overflow時は数量・履歴を含むTX全体を拒否する。
- 保存TXでcontextの版と現在の版、対象明細の所有者・状態を再検証する。違えば書込み0で拒否し、「数えている間に記録が変わりました。もう一度数えてください」を返す。最新状態で新contextを開始すれば直前の移動が何分前でも再試行できる。
- 未保存contextの失効は、商品切替、画面離脱、abandon、アプリの終了（未保存tokenは復元しない）、DB接続の交換（DB世代）と、保存TXでの商品revision・所有者・親状態の不一致に限る。PCの蓋閉じ・sleep・時刻変更では失効させない。その間に在庫が動いた場合は保存TXのrevision再検査で拒否する。contextの有効性をクライアントの日時申告で決めない。
- DB接続の置換・バックアップ復元でも、業務操作を再開する前に全contextを破棄する。別のDB状態へ古いrevisionやsource_cursorを持ち越さない。
- 保存処理は1商品1TX。`stocktake_items` の snapshot 更新とflag解消、または再実測行と補正movementを一括確定する。全商品の入力を集めてから保存しない。
- 保存済みcontextの再送は補正を再実行しない。処理済みIDで結果を照会し、保存応答の喪失を新しい実測として再実行しない。再起動後に未保存contextを復元して保存する経路は設けない。
- 版は競合検出と実測の新旧に使う。`created_at` の秒精度で同秒の先後を決めない。
- observation_revisionは、保存TX内の必要な数量・flag更新後にstock_revisionを進め、その増分後の値を記録する。同一商品で異なる実測に同じ版を与えない。複数回進めてもよいが、減少・再利用・overflowは許可しない。

保存した数量Nと保存時の帳簿Lについて、進行中の棚卸しは snapshot を `system_stock=L, actual_count=N` とし、確定時の補正を `N-L` とする。独立の再実測はその場で `N-L` のmovementを作る。差0でも実測の証拠は保存するが、0数量のmovementは作らない。

force_fillは実測ではなく、補完数量とsnapshotをともに `max(現在庫, 0)` にして補正0とする。実測の窓・cursorは作らない。負の現在庫を補完で0へ書き換えない。確定後評価額は `Σ max(補正後現在庫, 0) × 評価原価` とし、保存した古いNだけで合計しない。

### SPEC-STK-TIME-D2: 入力資料を「受け取った事実」を、売上取込みとは別に残す

構文・ファイル種別を検証できたZ004のbyte列をアプリが受領したとき、`pos_import_sources` にhashで一意な資料受領記録を作る。これは売上・在庫のcommitではない。全行0、保留、取込み取消でも資料を受け取った事実は残る。raw byte列・商品名・売上値はこの表へ複製しない。

この表のIDはDBの単調増加番号。計数contextの開始時に見えていた最大IDを `source_cursor` として固定する。ファイルFの受領IDがその値以下なら、Fの内容は計数を始める前に既に存在していた。正規のPOS出力を入力として扱う前提の下で、Fの販売・返品は今回の現物数に含まれると判断できる。

これは時計に依存しない復旧経路になる。初回、精算時刻なし、時計異常、EJ取得不能でも、ファイルを受領してから対象商品を新たに実測すれば、そのファイルの在庫変動をスキップできる。時計を直したというチェックだけで古いファイルの時刻を信用し直さない。

受領IDは計数の**保存時**に取り直さない。計数中に届いたファイルを過去の実測へ含めることになるためである。同じhashの再選択でも最初の受領IDを変えない。別hashは別資料として扱う。

### SPEC-STK-TIME-D3: 精算の識別メタで同一性を守り、時刻では前後を決めない

IOはマシン番号、帳票種別、精算番号、精算日時（settled_at）をOptionで抽出し、原文の意味を保つ。BIZが精算の同一性を判断する。精算日時は識別と表示のメタとして抽出・保存を続けるが、実測との前後判定には使わない。レジの時刻とアプリの時刻を比較しない。

- 受領順と精算順は別。逆順取込み、同日複数精算、番号のリセット・桁戻り、マシン識別の変更を通常の連番と推測でつながない。
- 精算系列（番号のリセット区間）を証明する手段は本ADRにない。同じ帳票種別でmachine_no・settlement_noが一致する別hashは、別系列と推測せず同一精算の衝突として拒否する。内容の重複か訂正版か分からない間はcommitしない。同一hash重複拒否も維持する。
- 取込み取消は、資料受領の事実を消さない。資料の受領と、売上が有効に取り込まれているかを別に扱う。0売上の資料も受領記録として残す。
- 本laneの欠落表示は、受領したが精算同一性guard（別hash衝突・識別メタ不足の同日追加）で拒否され、当該sourceのactive importがない資料に限定する（表示「取り込めていない精算資料があります」）。BIZ-03が拒否理由と初回拒否日時をsourceへ独立の証拠TXで保存する。read-onlyの準備照会はsource単位で `PosStockReadiness.issues.code=settlement_missing` を返す。source_idsとsettlement_datesは各1要素で、同じsourceの保存済み拒否理由を既存の利用者向け説明へ変換する。別sourceを同じissueへ集約せず、source ID昇順にする。stock_review.warningsへ欠落状態を複製しない。再起動・元import取消・現在庫の再実測・「ファイルが無い」の確認で消さず、当該sourceにactive importが成立したときだけ表示対象から外す（拒否証拠は保持）。保存失敗は業務拒否を維持して記録失敗を返し、通常の拒否記録成功と扱わない。
- 未提出の精算・系列の欠番は本laneでは検出/表示しない。番号の穴を売上欠落と断定せず、完全性検査が必要なEJはD5の別契約を維持する。拒否された別版が既存売上と重複している可能性もあるため、欠落数量/金額や別売上の存在を断定しない。欠落issueなしを「全精算が揃った」と表示しない。

識別メタが不足する同日追加は拒否する。同じsettlement_dateのactive import（completed / completed_partial）があり、取込み対象sourceまたは比較先active importのsourceのいずれかでmachine_no / settlement_noの片方でも欠ける場合、別精算と確認できないため、previewとcommit TXでsource_identity_conflictとして業務write前にfile全体を拒否する。同日追加確認では解除しない。両方欠落・片方欠落・比較先sourceを取得できない場合を候補なしへ落とさず、仮キーも作らない。同日activeがない場合はこの追加guardの拒否対象ではないが、既存のhash拒否と全受領sourceに対する同一精算別hashのguard等は引き続き適用する。

同一精算別hashの採用を決める操作や既存sourceのメタ補完は本scopeにない。誤った版を取り消しても訂正版との衝突証拠は残るため、その精算の売上を取り込めず、当該取込みによる在庫減算も行われない。番号resetの別系列を証明できない場合も同じ制限となる。識別メタ不足の同日追加も、上記の拒否条件が残る間は取り込めない。現在庫を再実測しても未取込みの売上は復旧しない。

取込み側の移行前提（owner決定、2026-09-19）: 店舗は[初導入・本番履歴なし](../project-memory.md)であり、本番開始前に識別メタの抽出から保存までを実装して新形式で開始する。識別メタを持たない旧Z004試験取込みは本番DBへ持ち込まない。それでも移行前importが比較先となりsourceや識別メタを欠く場合、上記の拒否を維持し、legacyだけ確認操作で通す例外は設けない。本番前preflightは該当するactive importの精算日一覧を表示して準備未完とする。旧取込みの存在を年齢やファイル形状で推測せず、現在の保存情報で検出する。日付+時刻だけを一意な精算identityにしない。

過去日の後追い取込みは対応対象として維持する。本番開始日より前・最終取込み日より前という理由だけでは拒否せず、識別情報・重複・棚卸しとの関係で判定する。全取り漏らしを更新前に解消する運用の約束は採らない。メタ完備の新形式どうしの別精算は、後追いでも他のguardを通れば追加できる。

Z004のparserは従来shapeとlayout Aだけを受理し、layout Bは未対応で安全停止する（[Z004 parser](../function-design/23-io-z004-parser.md)、[backlog](../backlog.md)）。layout Bに対応するときは、同じ精算のA/Bが別hashとなり上記の精算同一性guardで拒否されるため、その対応laneで同一性の比較方法を決め直す。

### SPEC-STK-TIME-D4: 前後の判定は一つの関数で行う

基準は最新の有効な実測。実測の新旧は商品状態の版で決め、同秒のtimestampのMAXに依存しない。force_fillと廃番自動入力は実測ではなく、この基準を作らない。

previewとcommitが同じBIZの判定を呼び、commit TXが現在の証拠で再判定する。判定は受領順と実測の種別だけを使い、時刻を使わない。

| 条件 | 在庫への扱い |
|---|---|
| `pos_stock_sync=false` | 売上のみ。在庫連動へ推測昇格しない。下記の非連動化の未調整記録は維持し、readyを現在庫の確認済みという意味にしない |
| 実測履歴そのものがない（NeverObserved） | 未実測商品として通常の在庫連動。ただし下記の共有JANの優先規則と、商品照合・重複等の既存拒否は維持 |
| 実測履歴はあるが時点証拠が欠ける（LegacyObserved） | 未実測へ読み替えず判定不能（理由は旧記録の実測）。新しい実測で移行する |
| 実測開始前に当該資料を受領済み（`source.id <= source_cursor`、D2） | 全部実測前。販売・返品とも在庫変動をスキップ |
| それ以外（計数開始後に受領した資料） | 判定不能 |

保存時刻Eや精算日時で「全部実測前」「全部実測後」を決めない。判定不能を実測前・実測後へ分ける方法（EJの取引単位の判定、番号印字）は次のdesign laneが決める。その方法が入っても判定不能の範囲が狭まるだけで、下記の出口は変わらない。

日計0のため既存仕様上sale_recordsを作らない行（数量・金額とも0の正常JAN行）も、在庫判定に必要な商品集合と下記の相殺の判定のために捨てない。

#### 判定不能からの復旧

- 一意の商品の判定不能は、最新の実測の所属（進行中の棚卸し・確定済みの棚卸し・独立再実測・legacy）によらず、Z004の在庫変動を通常適用する。同じ業務TXで (商品, 資料) 単位の要再確認flagを、作成したimportへの参照と理由とともに保存する。flagの保存に失敗したら取込みTX全体を戻す。
- flagの理由は次の5つ。
  - 計数と前後不明の販売（`sale_order_unknown`）: 数量が0でない行。数えた後に売れた商品に当たる。計数前の販売で二重に減算された場合も含むため、前後不明と呼ぶ。
  - 相殺の行あり（`offset_lines_present`）: 下記の相殺の判定で、精算区間に当該商品の動きがあった行。
  - 相殺の確認待ち（EJ待ち、`offset_check_pending`）: 下記の相殺の判定に必要なEJが取り込まれていない、または完全でない（区間の開始の証拠がないEJを含む）行と、前回の精算のZ004がまだ取り込まれていないだけの区間の行。EJか前回のZ004の取込みで再評価する。
  - 相殺の確認待ち（登録の変化、`offset_mapping_changed`）: 下記の相殺の判定で、どの商品の名称にも部門名にも前回のZ004の名称にも一致しない明細の行が区間のEJにある行と、前回を証明できない区間の行（最初の区間、settlement_noが戻った区間、受領済みの最小より小さいsettlement_noの区間を含む。D5）。EJを取り込み直しても解消しないので、EJの再評価の対象にせず、数え直しで解消する。直前のZ004が未受領の間のもの（最初の区間・受領済みの最小より小さい番号の区間・settlement_noが戻った区間）だけは、直前資料待ちの内部の印（previous_recheck_pending）を保持し、直前のsettlement_noのZ004を使う業務TXで再評価する（下記）。受領だけでは印を消さず、再評価を確定するまで再試行できる。
  - 旧記録の実測（`legacy_basis`）: LegacyObservedの行。数量によらず付け、legacyの基準は新しい実測で置き換えるまで解消しない。
- 確定対象の棚卸しに明細がある商品に未解消のflagが一つでもある間は、明細のkind（未計数・auto_filled〈廃番の開始時の自動入力を含む〉・measured）、最新の実測の所属、flagの理由によらず、force_fillでも確定できない。確定の拒否はその明細の計数へ案内する。拒否を解くのは次項以下のflagの解消（新しい実測の保存・当該importの取消・相殺の判定の再評価）だけで、force_fillとauto_filledはflagを解消しないので、force_fillで拒否を迂回できない。
- 確定済みの棚卸し・独立再実測に属する商品のflagは取込みを止めず、商品単位の準備issue（code `recount_after_import`、回復先 = active明細、なければ完了済み明細を参照する独立再実測）と取込み結果で示す。その商品にactive明細があれば、その棚卸しの確定は前項の規則で止まる。準備issueと取込み結果の数え直し対象は、その商品の未解消のflagの理由を型で持つ。1商品に理由の違うflagが複数あるときは、相殺の確認待ち2種以外が一つでもあれば「取り込んだ後に数の再確認が必要です」を示す。確認待ちだけのときは、D9の文言のうち次の最初に当たるものを示す。(1) 直前のZ004が未受領の間のものを除く登録の変化が一つでもあれば、数え直しだけを案内する登録の変化の文言。(2) EJの取込み機能がない間は、直前のZ004が未受領の間の登録の変化が一つでもあれば同じ登録の変化の文言、なければ取込み機能がない間のEJ待ちの文言。(3) 取込み機能が入った後は、EJが無い・不完全のEJ待ちが一つでもあれば「電子ジャーナルを取り込むか、今の数を確認してください」、なければ直前のZ004が未受領の間の登録の変化が一つでもあれば直前の精算の商品別CSVの文言、全てが前回のZ004の未受領のときだけ前回の商品別CSVの文言。
- flagの解消は、当該資料を計数開始前に受領していた新しい実測の保存（active明細へのmeasured保存、または独立再実測）か、当該importの取消に限る。相殺の確認待ち（EJ待ち）と、直前のZ004が未受領の間の相殺の確認待ち（登録の変化）だけは、下記の相殺の判定の再評価でも解消し得る。force_fill・再起動・設定変更・確認checkboxでは解消しない。
- 在庫は現物へ収束する。ただし数え直しが行われることが条件で、数え直すまでの間は計数前の販売を二重に減算して帳簿が一時的に現物より少なくなり得る（Consequences）。数値例（確定済みの商品P、帳簿10、現物8）: 実測後に2個販売 → 適用で8 + flag → 数え直し N=8, L=8 で補正0。実測前に2個販売 → 確定補正-2で8 → 適用で6 + flag → 数え直し N=8, L=6 で補正+2。数え直し前に取消 → 通常の戻しで8、flag解消。数え直し後に取消 → 戻し+2と補償-2が相殺して8。
- EJ欠落・不完全は、復旧のための再実測を拒否する理由にしない。確認checkbox一つで判定を代行しない。

##### 売上と返品の相殺

Z004は活動のない商品の行も数量0で出す（売上の有無を問わず全スロットを出力する）ため、数量0の行だけでは「動きなし」と「同じ精算区間で売れて戻った」を区別できない。計数の前に売れて計数の後に返品されると、Z004の純数量は0のまま帳簿が現物より1少なくなる（逆も同じ）。判定不能の商品（数えた商品）の行を次のとおり扱う。

- 数量0で金額が0でない行は動きの証拠なので、EJを待たずに相殺の行ありとする。
- 数量・金額とも0の行は、同じ精算区間のEJで判定する。完全なEJ（D5）の区間に当該商品の行（販売・戻・訂正・取消）が一つもなければflagを付けない。一つでもあれば相殺の行ありとする。区間の中の前後は問わない。行の有無だけを見るので、時刻や番号印字による取引単位の前後判定を要しない。
- 未精算の売上があるPLUをPLU書出しのclear行で消せる場合（D5の外部前提）は、数えた商品のうち今回のZ004に行がなく前回のZ004にはあるcodeの商品（廃番・code変更の書出しの当日に売れて、未精算の売上ごと消えた商品を含む）も、数量・金額とも0の行として同じくEJで判定する。消せない場合はレジがclearを拒み、その商品は今回のZ004に残るので、この扱いは要らない。前回のcodeが分からない区間（直前のsettlement_noのZ004を受領していない区間）の扱いは、下記の区間全体の確認待ちの対象に置く。
- 名称が重なる行は、区間を確認待ちにせず候補の商品に局所化する（D5の商品の行）。明細の行が複数の商品の名称に一致する（レジの名称の16バイトの切り詰めによる同名を含む）、商品の名称と部門名の両方に一致する、または前回のZ004から対応が変わった名称に一致する場合は、その名称を持つ候補の商品のうち、その区間で数量・金額とも0の数えた商品を全て相殺の行ありとする。候補でない数えた商品には付けない。書出しの反映が区間に1回以下なら行の本当の商品は候補に含まれ、見逃しは起きない。余分に付くのは同じ名称の候補だけである。
- 区間全体を確認待ちにするのは次の2つに限る。対象はその区間で数量・金額とも0の数えた商品の全てで、今回のZ004に行がない商品（PLUに登録していない商品）は含まない（上のclear行の場合の商品だけは含む）。前回のcodeが分からない区間（直前のsettlement_noのZ004を受領していない区間。最初の区間・受領済みの最小より小さい番号の区間・前回の未受領の区間・settlement_noが戻った区間）では、clear行の外部前提が真のとき、数えた在庫連動商品のうち今回のZ004に行がないものを全て対象に含め、区間の理由（EJ待ちか登録の変化）と同じflagを付ける。直前のsettlement_noのZ004を使う業務TXでの再評価（下記）で、前回にそのcodeがあれば下記の順で判定し（EJにその名称の行があれば相殺の行あり）、前回にも無ければ解消する。flagは取込みのTXで作るので、ほかのflagと同じく新しい実測の保存か当該importの取消でも解消する。JANのない在庫連動商品にも付く。前回資料を受領しただけでは消さず、再評価の業務TX、新しい実測、当該importの取消のいずれかで解消するまで残す。
  - 相殺の確認待ち（EJ待ち）: その区間のEJが取り込まれていない・完全でない（D5の精算の同一性、開始と終了・取引一連番号・分割fileの連続、商品別の符号付き合計のいずれかを満たさない。区間の開始の証拠がEJにない場合を含む）場合と、前回のZ004がまだ取り込まれていないだけの場合。
  - 相殺の確認待ち（登録の変化）: どの商品の名称にも部門名にも前回のZ004の名称にも一致しない明細の行が区間のEJにある区間と、前回を証明できない区間（D5。最初の区間、settlement_noが戻った区間、受領済みの最小より小さいsettlement_noの区間を含む）。この3つは、Z004の取込みの時点でEJの有無より先に判定する。この3つは直前のZ004が未受領の間の登録の変化で、直前資料待ちの印を保持し、直前のZ004を使う業務TXで再評価する（下記）。
  - どちらも、EJや前回のZ004の取込みに失敗した日と、レジの登録を前回と今回のZ004から説明できない区間だけの例外の保守的な扱いである。通常は下記の在庫連動の有効化の条件によりEJがそろい、価格だけ・廃番・名称変更・新しい名称の追加のPLU書出しや名称の重なりでも確認待ちにならない。
- 相殺の確認待ちは2種とも他の理由と同じく進行中の確定を止め、準備表示に出て、数え直しで解消する。再評価は、当該区間のEJまたは直前のsettlement_noのZ004を取り込む業務TXで、同一性・重複・共有JAN等のguardを通過した後に行う。previewと、それと独立した資料受領TX（D2）は、売上・在庫・要再確認flagを変更しない。BIZは初回受領か同hashの再選択かによらず、TX時点の保存済みflagと証拠を読み直して再評価の対象を選ぶ。相殺の確認待ち（EJ待ち）は再評価の対象とする。相殺の確認待ち（登録の変化）は原則としてEJの再評価の対象にしないが、直前のZ004が未受領の間のもの（最初の区間・受領済みの最小より小さい番号の区間・settlement_noが戻った区間）には、flagと同じ業務TXで内部の印previous_recheck_pendingを保存し、直前のZ004を利用できる業務TXで同じ順で全て再評価する（今日のZ004とEJを先に取り込み、古い番号のZ004を新しい方から後追いで取り込んだ場合にも、受領の順で判定を固定しないため）。戻った区間の直前資料は、戻った後に受領した直前の番号のZ004に限る。この印は、直前資料を受領しただけでは消さず、その資料を使った再評価を業務TXで確定するまで保持する。本ADRでいう「直前のZ004が未受領の間の登録の変化」には、受領後もその再評価が確定していないものを含む。再評価では、まずclear行の規則による対象を確かめ、今回にも直前のZ004にもcodeがない商品はflagを解消する。対象に残る商品は、どれにも一致しない行の有無（直前のZ004を利用できるときだけ判定する）と前回の証明を先に判定し、どれにも一致しない行があるか前回を証明できなければ（EJの開始の証拠が受領した前回と一致しなければ）相殺の確認待ち（登録の変化）とする。どちらもなく、それ以外の理由で完全でなければEJ待ちのまま残す。どちらもなく完全なときだけ、当該商品を候補に含む行がなければ解消、あれば相殺の行ありへ変える。直前資料を使った再評価を確定するとき、残すflagのprevious_recheck_pendingをfalseにする。前回が未受領の区間で登録の変化になる原因は上の3つだけなので（どれにも一致しない行の判定と開始の証拠の照合には前回の受領が要る）、そこで残る登録の変化（どれにも一致しない行がある区間と、EJの開始の証拠が受領した前回と一致しない区間）は証拠の矛盾として凍結し、以後のEJの再取込みでは再評価せず、数え直しで解消する。flagの変更・削除、印の更新、必要な商品revisionの更新は、その取込みの業務変更と同じTXで確定する。中止・guardによる拒否・業務TXの失敗ではこれらを確定せず、資料受領の記録と従前のflag・印を残す。再起動・previewの失効の後は、同じfileを再選択して最初の受領IDへ接続し（D2）、業務TXの再試行で対象を取り直す。初回受領の通知やpreview内の一時状態を、未処理であることの唯一の根拠にしない。再評価を含む業務TXが既に成功していれば、応答を失った後もactive hashの重複拒否を保ち、売上を再び適用しない。再評価は現存する未解消のflagだけに行い、途中の新しい実測や当該importの取消で解消したflagを作り直さない。flagを残す場合の作成importへの参照も変えない。同じ対象・同じ保存済みの状態・同じ証拠に対する再評価は同じ結果を返し、その結果への再評価は追加の変更をしない。結果が変わらない場合はflag・印を書き換えず、revisionも進めない。結果が変わる場合はD1のchecked版更新を同じTXで行う。flagの理由の5つは変えない。印は内部の永続状態であり、新しい理由・公開API・UIの確認操作を加えない。
- 採らない案: 数量0の行を全て要再確認にする（数えた後に売れた商品だけに付けるというowner判断 2026-09-24と合わない）。対策なしで残存riskとして受け入れる（ownerが対策を講じるとした）。確認待ちを警告だけにして確定を通す（利用者の注意に頼る）。数量0の行そのものを相殺の兆候とみなす（活動のない商品の行も出るので、全商品に付けるのと同じになる）。

#### 共有JANと設定

- **共有JANの優先規則**: JANの候補商品が複数あり、少なくとも一つが在庫連動対象の行は、上表の未実測・判定不能より先に行全体を検査する。非連動商品との共有でも、実際にどの商品が売れたかは分からない。全在庫連動候補で当該資料が実測前と証明できる場合だけ、全候補の在庫変動をスキップしてcommit可能。それ以外（判定不能・未実測・legacyを含む）はfile全体を保留し、先頭商品へ通常適用してから他の商品だけを再確認する経路を作らない。全候補が非連動なら在庫判定は不要。売上記録の先頭紐付けは既存互換として残すが、商品別売上の正確性を保証したとは記載しない。
- file全体の保留は、JANの候補商品が複数、かつ少なくとも一つが在庫連動対象の共有JAN行（非連動商品との共有を含む）で、全ての在庫連動候補の実測前を証明できない場合だけに残る。保留集合の再生成（同じfileの再選択と再preview）もこの場合に限る。
- 共有JANの復旧では、進行中明細がある候補はその実測保存、完了済み明細がある候補は独立再実測を使う。完了済みの自動補完明細も参照先には使えるが、その自動補完自体を実測の証拠とはしない。どちらの明細もない候補は、この限定した再実測APIでは解除できない。偽の明細作成や他商品の明細への関連付けをせず保留を維持する。このケースの手軽な解除は既存のDATA-2（商品同定）の範囲と合わせて別途設計する既知の制限で、全店棚卸しを自動開始して隠さない。
- **本番前の設定検査**: 在庫連動対象のJANが別の商品にも一致する設定は、自動在庫連動の利用条件を満たさない。設定有効化時・マスタ変更時の検証と、既存設定の本番前preflightで具体的な候補商品を示す。既存のpos_stock_sync値を無断で変更しないが、「連動可能」と表示して取込み開始後に初めて恒久的な制約を知らせることもしない。shared JANの在庫を先頭へ自動配賦していた旧動作とは意図的な互換性変更であり、CSV構文を受理することとcommit可能であることを区別する。全候補の実測によるスキップは一つの資料の復旧であり、翌日以降の恒久的な自動連動の解決ではない。EJの日次取込みがそろうまでの有効化の拒否は、下記の在庫連動の有効化の条件に置く。
- 検査は警告だけで有効化を通すものではなく、曖昧なJANを在庫連動対象として有効化する操作・新たにその曖昧さを作るマスタ変更を拒否する。既存の不適合設定は一覧に出し、商品同定の修正か、利用者による非連動への切替を案内する。非連動への切替は在庫を直す処理ではないため、その点を明示し、既存の要再確認flagも消さない。再有効化前には現在数の再確認と一意性の成立を要求する。pos_stock_syncの変更は商品状態の版を進め、開いた計数contextを失効させる。
- 上記の再確認は、既存のcount APIでmeasuredを保存することで行い、確認checkboxでは代替しない。対象の明細がない商品は前項の既知の制限に該当し、対象範囲内の解除手段が整うまで非連動のままにする。新しい商品単独の計数APIをこの条件のために無断で追加しない。
- 全行0でも、再確認・相殺の判定に使った資料は売上0の取込みとして完了可能。要再確認・保留が解消して対象数0になった再previewで拒否しない。

#### 在庫連動の有効化の条件

PLUの本番は、EJの取得・欠落時の拒否・再実測による復旧を実機で確かめてから有効にする（Consequences）。これを次の仕組みにする。EJがないと、数日かける棚卸しで毎晩のZ004が数えたPLU商品に要再確認か確認待ちを付け直し、確定に届かないためでもある。

- 準備照会は、EJの日次取込みと相殺の判定がないbuild（㉘）では、DBを入力にせず `ej_unverified` を常に返す。これを外すのは、EJの日次取込みと相殺の判定を実装するlaneのcode変更だけで、そのlaneのmerge条件は[取込みBIZの外部probe表](../function-design/32-biz-csv-import-service.md)のEJ完全性・EJ復元・商品同定の3行についてowner-operated gateの証拠があること。解除の条件には、PLU書出しの時点と準備照会で、切り詰め後の名称が他の商品や部門名と重なることを知らせる検知と、登録名の付け直しの支援が入っていることも含める。店は色違いの商品が多く、名称の重なりが多いと相殺の判定で候補の商品の数え直しが増えるため、PLUの本番より前に必須とする。DBのflag、設定key、確認checkbox、EJを1回取り込んだ事実では外れない（D5のparserの導入日や設定フラグで満たした扱いにしない、と同じ趣旨）。外した後にEJが欠けた日は、相殺の確認待ちだけで扱う。
- `ej_unverified` の間、BIZ-01は在庫連動のfalse→trueの遷移と、新規作成の商品・商品一括importの新規行でのtrueの設定を拒否する。true→true（既存の有効設定のままの更新）は許可し、既存の有効設定は本番前preflightに対象を示す（自動で書き換えない）。既定値はBIZがfalseにする（商品一括importの省略時）。商品フォームのpcs商品の提案値は、UIが準備照会の `ej_unverified` の間falseにする。DBの `products.pos_stock_sync` の `DEFAULT 1` は変えない。
- 拒否は既存の `validation` kindとfield `pos_stock_sync` で返し、messageはBIZが作る。商品フォームは在庫連動のcheckboxの近くに「電子ジャーナルの毎日の取込みが使えるようになるまで、在庫連動は有効にできません」を表示して入力を保持する。商品一括importは既存の行単位のvalidationと同じく当該行をerror行として同じ文言で示し、他の正常行の取込みは続ける（TX全体は拒否しない）。
- `ej_unverified` を外した後、在庫連動したことのない商品を初めてtrueにするとき、在庫連動なしで取り込んだ売上がその商品にあれば、その最後の売上の資料を計数開始前に受領していた（`source_id <= source_cursor`）適用済み実測を要求し、未達なら `recount_required` で拒否する（非連動化後の再有効化の規則〈[30](../function-design/30-biz-product-service.md)〉と同じ趣旨の、より強い基準を初回に当てる）。初導入で売上だけの期間に本番の販売がなければ該当しない。
- ㉘のtestとWindows L3の在庫連動商品は、既存のtest用seed（`src-tauri/src/db/test_support.rs`、`src-tauri/src/biz/csv_import_service/test_support.rs`）と、それで作ったL3用fixture DBの既存の有効設定（true→true）で用意し、UIの有効化操作に頼らない。

#### 非連動化の記録

非連動化による共有JAN行の保留の迂回を痕跡なしにしない。保留集合は永続しておらず、受領メタから対象商品を復元できないため、BIZ-01は既存商品のtrue→falseを全て検出し、同じTXで `products.pos_sync_disabled_revision` に変更後のstock_revisionを保存する。pos_stock_syncの書込みは、変更前値を同TXで読む単一の共通repo経路を通す。変更時は商品revisionを進め、true→falseの場合だけ同じ呼出しで切替版を保存する。汎用更新から直接setできる分岐を残さない。heldだったかを推測して対象を絞らない。設定変更は許可し、現在庫や既存importのflagは変更しない。新規falseやfalse→falseの無変更では記録を作らず、再度true→falseになれば新しい版へ更新する。未調整ではない商品にも確認を求め得る費用を受け入れ、無記録の過大在庫を避ける。

BIZ-03の準備照会は、非連動化の版より後の新方式の適用済み実測（完了したmeasured明細または独立recount）がない商品を、pos_stock_sync/廃番にかかわらず `sync_disabled_unreconciled` issueとして返す。記録は削除せず、その版との比較で解消を判定する。pendingへの新実測保存だけでは現在庫が直らないため、確定まではissueを残す。force_fill・取込み/取消・再起動・設定再有効化では解消しない。BIZ-01は未解消での再有効化をrecount_requiredで拒否する。一意性など既存guardも維持する。

未調整issueは商品単位で返し、targetsは当該商品の1要素にする。BIZはactiveのmeasuredかつobservation_revisionが切替版より後のpendingだけに「棚卸しを確定すると、在庫数に反映されます。それまでは未調整です」を返す。それ以前・同版・版なし・未計数/auto_filled/legacyなら「在庫連動をやめた後に、もう一度この商品を数えてください」と案内する。actionはどちらもactive_countのままとし、既存issueの利用者向け説明で伝える。51/73は準備照会から商品コードで対応する説明を取得し、UIへ生の版や新しい判別codeを追加しない。切替前のpendingを確定してもissueは残り、次は独立再実測へ案内する。

回復先は現在のactive明細、なければ完了済み明細に対する独立再実測、どちらもなければno_count_targetとする。明細がない商品には「棚卸しを始めると、この商品を数えられます」と次の操作を示す。開始自体では未調整を解消せず、active_countへ移る。明細がない間は制限を明示して記録を残し、偽明細や単独の新計数APIを作らない。activeでは通常の計数→確定、独立再実測では保存で現在庫を補正し、適用済み基準を新しい版にする。issueは通常の確定を妨げるimport flagではないため、実測済みactiveの確定を循環して拒否しない。

UIは切替前に「在庫連動をやめても、画面の在庫数は直りません。取り込めていない売上がある可能性があります。あとで今の数を確認してください」と表示する。保存後も商品画面と取込み準備表示から同じtyped issue/回復先へ戻れる。再previewで非連動商品がheldから外れ売上のみcommitできても、stock_review/取込み結果に「在庫数は未調整です」を表示し、準備issueは残す。これは拒否の確認解除でも、売上から欠落数量を推測する処理でもない。

共有JAN行の保留集合はpreviewから導出する一時結果であり、新しい保留tableは作らない。再起動・preview失効後は利用者が同じfileを再選択し、hashから同じ受領記録へ接続して、現在の実測・マスタで集合を再生成する。保存済み実測と補正はDBに残り、未保存入力は復元しない。`pos_import_sources` だけから元fileの明細を復元できるとは扱わず、fileを用意できなければ未取込みのまま。要再確認flagは、通常適用されたimportに属する永続状態として別に保持する。

### SPEC-STK-TIME-D5: EJの「完全」と「商品を判定可能」を分ける

EJ本番有効化前に次を合成fixtureと承認済みサンプルで確認する。単なるparserの導入日や設定フラグでPLU本番の条件を満たした扱いにしない。

- 同じマシン・精算系列のZ004とEJを対応づける。対象精算の終端だけでなく、区間の開始をどの証拠で確認したかを持つ。初回の開始を推測しない。
- 取引ブロックの一連番号、必要な開始・終了の境界、分割ファイルの連結を照合する。存在するファイルの末尾番号だけから「続きは全部ある」と推測しない。
- 取引内の明細復元数量と合計点数、商品別の符号付き集計とZ004を照合する。日計合計一致だけを完全性の証明にしない。
- 通常販売、返品モード、数量×単価、同じ名称行の繰返し、訂正・取消を区別する。未知の行・未知の取引形式を黙って除外しない。
- 名称照合はレジへ出力した名称の規則に合わせる。名称変更・衝突・部門売りとの衝突は、現在のマスタ名だけから過去の取引を一意と扱わない。
- EJの時刻で取引を実測の前後へ分けることは本ADRでは行わない（次のdesign lane）。EJは相殺の判定（D4）で、精算区間に商品の行があるかを示す証拠として使う。D2の復旧は常に利用できる。

EJの検査が示せるのは提供資料の整合性と、証拠のある期間の分類である。店が提出していない未知の資料や、アプリ操作より前に紙へ控えた実測値の真偽まで証明するものではない。

相殺の判定で「完全なEJ」とは、上の全条件を満たすことを指す。Z004と同じ精算であること（machine_no・settlement_noの一致）、精算の開始と終了・取引一連番号の連続・分割fileの続きがそろうこと、商品別の符号付き合計が同じZ004と一致すること。満たさなければD4の相殺の確認待ち（EJ待ち）とする。これとは別に、帰属できない行がある区間と前回を証明できない区間はD4の相殺の確認待ち（登録の変化）とする（下記）。

商品別の符号付き合計の照合は、下記の候補の商品の集合でつながる名称と商品をまとめた単位（連結成分）ごとに、その単位のEJの行の符号付き合計と、その単位の商品のZ004の数量の合計を比べる。区間の途中で名称が変わったり入れ替わったりして、同じ商品が前後で別の名称で売れても不一致にしないためである。名称が一意で部門名と重ならない商品では、単位はその商品だけになる。Z004側の合計はslot（スキャニングコード）単位で数え、アプリの商品に対応しないslotも含める。次の単位は照合しない。

- 部門名とも一致する名称を含む単位。その名称の行は部門売りと区別できない。その名称の行が一つでもあれば候補の商品は相殺の行ありになるので、見逃しにはならない。
- clear行の外部前提（下記）が真の場合に、今回のZ004に行がないcode（前回のZ004にはあるcode）の商品を含む単位。未精算の売上がclearでZ004から落ちうるためである。

対応が変わった名称とは、Z004の行が持つスキャニングコードと名称（「キャラクター」欄、レジ側の名称）の組の集合差 `{名称 | (コード, 名称) ∈ 前回 − 今回}` をいう。消えた名称、別のコードへ移った名称、載るコードの組が変わった名称がこれに当たる。名称をキーにした対応表で比べると同じ名称の2組が一つに潰れるため、組の集合で比べる。区間のEJにその名称の明細の行があれば、区間の途中でレジの名称が変わった可能性があるため、前回の組と今回の組でその名称を持つ商品の和を候補とし、区間を不完全にしない（下記の商品の行）。したがって価格だけ・廃番・名称変更・新しい名称の追加のPLU書出しは区間を確認待ちにせず、変わった名称の行があればその候補だけが相殺の行ありになる。

「前回」は同じmachine_noの直前のsettlement_noのZ004で、EJの区間の開始と連続（上の条件）が証明できるものに限り、受領順では選ばない。レジ側の実際の状態を比べる条件で、アプリ側のPLU書出しの確認の時刻や受領順を使わない（アプリ側の確認はレジへの反映の証明でもない）。この比較のため、受領したZ004ごとにスキャニングコードと名称の組を残す。前回は、Z004の受領記録とEJから次のとおり決める。

- 最初の区間: そのmachine_noのZ004をアプリが一度も受領していない（前回が存在しない扱い）。EJの有無より先に判定し、Z004の取込みの時点でD4の相殺の確認待ち（登録の変化）にする。最初の区間かは、同じmachine_noの受領記録の順から分かる。直前のsettlement_noのZ004を使う業務TXで、D4の順と再試行の契約に従って再評価する（直前のZ004が未受領の間の登録の変化。受領済みの最小より小さい番号とsettlement_noの戻りも同じ）。
- 前回の未受領: そのmachine_noのZ004を受領したことがあり、直前のsettlement_noのZ004だけがない。D4の相殺の確認待ち（EJ待ち）とし、そのZ004を使う業務TXでD4に従って再評価する。受領だけではflagを変更せず、中止・失敗の後も同hashの再選択から再試行する。
- 欠番の後追い: 同じmachine_noで受領済みの最小と最大のあいだの欠番を埋めるZ004は、後追いの通常の受領として扱う。そのZ004の前回もこの節の規則で決め、1つ大きいsettlement_noの区間の前回として、直前のZ004が未受領の間の登録の変化と前回の未受領の再評価に使う。
- 受領済みの最小より小さい番号: 同じmachine_noで受領済みの最小のsettlement_noより小さいsettlement_noのZ004は、前回を証明できない扱い（D4の相殺の確認待ち〈登録の変化〉）とする。1つ大きいsettlement_noの区間の前回としては使い、その区間が最初の区間か受領済みの最小より小さい番号の区間なら、その再評価もこれで行う（今日のZ004を先に、直前のZ004を後から取り込んだ場合）。自分の区間は、直前のsettlement_noのZ004を使う業務TXでD4に従って再評価する。10を受領して数えた後に9、8と遡って取り込む場合、9の区間は8の取込みの業務TXで再評価し、そのTXが失敗すれば同hashの再選択の後の業務TXで再試行する。
- settlement_noの戻り: 同じmachine_noで受領済みのsettlement_noと同じ番号のZ004を、別の精算（精算の同一性が一致しない）として受領したときに限って判定する。そのZ004は前回を証明できない扱い（D4の相殺の確認待ち〈登録の変化〉）とし、以後の「前回」の候補は、戻った後に受領したZ004（戻りを起こしたZ004を含む）に限る。レジ入替・番号resetの後に、戻る前のZ004を前回と取り違えないためである。以後の最小・最大・欠番・戻りの判定も、戻った後に受領したZ004の番号で行う。戻りを起こしたZ004の区間は、戻った後に受領した直前の番号のZ004を使う業務TXで、D4の順と再試行の契約に従って再評価する。D3の精算同一性guardは、同じmachine_no・settlement_noの別hashを同一精算の衝突として拒否するため、この判定が働くのは、次のdesign laneが精算系列と同一性の比較方法を決めて、同じ番号の別の精算を取り込めるようになった後である。それまで、そのZ004は取り込まれず在庫を動かさない。
- 前回を証明できない: EJに区間の開始の証拠はあるが、受領済みの前回のZ004と一致しない場合をいう。D4の相殺の確認待ち（登録の変化）とする。開始の証拠がEJにない場合は、証明できないのではなく不完全として、D4の相殺の確認待ち（EJ待ち）とする。

帰属できない行と前回を証明できないことによる確認待ちは、EJを取り込み直しても解消しないので、ほかの不完全と区別して返す（D4の相殺の確認待ちの2種）。

EJの明細の行は次の4つに分類する。一致は、今回のZ004の商品の名称、部門名、前回のZ004から対応が変わった名称を合わせて数える。

- 商品の行: 今回のZ004で商品のスキャニングコードの行が持つ「キャラクター」欄（レジ側の名称。今のマスタ名ではない）か、対応が変わった名称に一致する明細の行。候補の商品は、今回のZ004でその名称を持つ商品（対応が変わった名称では、前回のZ004と今回のZ004でその名称を持つ商品の和）とする。候補が一つで部門名とも一致しなければ、その商品の行である。複数の商品に一致する行（16バイトの切り詰めによる同名を含む）、商品の名称と部門名の両方に一致する行（部門売りへ先に分類するとその商品の相殺を見逃すため）、対応が変わった名称の行は、候補の商品全ての行として扱い、区間を不完全にしない。
- 部門売り: 部門名だけに一致する明細の行（どの商品の名称にも対応が変わった名称にも一致しない）。既知の行として商品の判定から外し、区間を不完全にしない。店の日々のレジ登録は部門キーと金額が常態である。
- 明細でない行: 合計・支払・税など。既知の行として外す。
- 帰属できない行: 明細の形で、どの商品の名称にも部門名にも前回のZ004の名称にも一致しない行。一つでもあれば、その区間で数量・金額とも0の数えた商品を全てD4の相殺の確認待ち（登録の変化）とする。この判定は前回のZ004を受領しているときだけ行う。前回の名称が分からないと帰属できるかを決められないので、前回のZ004が未受領の間は、行の内容によらずD4の相殺の確認待ち（EJ待ち）とする。

名称が重なる行の候補は余分に広がりうるが、見逃さないための費用として受け入れる。部門名はZ004どうしの比較に含めない。区間の途中で部門名が変わり、旧部門名が今回の商品の名称と一致すると、その商品に誤った相殺の行ありが付く。旧部門名がどの商品の名称にも部門名にも一致しなければ、その行は帰属できない行になり、区間が相殺の確認待ち（登録の変化）になる。どちらも見逃しではなく数え直しが増える側なので受け入れる。

実機と承認済みサンプルで確かめる外部前提（崩れた場合は、どれも帰属できない行か合計の不一致として確認待ちへ倒れる）: 返品モードの取引がEJにあることはサンプルで確認済みだが、戻の行に商品名が載るかは未確認。店が値引き・訂正・取消を使うことは確認済み（owner回答 2026-09-24）だが、値引き（％－キー）・訂正・取消のEJの行の形、取引と数量の復元、行の分類（商品の行・部門売り・明細でない行・帰属できない行）は未検証である。使用の確認をEJの復元・分類の検証済みの証拠に読み替えず、D4の在庫連動の有効化の条件（EJ復元を含む3行のowner-operated gate）を保つ。EJの精算区間とZ004の対応、16バイトのレジ名称の重なりの程度（重なると候補の商品が余分に相殺の行ありになる）、締めの時点で同じ日のEJをSDから取れることも確かめる。未精算の売上があるPLUをPLU書出しのclear行で消せるか（消せると、計数後の販売がZ004から落ちうる）も確かめる。真ならD4のclear行の扱いと上の合計の照合の除外を当て、偽なら要らない。Z004のsettlement_noがZ004ごとに1ずつ増えること（他のZ帳票と共有のカウンタでないこと）も確かめる。「前回」を直前のsettlement_noで決める前提である。

### SPEC-STK-TIME-D6: 取消で、既に実測へ吸収した数量を二重に戻さない

数量補正はD-D5の方針を維持し、吸収済みかの判断をアプリ内の順序へ置き換える。各実測のsnapshotと同じTXで、その商品について見えていた最後の `inventory_movements.id` を `ledger_cursor` に保存する。

取消対象の有効movementについて、IDが実測のcursor以下なら、その実測のsnapshotに含まれていた。対象importの全movementは1TXなので、実測が同じimportの途中へ割り込むことはない。timestampの同秒一致で先後を推測しない。取消側はmovement IDを取得する必要があるため、旧案の「VoidedMovementの拡張不要」は引き継がない。

- 対象movementを吸収した最も早い**現在も効力を持つ実測**を探す。進行中で上書きされた旧カウントは対象外。確定済みの明細と独立再実測は残る。
- それが進行中なら、取消の数量をsnapshotにも同じ向きで戻す。`system_stock -= SUM(voided.quantity)`。後で確定する補正量と現在庫の二重増減を防ぐ。
- このsnapshot補正では実測自体のS/E、N、cursor、observation_revisionを変更しない。商品状態のstock_revisionだけを進める。取消を新しい物理実測として順序へ挿入しない。
- それが確定済み・独立再実測なら、対象movementを全てvoidして通常の取消で在庫を戻した後、商品ごとに取消quantityをchecked SUMし、同TXに純量と同額のrollback_compensationを非0なら商品ごと1本だけ作る。純量0なら作らない。pendingのsnapshot補正も同じ純量を使い、行ごとや複数観測へ重ねて補償しない。元の実測値・評価額を書き換えない。
- 吸収した実測がなければ、通常の取消だけ。スキップ行にはmovementがなく、戻す在庫もない。取消で元のimportが立てたflagだけを消す。
- 独立再実測とその補正はimportを参照しない。import取消で消さない。再取込みの新movementは新IDとなる。
- 再実測・snapshot変更・取消・補正・flagの更新は同一TX内で商品状態の版にも反映する。開いていた古い計数contextを無効にする。

`stock_quantity = SUM(non_voided movements)` を維持する。実測誤入力は逆仕訳だけで消さず、新しい現物確認によって補正する。

#### legacyの取消は「証拠なし」を「吸収なし」にしない

migrationは、その時点のmovement IDの最大値を不変のlegacy上限（`legacy_movement_ceiling`、内部key `stocktake_legacy_movement_ceiling`）として記録する。これは旧実測が何を吸収したかのwatermarkではなく、旧実測より後に作られたmovementを区別する上限である。上限より大きいmovementは旧実測に含まれ得ない。旧実測のtimestampから正確なcursorを推定しない。

有効なlegacy観測があり、取消対象がこの上限以下で、新方式の**適用済み**実測に吸収されたことも確認できない商品は、取消全体を業務write前に保留する。legacyを吸収先探索から単に除外して通常の在庫戻しへ進まない。商品別の取消純量が0なら、在庫補正の不確実性はないが、flag・履歴・revisionの処理は維持する。 保留はvoid前に全体を停止し、`rollback_recheck_required` で対象商品と回復先を返す。旧完了記録の表示はreconciliation_version=0の意味で維持する（D8）。

新方式のpendingだけでは、この保留を解除しない。例: 在庫10から販売-2、旧実測8で確定、新pendingに8を保存した後、通常取消とpending snapshot補正だけを行うと現在庫は10に戻る。後の確定では8へ収束するが、それまで旧確定済み実測に反する現在庫を表示するため、適用済みの新基準を要求する。

pendingを取消TX内で適用済みへ昇格させる案は、算術上の成立とは別に、取消の副作用として未確定の棚卸し差異まで在庫へ反映し、確定時に補正する操作契約と差異件数の意味を変えるため採らない。

保留の解除は、対象商品に新しい適用済み実測を作ってから取消を再試行する。進行中の明細があればその計数と棚卸しの確定、なければ完了済み明細を参照する独立再実測で作る。回復先の案内は通常の `active_count` / `independent_recount` を使い、取消のための用途・理由・actionを別に設けない。新しい適用済み実測が元のmovementを吸収しているため、再試行した取消の戻しと補償が相殺され、確認した現在庫を維持する。取消を中止しても実測は現物の新しい事実として残る。

進行中の明細がある商品は、その棚卸しを確定するまで取消を再試行できない。進行中の所有者を独立再実測で迂回しない規則（D7）を例外なく保つための費用として受け入れる。

### SPEC-STK-TIME-D7: 訂正は「現在の現物」を直し、過去評価を上書きしない

棚卸し記録詳細に「今の数を確認して直す」を設け、D1と同じcontext・保存処理を使う。過去に入力した数量を、新しい実測日時だけ付けて再保存しない。

その商品の進行中明細が存在する場合は、未計数・自動補完を含め、その明細の計数へ案内する。古い完了済み記録から独立再実測で進行中の所有者を迂回する経路を作らない。この条件はUIだけでなくbeginと保存TXで検証する。

独立再実測はappend-onlyで、実測前帳簿・入力値・差・保存順序を記録する。movementの区分は明示する（確定補正 / 取消補償 / 再実測）。`created_at <= completed_at` という秒精度の推定やnote文字列の解釈で区分を決めない。差異件数は確定補正だけを数える。

大きな差の確認は補助UIに限る。現物との差があること自体は棚卸しの正常な入力なので、差10・50%などの未検証閾値を安全条件にしない。既存のカウント時在庫・入力値・差の表示、入力値の検証、保存後の訂正を最低契約とする。追加の異常値警告は実例と頻度を根拠に再訪する。

確定済みのheaderと `total_cost` は変更しない。「現在庫を直した」と「過去の報告値が正しい」は別である。差が確定前の数え違いか確定後の移動かを自動で断定しない。記録詳細に「現在庫の再確認。確定時の評価額は変更していません」を出す。

#### 保存APIとwireの契約（proposed、未実装）

abandonはUIが持つ商品切替・画面離脱をBIZ所有のcontextへ伝える失効処理であり、時間切れだけでは代替できない。reconciliation_versionは明細の最新kindではなく、確定時に使った計算・表示契約の世代を保存する。旧完了記録へ新方式の再実測を追記しても旧評価額の意味を変えないため、kindから都度導出しない。

tokenはBIZが生成・検証するcontextの識別子で、CMD側の保管とlookupは薄いtransport処理に限る。計数開始の応答が返り「数えてください」と表示されてから実測する。保存時のS/Eやcursorをリクエストに含めず、tokenからBIZが復元する。商品変更は旧tokenを破棄して新しいbeginを行う。通常の棚卸し入力・保留画面・記録詳細からの訂正がこのAPIを共用する。

現在のtokenなしのupdate_count commandは、新しいUIへ切替えるruntimeで公開登録から外すか、同じ必須context検査へ接続する。無検査で保存できる旧入口を残さない。内部の数量保存helperを再利用することと、旧wireを安全検査なしで許可することを区別する。

保存済みrequest IDは、進行中明細では最後の保存要求、独立再実測ではappend-only行に保存する。同じ要求・同じ値の再送は再補正しない。同じID・違う値は競合として拒否する。古い進行中要求が既に別の実測へ置き換わり結果を復元できない場合は「最新の記録を確認してください」と返し、期限切れtokenを新規要求として扱わない。

公開count_tokenはサーバーが生成するUUIDで、その文字列を公開保存要求のrequest IDとする。通常保存は明細のlast request、独立再実測はrecount行に同じIDを記録する。各保存先でrequest IDをUNIQUEとし、公開IDの照会が複数の保存先に一致する異常は書込みせず拒否する。

saveの入口は、DBに保存済みrequestがあるかの照会を未保存tokenの有効性検査より先に行う。保存済みなら副作用のない再送応答を返し、未保存なら有効なcontextを要求する。応答喪失時は同じ要求でsaveを再送してこの照会を使う。再起動でUIのtoken自体が失われた場合は既存の明細・記録取得で保存済み状態を確認し、古い数量を新規saveへ運ばない。照会専用の新APIは増やさない。

数量は既存の整数契約を維持し、負のactual_count・非整数・表現範囲外・補正式のoverflowは書込み0で拒否する。system_stockは負を許す。表示数値もJSで損失なく扱えるかを検査し、丸めた値を確認値として使用しない。新しいerrorの区分は「再計数が必要」「保存済み」「保存先が変わった」「入力不正」を機械的に区別し、UIがmessage文字列を解析して状態遷移しない。

previewのprivate cacheは、資料hashと、JAN照合候補・pos_stock_syncなど判定に使ったマスタ状態を保持する。commitはTX内で現在の候補と証拠を再検証し、候補が変わった場合は再previewへ戻す。取込み開始時の候補だけを信用して、途中の商品設定変更を無視しない。

アプリ内のdatetimeの表記は既存契約を維持する。比較では型として解釈する。日時文字列や商品状態の版をJSの安全整数範囲外へ無検証で渡さず、opaque tokenを往復させる。

#### 初導入と既存DBの互換性

初導入の本番には移行対象の旧履歴がない（確認日とowner回答の要旨はproject-memory）。D3の新形式による開始を前提とし、旧Z004試験履歴を本番へ持ち込まない。列追加だけで完了とせず、IOのマシンNo.・精算回数・精算日時の抽出→BIZ受領→DB保存を本番開始前に実装・検証する。旧importからsourceをbackfillしてもDBにない識別メタは復元できず、NULLを仮値で埋めない。原本CSVの再提示と保存済みhash一致による補完は技術的に可能だが、このscopeでは作らない。

旧DBを扱う開発・demo・試験や将来の更新のため、以下の分類・拒否・legacy取消の保留は残す。sourceなし/識別メタ不足のactive importを本番前preflightで精算日付きで示し、D3の比較先としての拒否を維持する。初導入という申告で既存行の検査を省略しない。開発・試験DBを作り直す場合も、残すマスタを確認し、売上・在庫移動と整合した単位で行う。csv_importsだけを消す手順やmigrationによる試験データの自動削除は設けない。実際のDB作り直しは本run外で、対象と保全範囲を定めた別の承認を要する。

旧DBの `counted_at` を計数開始Sとみなさない。migrationは旧producerの意味に従い分類する。

| actual_count | counted_at | 移行先 |
|---|---|---|
| NULL | NULL | uncounted |
| NOT NULL | NULL | auto_filled（廃番・在庫0の開始時自動入力。actual_count=0かつsystem_stock=0を確認） |
| NOT NULL | NOT NULL | legacy（手入力と旧force_fillが混在し、時点証拠はない） |

NULL数量に時刻だけある場合や、自動入力候補なのに0/0でない場合は既知のproducerに一致しない。安全なauto/uncountedへ推測せずlegacyとして移行異常を表示し、新実測を要求する。現在の廃番フラグから過去の種別を推定しない。根拠は旧start_stocktakeの0/0 INSERT、counted_atを省略するinsert_stocktake_item、手入力とforce_fillがともに数量・時刻を更新する既存経路。登録済みmigration v1〜v6にはこの時刻を後から埋める処理がない。runtime移行テストで各形と履歴・評価額の非変更を固定する。

新方式の作成・保存ではkindを明示し、measuredは証拠一式（S/E・両cursor・版・request ID）を必須、auto_filledは実測証拠を持たない。既存完了記録の表示・評価額はreconciliation_version=0の意味で維持し、曖昧な後着取込みでは再実測で移行する。進行中の旧実測は開始時snapshotの可能性があるため、そのまま新しい差分確定式へ流さず、再実測が済むまで確定を止める。force_fillでlegacy実測の再確認を飛ばさない。旧activeを新方式で確定する場合は、必要な再確認が解消した同TXでversion=1にする。

migrationは既存データの削除・過去の在庫補正を行わない。新しい証拠がNULLであることを安全と解釈しない。既存importから受領記録を作る場合も、過去の実測に受領cursorを後付けしない。

| 取込みで要再確認 | 対象商品と理由（計数と前後不明の販売 / 相殺の行あり / 相殺の確認待ち〈EJ待ち〉 / 相殺の確認待ち〈登録の変化〉 / 旧記録の実測）を表示。取込み自体は完了する。準備表示ではissue `recount_after_import` として残る。進行中明細があれば未計数でもその明細へ、なければ完了済み明細を参照する商品単位の再実測へ |
| 相殺の確認待ち | EJ待ちは、EJの取込み機能がない間は「この日の電子ジャーナルがないため、売上と返品の相殺を確かめられません。今の数を確認してください」と数え直しだけを案内する。取込み機能が入った後は「電子ジャーナルを取り込むか、今の数を確認してください」、そのうち前回のZ004が未受領なだけの区間は「前回の精算の商品別CSV（電子ジャーナルがまだならそれも）を取り込むか、今の数を確認してください」。登録の変化（どの名称にも一致しない明細の行がある区間と、前回を証明できない区間）は、取込み機能が入った後も「レジの商品の登録が変わったため、売上と返品の相殺を確かめられません。今の数を確認してください」と数え直しだけを案内する。ただし直前のZ004が未受領の間のもの（最初の区間・受領済みの最小より小さい番号の区間・settlement_noが戻った区間）は、取込み機能が入った後は「直前の精算の商品別CSV（電子ジャーナルがまだならそれも）を取り込むか、今の数を確認してください」とし、取込み機能がない間はほかの登録の変化と同じ文言にする |
| 共有JANの保留 | 「販売の前後を確認できません。今の数を確認してください」。全候補を数えて同じfileを選び直す。再起動・preview失効後も同じfileを再選択して再previewし、保存済み実測を使って残る対象を再生成する。未保存だけ新しく数える |
| 拒否された未取込み資料 | settlement_missingの精算日と理由を表示し、元資料/既存記録を確認する。現在庫の再実測で表示を消さず、未提出資料や欠番全般を検出したとは表示しない |
| 在庫連動をやめた後の未調整 | 商品画面/取込み準備に対象商品と「在庫数は未調整です」。active計数→確定、なければ独立再実測へ。参照明細なしは制限を表示 |
| 在庫連動を有効にできない | 「電子ジャーナルの毎日の取込みが使えるようになるまで、在庫連動は有効にできません」。入力を保持し、既存の有効設定は変えない |
| 記録詳細から訂正 | 「今の数を確認して直す」。過去の確定値の編集とは表示しない |
| 旧記録がある商品の取消の保留 | 「この取込みを取り消す前に、対象商品の今の数を確認してください」。進行中の棚卸しがあればその計数と確定、なければ独立再実測の後に、同じ取消を再試行する |

IME確定Enter、連打、商品切替、画面離脱・戻る、非同期応答の順序を既存UI契約どおり保護する。再previewや取込み完了後のrefetchで、保存済みの実測を未保存状態へ戻さない。Windows native L3で「数える開始→保存」「変更で拒否→数え直し」「取込み後の要再確認→再起動→数え直しで解消」「共有JAN行の保留→一部保存→再起動→残り」「記録詳細から訂正」を検証する。

## Rejected Options

- 日付だけの前後比較、初回の仮始端、連番抜けを0売上として確認解除する案: 証拠がない部分を安全と誤認する。
- 保存時刻だけ、または一律60分で計数中かを推測する案: 古い入力を見逃し、正しい再計数も止める。時間を経過させると解除されることは正しさの証明にならない。
- 全商品一括入力・一括補正: 入力時点が商品ごとに違うのに、commit時の現在庫へ古い値を適用する。
- EJの日計合計だけで完全性を保証する案: 相殺する取引や先頭・末尾の欠落を見逃す。
- 任意の在庫スキップ確認: 現物の再確認なしに二重減算と減算漏れを選択するだけになる。
- 生時刻を指定できる自由なバックデート: 実測時刻の自己申告を増やし、snapshot・取消の順序も壊す。
- 独立再実測を取込み取消で消す案: 取込みと別の現物確認を取り消すことになる。
- 開店前の計数は同日の販売を計数後、閉店後は計数前とみなす日付と時間帯の規則（ownerの2026-09-16の案）: 営業中は日付では決まらず、同日の販売を一律に計数前とする適用はownerが承認しなかった（2026-09-17）。
- 「数えたら入出庫の前に保存し、売れた後に数え直すときは実数を入れる」という運用の約束（2026-09-16）: D1の「今から数える → 保存」と商品ごとの保存に置き換えた。運用に頼らないownerの方針とも合わない。
- 棚卸し画面を開いた・閉じたことを記録し、その時点の状態を保存する案（ownerの2026-09-24の提案）: 一部採用。安全の仕組みとしては採らない。計数contextは商品ごとのbeginで受領上限と版を固定し、画面離脱で失効する。画面を開いた時点の全商品の状態は各商品の計数より古く、それで保存・判定すると上の全商品一括の基準に戻る。時刻による比較も捨てた。計数の作業のまとまり（その日の開始と終了）の境界を残す考えは、番号印字を作業の開始と終了に1回ずつ打ちEJの取引順で挟む案と同じ形なので、次のdesign laneの入力へ渡す。㉘に画面の開閉の記録を加えない。
- 計数中のOSの通知による監視と、PC時計による比較の維持: 適用範囲の但し書きのとおり、安全性に寄与しないか、日常の運用で成り立たない。
- 旧記録の取消のための専用の復旧の維持、または旧記録を持つDB全体の拒否: 初導入で本番の旧履歴がなく、前者は開発・試験DBのためだけに状態機械を抱え、後者は開発・試験DBの互換を失う。
- 判定不能を最新の実測の所属で通常適用とfile全体の保留へ分ける規則: 適用範囲の但し書きのとおり。

## Consequences

判定は受領順と実測の種別だけで決まり、判定不能は所属によらず通常適用と要再確認という一つの出口を持つ。計数開始の操作と資料受領の永続化、版・cursor、旧データが存在する環境での再実測移行が増える。これは誤入力の確認dialogを増やす代わりに、実際の状態変化と証拠を使うための費用である。計数の可否はOSの通知の登録やPCの時計に左右されない。

PLU本番はEJの取得・欠落時の拒否・再実測による復旧まで実機で検証してから有効化する方針を維持し、D4の在庫連動の有効化の条件で仕組みにする。㉘の段階でEJがないことを「安全を保証済み」とは表現しない。物理的な計数がcontext内に行われること、提出されていない資料の存在、商品別に記録されない移動は残存限界として明記する。PLU商品を部門キーで売った分はZ004にもEJの商品の行にも現れず見えない。これも既存の残存限界である。未精算の売上があるPLUをPLU書出しのclear行で消せる（D5の外部前提が真の）場合は、数えていない商品でもclearの前の売上がZ004から落ちて帳簿に入らず、帳簿が現物より多いまま残り得る。相殺の判定は数えた商品だけを対象にするので、これを検出しない。外部前提が実機で偽と分かれば起こらない。相殺の判定の対応が変わった名称（D5）は前回と今回のZ004だけから求めるので、一つの区間の中でPLU書出しが2回以上レジに反映された場合（名称が変わって元へ戻る場合を含む）は、途中だけに使われた名称を検出しない。途中の名称がどの名称にも一致しなければ帰属できない行として区間全体が相殺の確認待ち（登録の変化）になるが、今回の別のコードの名称と一致したときはその名称の候補だけに帰属し、本当の商品の相殺を見逃すか、別の商品に誤った相殺の行ありを付ける。反映が区間に1回以下なら、この見逃しは起きない。店は書出しを1日に何度もレジへ反映する運用ではないため、この限界を受け入れる（塞ぐ案はRevisit Trigger）。名称が重なる行（16バイトの切り詰めによる同名、商品の名称と部門名の一致、対応が変わった名称）は候補の商品全てを相殺の行ありにするので、動きのない商品にも数え直しが要ることがある（D5）。見逃しを避ける費用として受け入れる。部門名はZ004どうしの比較に含めないので、区間の途中で部門名が変わると、旧部門名が今回の商品の名称と一致すればその商品に誤った相殺の行ありが付き、どの名称にも一致しなければ区間全体が相殺の確認待ち（登録の変化）になる（D5）。どちらも見逃しではなく数え直しが増える側なので受け入れる。名称の重なりの検知（PLU書出しの時点と準備照会で、切り詰めた後の名称が他の商品や部門名と重なることを知らせる）と、登録名の付け直しの支援は、PLU書出し側の別の変更で扱い、在庫連動の有効化より前に入れる（D4の在庫連動の有効化の条件）。

在庫は現物へ収束するが、それは数え直しが行われることを条件とする。計数の前に売れた分は実測に含まれたうえで後着のZ004でも減算されるため、数え直すまでの間は帳簿が一時的に現物より少なくなり得る。数え直しの補正は再実測の区分で記録され、二重減算の戻しが棚卸し差のように見える。確定済みの評価額は非遡及で変わらない。

この改訂を実装しても、日次の自動在庫連動（v1.0の必須、D-070）は達成しない。数えたPLU商品は、数えた後に売れる（または同じ精算で売れて戻る）たびに資料ごとの要再確認になる。確定済みの棚卸しの商品では、この要再確認が商品単位の準備issueとして毎日加わり、独立再実測まで残るので、準備表示は確定後に空にならない。残った要再確認の商品は、次の棚卸しでforce_fillで飛ばせず数える（D4の確定の拒否）。件数は計数後に売れたPLU商品の数に比例し、規模は未実測。数え直しの循環を抜ける方法は次のdesign laneで決める。設定前のpreflightで満たしていない条件を示し、再確認の手間が単に少し増えるだけと説明しない。

複数日の棚卸しでは、各日の締め後にZ004と同じ締めのEJを取り込む。数えた後に売れた商品（または同じ精算で売れて戻った商品）だけが要再確認になり、確定の前に数え直す。最終日の取込みで計数後に売れた商品を数え直す負担が残る。ある日のEJを取り込めなかった場合は、その日の資料で数量・金額とも0の数えた商品が相殺の確認待ち（EJ待ち）になり、その日のEJを後から取り込むか数え直すまで確定を止める。前回の精算のZ004を取り込んでいないだけの日も相殺の確認待ち（EJ待ち）になり、そのZ004を取り込んだ時点で再評価される。どの名称にも一致しない行がEJにある日と、前回を証明できない日（最初の区間とsettlement_noが戻った区間を含む）は相殺の確認待ち（登録の変化）になり、EJでは解消せず数え直すまで確定を止める。ただし直前のZ004が未受領の間のもの（最初の区間・受領済みの最小より小さい番号の区間・settlement_noが戻った区間）は、直前の精算のZ004を後から取り込めば再評価される。価格だけ・廃番・名称変更・新しい名称の追加のPLU書出しや名称が重なる商品の販売では確認待ちにならず、その名称の候補の商品だけが相殺の行ありになる。最初の区間は前回がなく相殺の確認待ち（登録の変化）になるため、本番で最初の計数を始める前に、その直前の精算のZ004を取り込んでおく（「前回」は直前のsettlement_noなので、それより古いZ004では足りない）。

商品一括importで在庫連動商品のJANを別の一意なJAN（またはNULL）へ変えても、一意の商品の判定不能は保留ではなく通常適用と要再確認なので、保留の迂回にはならない。共有JANの行では、どの候補が売れたかを決められない商品同定の限界（DATA-2）が残り、保留と全候補の再実測で扱う。非連動化専用の記録/案内へJAN変更を混ぜず、個別フォームのJAN読取り専用は維持する。

取込み済みimportについて後から同一性衝突が判明しても、既にcommitした在庫適用を自動再判定・訂正しない残存リスクを持つ。訂正版の採用決定は本laneの非対応であり、現在庫は新しい実測で復旧する。

棚卸し側の移行費用: 旧観測を持つDBでは、過去の入力をlegacyへ分類することにより、アップグレード直後の最初のZ004から多数の商品が要再確認になり得る。preflightで在庫連動対象のうちlegacyが基準となる件数と商品一覧を表示し、新方式の実測で基準を作り直してから自動連動を始める。auto_filled自体はlegacy件数に含めず、実測基準にも使わない。ただし、その商品に別の有効なlegacy基準があればそちらで判定する。旧activeは必要な再実測後に新方式で確定する。旧記録の実測のflagがある商品は、最初の新方式の棚卸しでforce_fillで飛ばせず全部数える（D4の確定の拒否。初導入の本番には無い）。完了済みlegacyの商品はD4の回復先に沿う実測で移行できる。旧データを持つ環境の更新を、追加作業なしで従来どおり動く更新とは説明しない。その更新では作業件数の確認を受入条件とするが、初導入の本番に既存の棚卸し履歴があるとは扱わず、その再実測作業を要求しない。互換機構の合成テストは維持する。

取込み側の移行費用: 旧importは、原本がlayout Aでも現行DBに識別メタを保存していないため、同日追加拒否の比較先になり得る。費用は従来shapeに限られず、sourceなし/メタ不足のactive importがある全日付の追加取込みに及び、再実測では売上欠落を解消できない。初導入ではその本番履歴が存在しないことを前提に、新形式で開始し、旧試験履歴を持ち込まない。本番前preflightで該当日付が見つかった場合は準備未完を表示し、取込み前に把握できるようにする。将来の更新・旧試験DBに対する拒否は残すが、更新前の全取り漏らし解消や後追い禁止を運用条件にしない。開発DBの整合した作り直しは別作業であり、このdocs変更を削除許可としない。

本案は任意の時刻入力や追加の本番データ採取を要求しない。新たな実機操作が必要な確認は、対象と目的を限定した既存のowner-operated gateで行う。技術的な保存先・token・queryの選択を新たなowner判断へ細分化しない。

次のlaneの出発点（出典：2026-09-22 の外部設計相談、owner 実施）：実測は時間帯に関わらず精算区間のいずれかに入り、その区間のZ004は実測をまたぐため、Z004だけでは解けず取引単位の資料（EJ）が要る。受領後の数え直しだけでは、毎回数え直す循環を抜けられない。時計を使わない接続の未検証候補は、アプリ発行の識別コードをPOSへ記録し、EJの取引順で「記録A < 実測 < 記録B」を作る方法である。相談で確認された範囲は、SR-S4000の取扱説明書に売上金額ではない数値を印字する「番号印字」（取引外でも可）があることまでである。EJへの記録、取引の一連番号・時刻との並び、売上・Z004への副作用は実機で確かめる事項であり、採用済みの設計ではない。

## Revisit Trigger

実機で精算番号の意味・リセットの扱いが本案の条件と一致しない場合、取得済み資料の受領証拠を維持したまま精算同一性guardを見直す。Z004のsettlement_noがZ004ごとに1ずつ増えない（他のZ帳票と共有のカウンタである）と分かった場合は、相殺の判定の「前回」を直前のsettlement_noで決める規則とsettlement_noの戻りの扱い（D5）を見直す。業務日付を持つ完全な商品別ledger、過去評価額の訂正機能、部門売りからPLUへの全面移行は別の要求が出た時点で再訪する。

相殺の判定で、一つの区間にPLU書出しが2回以上レジに反映される運用が生じた場合（Consequencesの限界）、アプリが書き出したスキャニングコードと名称の組のうち今回のZ004にないものの名称も、対応が変わった名称に含める案を再訪する。履歴の範囲を決めないと、名称を別の商品へ使い回したときに区間が不完全のまま残るため、今回は採らない。

次のdesign lane「実測とPOS系列の対応を取得・保存する」の結論が出たら、[適用範囲の但し書き](#適用範囲の但し書き)に挙げた決定事項を本ADRへ加え、判定不能の範囲を狭める。
