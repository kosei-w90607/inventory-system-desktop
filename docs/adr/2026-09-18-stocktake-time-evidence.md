# 棚卸しと後着売上の時点を、観測できた証拠で分ける

## Status

proposed — 2026-09-18、owner の「設計を任せる」を受けた Codex の統合案。

対象は REQ-205 / REQ-401。実装済みの契約ではない。㉗の Design Phase の出力として、[packet](../plans/2026-09-16-stocktake-count-baseline.md) の D-D4 / D-D8 / D-D9 / D-D10 と、その派生する実装指示を置き換える案をここに集約する。D-D1〜D-D3 の snapshot 補正、商品ごとの即保存、売上と在庫の分離、確定済み評価額の非遡及は維持する。実装開始には source docs の詳細同期と独立 Plan Gate が必要。

## Context

販売の発生、精算、ファイルの受領、実測、入力の保存は異なる出来事である。日付だけの比較、保存時刻だけの比較、任意の過去60分、初回の仮時刻では、どの増減が現物数に含まれるかを証明できない。

目的は、観測できる変化を保存前に止め、判定できない後着売上を再確認へ回し、誤った実測も後から訂正できること。実際に数えた商品・数量をアプリが直接観測した、と偽装しない。

非目的は、棚卸し確定の取消、過去評価額の自動再計算、部門売りの商品への推測配賦、実POSデータの保存形式変更、汎用イベント基盤の導入。EJ parser の実装は別laneだが、下記の証拠条件と実行拒否はそのlaneの必須契約とする。

## Decision

### SPEC-STK-TIME-D1: 実測には開始と保存、アプリ内の順序には単調な番号を使う

商品を選択しただけでは計数を開始しない。「今から数える」の操作で BIZ が計数contextを発行する。context は商品、対象の棚卸し明細、開始時刻 S、商品状態の版、受領済み資料の上限IDを保持する。数量欄は新しいcontextでは空にする。紙の古い値を新contextへ自動転記しない。

「数を保存」で現在時刻 E を採り、現物を数えた時点を `[S, E]` のどこかとして扱う。S / E はアプリが観測した操作の時刻であり、物理的な計数時刻を証明するものではない。「開始してから数える、数量が動いたらやり直す」は残る外部前提である。

- `products.stock_revision` は商品単位の単調増加整数。既存商品の数量更新は `inventory_repo::update_stock_quantity` に限定し、同関数内で数量と版のchecked増分を不可分に更新する。呼出し側へ増分責任を分散させない。共通入出庫・取込み取消の戻し・棚卸し確定補正・`fix_integrity` の全経路に適用し、同じ数量への更新も版を進める。汎用 `ProductUpdates.stock_quantity` とそのSQL分岐はruntimeで除き、迂回路を残さない。新商品INSERT時の初期数量・版0は別で、既存商品の更新に流用しない。
- 数量を変えない実測基準・snapshot・要再確認flag・`pos_stock_sync` の更新、純量0の取消、差0の確定でも、同じTXで共通のchecked版更新処理を呼ぶ。数量更新済みでも追加で版が進むことは許す。履歴上の更新を最終数量の一致で省かず、減算と加算が相殺するABAも検出する。overflow時は数量・履歴を含むTX全体を拒否する。
- 保存TXでcontextの版と現在の版、対象明細の所有者・状態を再検証する。違えば書込み0で拒否し、「数えている間に記録が変わりました。もう一度数えてください」を返す。最新状態で新contextを開始すれば直前の移動が何分前でも再試行できる。
- 商品切替、画面離脱、中断、再起動で未保存contextは失効する。OSの時刻変更、復帰時に連続性を確認できないsleepでも失効する。contextの有効性をクライアントの日時申告だけで決めない。
- DB接続の置換・バックアップ復元でも、業務操作を再開する前に全contextを破棄する。別のDB状態へ古いrevisionやsource_cursorを持ち越さない。
- 保存処理は1商品1TX。`stocktake_items` の snapshot 更新とflag解消、または再実測行と補正movementを一括確定する。全商品の入力を集めてから保存しない。
- 保存済みcontextの再送は補正を再実行しない。処理済みIDで結果を照会し、保存応答の喪失を新しい実測として再実行しない。再起動後に未保存contextを復元して保存する経路は設けない。
- 版は競合検出と実測の新旧に使う。`created_at` の秒精度で同秒の先後を決めない。
- observation_revisionは、保存TX内の必要な数量・flag更新後にstock_revisionを進め、その増分後の値を記録する。同一商品で異なる実測に同じ版を与えない。複数回進めてもよいが、減少・再利用・overflowは許可しない。

Windowsでの失効機構は商品revisionと別に持つ。MNT側で suspend/resume とシステム時刻変更の通知を受け、プロセス内の `count_platform_generation` を増やす。contextは開始時のgenerationを持ち、BIZは保存TXの前と保存直前に一致を確認する。登録に失敗した状態では新contextを発行しない。終了時に通知登録を解除する。Windowsの正式な通知機構は [PowerRegisterSuspendResumeNotification](https://learn.microsoft.com/en-us/windows/win32/api/powerbase/nf-powerbase-powerregistersuspendresumenotification) と [WM_TIMECHANGE](https://learn.microsoft.com/en-us/windows/win32/sysinfo/wm-timechange) を使える（API存在確認済み、Tauriへの接続と通知順序はnative probe未実施）。

本製品の受入対象はWindows。非Windowsの製品実行で監視の成立を確認できなければ計数を利用不可として理由を表示する。Rust単体試験・WSLの開発用検証では、productionから選べないtest/dev用のgeneration供給を注入して業務ロジックを検証する。これをWindowsで監視済みという証拠にしない。

通知の到着順の補助検査として、開始時にwall-clockと `std::time::Instant` を併せて採り、保存時の両経過時間の差が1秒を超える、逆行する、または `checked_duration_since` が失敗する場合も失効させる。1秒は時計検査の許容差という契約定数で、実測が1秒以内だったとみなす閾値ではない。外部時刻と比較する計数窓にはこの観測誤差を両端へ加える。Rustの [Instant](https://doc.rust-lang.org/std/time/struct.Instant.html) はsleep時間を含むかをプラットフォーム横断で保証しないため、この差分検査だけをsleep検知として使わない。Windows L3では通知登録失敗、sleep前後、保存直前の時計変更を検証し、WSL上のmock成功で代用しない。

保存した数量Nと保存時の帳簿Lについて、進行中の棚卸しは snapshot を `system_stock=L, actual_count=N` とし、確定時の補正を `N-L` とする。独立の再実測はその場で `N-L` のmovementを作る。差0でも実測の証拠は保存するが、0数量のmovementは作らない。

force_fillは実測ではなく、補完数量とsnapshotをともに `max(現在庫, 0)` にして補正0とする。実測の窓・cursorは作らない。負の現在庫を補完で0へ書き換えない。確定後評価額は `Σ max(補正後現在庫, 0) × 評価原価` とし、保存した古いNだけで合計しない。

### SPEC-STK-TIME-D2: 入力資料を「受け取った事実」を、売上取込みとは別に残す

構文・ファイル種別を検証できたZ004のbyte列をアプリが受領したとき、`pos_import_sources` にhashで一意な資料受領記録を作る。これは売上・在庫のcommitではない。全行0、保留、取込み取消でも資料を受け取った事実は残る。raw byte列・商品名・売上値はこの表へ複製しない。

この表のIDはDBの単調増加番号。計数contextの開始時に見えていた最大IDを `source_cursor` として固定する。ファイルFの受領IDがその値以下なら、Fの内容は計数を始める前に既に存在していた。正規のPOS出力を入力として扱う前提の下で、Fの販売・返品は今回の現物数に含まれると判断できる。

これは時計に依存しない復旧経路になる。初回、精算時刻なし、時計異常、EJ取得不能でも、ファイルを受領してから対象商品を新たに実測すれば、そのファイルの在庫変動をスキップできる。時計を直したというチェックだけで古いファイルの時刻を信用し直さない。

受領IDは計数の**保存時**に取り直さない。計数中に届いたファイルを過去の実測へ含めることになるためである。同じhashの再選択でも最初の受領IDを変えない。別hashは別資料として扱う。

### SPEC-STK-TIME-D3: 精算区間は判明した境界だけを使う

IOはマシン番号、帳票種別、精算番号、精算日時をOptionで抽出し、原文の意味を保つ。BIZが証拠の信頼性を判断する。外部の時刻とアプリの時刻を直接同一視しない。

- 今回の精算は対象期間の終端の候補。前回の同じ精算系列の終端は始端の候補。番号の隣接と、実際に当該Z004がそのリセット区間を表すことをContract Probeで確認する。
- 初回や前回資料なしでは始端は不明のまま。前日0時などを置かない。十分古い同系列の既知境界を下限に使える場合も、正確な始端ではなく保守的な下限として扱う。
- 受領順と精算順は別。逆順取込み、同日複数精算、番号のリセット・桁戻り、マシン識別の変更を通常の連番と推測でつながない。系列不明なら時刻による自動適用はしない。
- 同じ精算の別hashは追加売上と決めつけない。内容の重複か訂正版か分からない間はcommitを拒否する。同一hash重複拒否も維持する。
- 取込み取消は、資料受領の事実を消さない。精算境界の証拠の有無と、売上が有効に取り込まれているかを別に扱う。0売上の資料も境界として残す。
- 精算の欠落は欠落として表示し続ける。利用者の「ファイルが無い」という回答で、欠落売上を0と認定しない。現在庫の復旧と過去売上の欠落は別の結果である。

時刻による境界には、PC時計との対応が検証された範囲だけを使う。レジの分精度は1分の幅、時計差は検証された誤差幅として広げる。接触する境界も判定不能とする。

保存形式による丸めも分けて扱う。秒精度のアプリ時刻なら計数窓の終端にその1秒の幅、分精度のPOS時刻なら取引期間の終端にその1分の幅を加え、その外側へ時計観測の誤差を加える。丸めた終端を真の終端とみなさない。モデルのCount/Sourceはこの拡張後の境界であり、外部時計の誤差がその幅に収まるという事実自体は実機probeの責務である。

時計検証が未実施・期限切れ・矛盾ありなら外部時刻の証拠を使わず、D2の受領順と再実測へ退避する。時計異常は「全ファイルを永久に拒否」ではなく「この時刻による前後判定を使用不可」にする。形式不正・商品特定不能等の別の拒否理由を解除するものではない。

PC側の時計変更を検出した場合も、外部時刻との対応を再検証する。異なる時計の対応期間に属する実測と取引を、未検証のまま同じ時軸として比較しない。受領順の証拠は日時文字列の大小に依存せず引き続き使える。

10分は時計誤差の暫定上限候補であり、安全性の実測結果ではない。年1回の時計合わせをしたという申告だけで、過去ファイルへ遡って信用を与えない。時刻対応の測定、確認対象の期間、失効、時計変更時の扱いをEJ本番有効化のContract Probeへ含める。未来時刻検査や逆転検査は異常の一部を検出する補助であり、未検出を正しい時計の証明にしない。

D4の早期returnより前に、区間の逆転と、受領順の証拠との矛盾も検査する。`received <= source_cursor` なのに信頼済み下限が計数開始Sの最も遅い候補 `S_latest` を超えるなら、開始前に存在した資料の取引が真の開始より確実に後となり両立しない。S_latestは保存Eではなく、開始S自身の保存精度と観測誤差から導く（秒の先頭へ丸めたSなら `S + 1秒 + 開始の観測誤差`）。拡張後の窓の始端はSの最も早い候補なので、この矛盾判定の閾値には使わない。下限と開始の候補範囲が重なる・接触するだけなら矛盾とは断定せず、開始の上限が不明なら仮値で補完しない。モデルではこの上限をCount.start_latestで別に表し、Noneを不明とする。実測後の通常適用を決める下限とEの比較は変更しない。

矛盾が確認された時計対応の検証状態を無効化して理由を表示し、他の判定にも信用を持ち越さない。受領事実自体が正しい限りD2によるbeforeは引き続き使える。legacy分岐も検査を迂回せず、区間自体の逆転は実測証拠の有無によらず検出する。矛盾を無視して時計を信用し続けることも、時計異常だけで受領後の再実測を永久保留にすることもしない。

### SPEC-STK-TIME-D4: 前後の判定は一つの関数で行う

基準は最新の有効な実測。実測の新旧は商品状態の版で決め、同秒のtimestampのMAXに依存しない。force_fillと廃番自動入力は実測ではなく、この基準を作らない。

まずD3の矛盾検査で使用可能な時刻証拠を確定し、その後の判定順序を以下とする。previewとcommitが同じBIZの判定を呼び、commit TXが現在の証拠で再判定する。

| 条件 | 在庫への扱い |
|---|---|
| `pos_stock_sync=false` | 既存契約どおり売上のみ。在庫連動へ推測昇格しない |
| 実測履歴そのものがない（NeverObserved） | 未実測商品として通常の在庫連動。ただし下記の共有JANの優先規則と、商品照合・重複等の既存拒否は維持 |
| 実測履歴はあるが時点証拠が欠ける（LegacyObserved） | 未実測へ読み替えず判定不能。新しい実測で移行する |
| 実測開始前に当該資料を受領済み（D2） | 全部実測前。販売・返品とも在庫変動をスキップ |
| 信頼できる取引期間の上限が実測開始Sより前 | 全部実測前。スキップ |
| 信頼できる取引期間の下限が実測保存Eより後 | 全部実測後。通常適用 |
| 期間と実測窓が重なる、境界不明、時計不明 | EJの有効な商品別証拠があれば同じ前後判定を各取引に適用。それ以外は判定不能 |

保存時刻Eだけで「全部実測前」を決めない。これにより、区間判定済みを理由に計数中のPOS販売をEJ検査から迂回させる経路を作らない。実測の時間窓内の取引は、誤差を考慮した上でも前後を確定できない限り判定不能である。

EJが判定できた場合、売上はZ004の日計純数量、在庫は実測後の純数量だけを反映する。日計0でも実測後の純数量が0とは限らない。日計0のため既存仕様上sale_recordsを作らない行でも、在庫判定に必要な商品集合とEJ取引は捨てない。

#### 判定不能からの復旧

- 最新実測が進行中棚卸しに属する商品: 従来合意どおりZ004を通常適用し、明細に要再確認flagを保存する。flagがある間はforce_fillでも確定できない。資料受領後の新しい実測保存でsnapshotを取り直し、flagを解消する。
- 最新実測が完了済み棚卸し・独立再実測に属する商品: 当該file全体の業務commitを保留する。復旧先は現在の所有者で決め、進行中の対象明細があれば未計数・自動補完でもその明細へ実測保存し、なければ完了済み明細を参照する独立再実測を使う。資料を受領済みなのでD2が成立し、再previewで保留が外れる。共有JAN・記録詳細からの訂正も同じ導線とし、通常の独立再実測で進行中明細を迂回しない。
- EJ欠落・不完全は、EJによる自動分割を許可しない理由となる。復旧のための再実測まで拒否しない。EJが取得できない場合は、上の明示的な再実測経路で進める。チェック一つで自動分割を代行しない。
- **共有JANの優先規則**: JANの候補商品が複数あり、少なくとも一つが在庫連動対象の行は、上表の未実測・通常適用より先に行全体を検査する。非連動商品との共有でも、実際にどの商品が売れたかは分からない。全在庫連動候補で当該資料が実測前と証明できる場合だけ、全候補の在庫変動をスキップしてcommit可能。それ以外（AFTER・不明・未実測・legacyを含む）はfile全体を保留し、先頭商品へ通常適用してから他の商品だけを再確認する経路を作らない。全候補が非連動なら在庫判定は不要。売上記録の先頭紐付けは既存互換として残すが、商品別売上の正確性を保証したとは記載しない。
- 共有JANの復旧では、進行中明細がある候補はその実測保存、完了済み明細がある候補は独立再実測を使う。完了済みの自動補完明細も参照先には使えるが、その自動補完自体を実測の証拠とはしない。どちらの明細もない候補は、この限定した再実測APIでは解除できない。偽の明細作成や他商品の明細への関連付けをせず保留を維持する。このケースの手軽な解除は既存のDATA-2（商品同定）の範囲と合わせて別途設計する既知の制限で、全店棚卸しを自動開始して隠さない。
- **本番前の設定検査**: 在庫連動対象のJANが別の商品にも一致する設定は、自動在庫連動の利用条件を満たさない。設定有効化時・マスタ変更時の検証と、既存設定の本番前preflightで具体的な候補商品を示す。既存のpos_stock_sync値を無断で変更しないが、「連動可能」と表示して取込み開始後に初めて恒久的な制約を知らせることもしない。shared JANの在庫を先頭へ自動配賦していた旧動作とは意図的な互換性変更であり、CSV構文を受理することとcommit可能であることを区別する。全候補の実測によるスキップは一つの資料の復旧であり、翌日以降の恒久的な自動連動の解決ではない。
- 検査は警告だけで有効化を通すものではなく、曖昧なJANを在庫連動対象として有効化する操作・新たにその曖昧さを作るマスタ変更を拒否する。既存の不適合設定は一覧に出し、商品同定の修正か、利用者による非連動への切替を案内する。非連動への切替は在庫を直す処理ではないため、その点を明示し、既存の要再確認flagも消さない。再有効化前には現在数の再確認と一意性の成立を要求する。pos_stock_syncの変更は商品状態の版を進め、開いた計数contextを失効させる。
- 上記の再確認は、既存のcount APIでmeasuredを保存することで行い、確認checkboxでは代替しない。対象の明細がない商品は前項の既知の制限に該当し、対象範囲内の解除手段が整うまで非連動のままにする。新しい商品単独の計数APIをこの条件のために無断で追加しない。
- 全行0でも、時点境界の評価や再確認に使った資料は売上0の取込みとして完了可能。要再確認・保留が解消して対象数0になった再previewで拒否しない。

保留集合はpreviewから導出する一時結果であり、新しい保留tableは作らない。再起動・preview失効後は利用者が同じfileを再選択し、hashから同じ受領記録へ接続して、現在の実測・マスタで集合を再生成する。保存済み実測と補正はDBに残り、未保存入力は復元しない。`pos_import_sources` だけから元fileの明細を復元できるとは扱わず、fileを用意できなければ未取込みのまま。要再確認flagは、通常適用されたimportに属する永続状態として別に保持する。

### SPEC-STK-TIME-D5: EJの「完全」と「商品を判定可能」を分ける

EJ本番有効化前に次を合成fixtureと承認済みサンプルで確認する。単なるparserの導入日や設定フラグでPLU本番の条件を満たした扱いにしない。

- 同じマシン・精算系列のZ004とEJを対応づける。対象精算の終端だけでなく、区間の開始をどの証拠で確認したかを持つ。初回の開始を推測しない。
- 取引ブロックの一連番号、必要な開始・終了の境界、分割ファイルの連結を照合する。存在するファイルの末尾番号だけから「続きは全部ある」と推測しない。
- 取引内の明細復元数量と合計点数、商品別の符号付き集計とZ004を照合する。日計合計一致だけを完全性の証明にしない。
- 通常販売、返品モード、数量×単価、同じ名称行の繰返し、訂正・取消を区別する。未知の行・未知の取引形式を黙って除外しない。
- 名称照合はレジへ出力した名称の規則に合わせる。名称変更・衝突・部門売りとの衝突は、現在のマスタ名だけから過去の取引を一意と扱わない。
- 時計が信頼できない場合、EJに時刻が存在するだけでは分割しない。D2の復旧は利用できる。

EJの検査が示せるのは提供資料の整合性と、証拠のある期間の分類である。店が提出していない未知の資料や、アプリ操作より前に紙へ控えた実測値の真偽まで証明するものではない。

### SPEC-STK-TIME-D6: 取消で、既に実測へ吸収した数量を二重に戻さない

数量補正はD-D5の方針を維持し、吸収済みかの判断をアプリ内の順序へ置き換える。各実測のsnapshotと同じTXで、その商品について見えていた最後の `inventory_movements.id` を `ledger_cursor` に保存する。

取消対象の有効movementについて、IDが実測のcursor以下なら、その実測のsnapshotに含まれていた。対象importの全movementは1TXなので、実測が同じimportの途中へ割り込むことはない。timestampの同秒一致で先後を推測しない。取消側はmovement IDを取得する必要があるため、旧案の「VoidedMovementの拡張不要」は引き継がない。

- 対象movementを吸収した最も早い**現在も効力を持つ実測**を探す。進行中で上書きされた旧カウントは対象外。確定済みの明細と独立再実測は残る。
- それが進行中なら、取消の数量をsnapshotにも同じ向きで戻す。`system_stock -= SUM(voided.quantity)`。後で確定する補正量と現在庫の二重増減を防ぐ。
- このsnapshot補正では実測自体のS/E、N、cursor、observation_revisionを変更しない。商品状態のstock_revisionだけを進める。取消を新しい物理実測として順序へ挿入しない。
- それが確定済み・独立再実測なら、通常の取消で在庫を戻した後、同TXに同額を打ち消すstocktake movementを作る。元の実測値・評価額を書き換えない。
- 吸収した実測がなければ、通常の取消だけ。スキップ行にはmovementがなく、戻す在庫もない。取消で元のimportが立てたflagだけを消す。
- 独立再実測とその補正はimportを参照しない。import取消で消さない。再取込みの新movementは新IDとなる。
- 再実測・snapshot変更・取消・補正・flagの更新は同一TX内で商品状態の版にも反映する。開いていた古い計数contextを無効にする。

`stock_quantity = SUM(non_voided movements)` を維持する。実測誤入力は逆仕訳だけで消さず、新しい現物確認によって補正する。

#### legacyの取消は「証拠なし」を「吸収なし」にしない

migrationは、その時点のmovement IDの最大値を不変のlegacy上限として記録する。これは旧実測が何を吸収したかのwatermarkではなく、旧実測より後に作られたmovementを区別する上限である。上限より大きいmovementは旧実測に含まれ得ない。旧実測のtimestampから正確なcursorを推定しない。

有効なlegacy観測があり、取消対象がこの上限以下で、新方式の**適用済み**実測に吸収されたことも確認できない商品は、取消全体を業務write前に保留する。legacyを吸収先探索から単に除外して通常の在庫戻しへ進まない。商品別の取消純量が0なら、在庫補正の不確実性はないが、flag・履歴・revisionの処理は維持する。

新方式のpendingだけでは、この保留を解除しない。例: 在庫10から販売-2、旧実測8で確定、新pendingに8を保存した後、通常取消とpending snapshot補正だけを行うと現在庫は10に戻る。後の確定では8へ収束するが、それまで旧確定済み実測に反する現在庫を表示するため、適用済みの新基準を要求する。復旧でpendingをN/Nにした明細は確定補正の差異件数へ加算せず、差そのものは再実測の区分で補正前L・N・差を表示する。

pendingを取消TX内で適用済みへ昇格させる案は、算術上の成立とは別に、取消の副作用として未確定の棚卸し差異まで在庫へ反映し、確定時に補正する操作契約と差異件数の意味を変えるため採らない。

復旧は取消対象商品の現在数をD1のcontextで確認する。通常の独立再実測が使える場合はその保存で解消する。進行中の明細がある場合は、**旧取込み取消の復旧専用の再確認**として、以下を1商品1TXで行う。

1. 現在庫Lと実数N、S/E、cursorを持つ再実測行を保存し、N-Lを現在庫へ即時反映する（適用済みの新基準）。
2. 進行中の当該明細をN/Nのsnapshotへ同TXで更新する。元の未適用差異はこの再実測で置き換え済みなので再度適用しない。kindをmeasuredにし、再実測RのS/E・source_cursor・時計証拠の対応を引き継ぐ。古い明細の時点証拠は残さず、保存時のsource_cursorにも取り直さない。ledger_cursorはN/Nのsnapshotが含む補正後の最後のmovement IDとする（R自身は補正前のcursorを持つ）。再実測行の版より後の版を明細へ与え、rebased_from_recount_idでRを参照する。
3. 再実測行には補正前LとN、理由「旧取込み取消前の再確認」を残し、差を隠さない。現在庫とpending差異の両方を更新しない汎用の迂回操作は許可しない。

全対象の復旧後に取消を再実行する。新しい適用済み実測が元のmovementを吸収しているため、取消の戻しと補償が相殺され、確認した現在庫を維持する。取消を中止しても再確認は現物の新しい事実として残る。これは保留解除や記録詳細からの通常再実測のactive-owner guardを解除するものではなく、legacy取消という特定の回復commandだけの契約である。

### SPEC-STK-TIME-D7: 訂正は「現在の現物」を直し、過去評価を上書きしない

棚卸し記録詳細に「今の数を確認して直す」を設け、D1と同じcontext・保存処理を使う。過去に入力した数量を、新しい実測日時だけ付けて再保存しない。

その商品の進行中明細が存在する場合は、未計数・自動補完を含め、その明細の計数へ案内する。古い完了済み記録から独立再実測で進行中の所有者を迂回する経路を作らない。この条件はUIだけでなくbeginと保存TXで検証する。D6のlegacy取消復旧だけは専用TXで再実測と進行中基準を同時更新する。

独立再実測はappend-onlyで、実測前帳簿・入力値・差・保存順序を記録する。movementの区分は明示する（確定補正 / 取消補償 / 再実測）。`created_at <= completed_at` という秒精度の推定やnote文字列の解釈で区分を決めない。差異件数は確定補正だけを数える。

大きな差の確認は補助UIに限る。現物との差があること自体は棚卸しの正常な入力なので、差10・50%などの未検証閾値を安全条件にしない。既存のカウント時在庫・入力値・差の表示、入力値の検証、保存後の訂正を最低契約とする。追加の異常値警告は実例と頻度を根拠に再訪する。

確定済みのheaderと `total_cost` は変更しない。「現在庫を直した」と「過去の報告値が正しい」は別である。差が確定前の数え違いか確定後の移動かを自動で断定しない。記録詳細に「現在庫の再確認。確定時の評価額は変更していません」を出す。

### SPEC-STK-TIME-D8: 保存先・境界・互換性

この案の保存先は以下。migration番号・index名と実装上のprivate helper名はruntime packetで既存registryと合わせるが、情報の意味を後から変更しない。raw POSデータを監査表へ複製しない。

新しいIDは正のINTEGER、cursorは0を空集合として許す非負INTEGER、revisionは非負INTEGERで、加算をcheckedにする。kindは列挙値をCHECKで制限する。新しいmeasured行では開始・保存・両cursor・版・request IDを一式で保存する。kindがauto_filledやuncountedの行へ実測cursorを作らない。sourceのIDはAUTOINCREMENT、hashはUNIQUE、recountのrequest IDはUNIQUE、flagは明細/importの組をUNIQUEとする。監査対象のparent/sourceはFKで参照し、業務取消で物理削除しない。cursorは行の参照ではなく上限なので、IDへのFKを張って0を偽の行として作らない。

| products | stock_revision | 計数中の変化・基準の変更検出、実測の新旧。数量更新はupdate_stock_quantity内部でchecked増分を強制し、数量以外の対象更新も同じTXで共通の版更新処理を通す |
| stocktakes | reconciliation_version（旧データ0、新方式1） | 旧記録の表示を保存し、移行前の式で保存された明細を区別 |

| stocktake_recounts（新設） | 明細への参照、N/L/S/E、ledger_cursor、source_cursor、observation_revision、保存request ID | 独立再実測のappend-only記録。import IDを要求しない |

計数contextは業務状態ではない一時tokenで、BIZが所有する。CMDは薄く、UIは生の時刻・版・cursorを自由に指定できない。再起動後の旧tokenを新規書込みの権限としては拒否する。保存済みrequestの重複はDBの識別子を根拠に副作用なしで扱う。

#### 保存APIとwireの契約（proposed、未実装）

| API | 入力 | 結果 / BIZの検査 |
|---|---|---|
| begin_stocktake_count | stocktake_item_id、用途（進行中の入力 / 独立再実測） | opaque count_token、対象商品の表示情報、開始時帳簿、保存先を返す。存在・最新の所有者・親状態・環境監視の稼働を検査し、同一DB snapshotからcontextを作る |

| abandon_stocktake_count | count_token | 未保存contextだけを破棄。業務数量や保存済み実測を取り消さない |

abandonはUIが持つ商品切替・画面離脱をBIZ所有のcontextへ伝える失効処理であり、時間切れだけでは代替できない。reconciliation_versionは明細の最新kindではなく、確定時に使った計算・表示契約の世代を保存する。旧完了記録へ新方式の再実測を追記しても旧評価額の意味を変えないため、kindから都度導出しない。

legacy取消の復旧では、beginへ取消対象importを結び付けた用途を追加し、BIZが当該商品にその復旧が必要なことを検査する。UIが用途を指定しただけでactive明細を即時補正できないようにする。結果に即時補正とpending基準の更新先を返す。

tokenはBIZが生成・検証するcontextの識別子で、CMD側の保管とlookupは薄いtransport処理に限る。計数開始の応答が返り「数えてください」と表示されてから実測する。保存時のS/Eやcursorをリクエストに含めず、tokenからBIZが復元する。商品変更は旧tokenを破棄して新しいbeginを行う。通常の棚卸し入力・保留画面・記録詳細からの訂正がこのAPIを共用する。

現在のtokenなしのupdate_count commandは、新しいUIへ切替えるruntimeで公開登録から外すか、同じ必須context検査へ接続する。無検査で保存できる旧入口を残さない。内部の数量保存helperを再利用することと、旧wireを安全検査なしで許可することを区別する。

保存済みrequest IDは、進行中明細では最後の保存要求、独立再実測ではappend-only行に保存する。同じ要求・同じ値の再送は再補正しない。同じID・違う値は競合として拒否する。古い進行中要求が既に別の実測へ置き換わり結果を復元できない場合は「最新の記録を確認してください」と返し、期限切れtokenを新規要求として扱わない。

公開count_tokenはサーバーが生成するUUIDで、その文字列を公開保存要求のrequest IDとする。通常保存は明細のlast request、独立再実測・legacy復旧はrecount行に同じIDを記録する。legacy復旧から派生するN/N明細には公開tokenを重複保存せず、`rebase:<recount_id>` の内部専用IDを付ける。この内部名前空間は公開saveのtokenとして受理しない。各保存先でrequest IDをUNIQUEとし、公開IDの照会が複数の保存先に一致する異常は書込みせず拒否する。

saveの入口は、DBに保存済みrequestがあるかの照会を未保存tokenの有効性検査より先に行う。保存済みなら副作用のない再送応答を返し、未保存なら有効なcontextを要求する。応答喪失時は同じ要求でsaveを再送してこの照会を使う。再起動でUIのtoken自体が失われた場合は既存の明細・記録取得で保存済み状態を確認し、古い数量を新規saveへ運ばない。照会専用の新APIは増やさない。

数量は既存の整数契約を維持し、負のactual_count・非整数・表現範囲外・補正式のoverflowは書込み0で拒否する。system_stockは負を許す。表示数値もJSで損失なく扱えるかを検査し、丸めた値を確認値として使用しない。新しいerrorの区分は「再計数が必要」「保存済み」「保存先が変わった」「入力不正」を機械的に区別し、UIがmessage文字列を解析して状態遷移しない。

previewのprivate cacheは、資料hashと、JAN照合候補・pos_stock_syncなど判定に使ったマスタ状態を保持する。commitはTX内で現在の候補と証拠を再検証し、候補が変わった場合は再previewへ戻す。取込み開始時の候補だけを信用して、途中の商品設定変更を無視しない。

アプリ内のdatetimeの表記は既存契約を維持する。比較では型として解釈する。日時文字列や商品状態の版をJSの安全整数範囲外へ無検証で渡さず、opaque tokenを往復させる。

旧DBの `counted_at` を計数開始Sとみなさない。migrationは旧producerの意味に従い分類する。

| actual_count | counted_at | 移行先 |
|---|---|---|
| NULL | NULL | uncounted |
| NOT NULL | NULL | auto_filled（廃番・在庫0の開始時自動入力。actual_count=0かつsystem_stock=0を確認） |
| NOT NULL | NOT NULL | legacy（手入力と旧force_fillが混在し、時点証拠はない） |

NULL数量に時刻だけある場合や、自動入力候補なのに0/0でない場合は既知のproducerに一致しない。安全なauto/uncountedへ推測せずlegacyとして移行異常を表示し、新実測を要求する。現在の廃番フラグから過去の種別を推定しない。根拠は旧start_stocktakeの0/0 INSERT、counted_atを省略するinsert_stocktake_item、手入力とforce_fillがともに数量・時刻を更新する既存経路。登録済みmigration v1〜v6にはこの時刻を後から埋める処理がない。runtime移行テストで各形と履歴・評価額の非変更を固定する。

新方式の作成・保存ではkindを明示し、measuredは証拠一式を必須、auto_filledは実測証拠を持たない。既存完了記録の表示・評価額はreconciliation_version=0の意味で維持し、曖昧な後着取込みでは再実測で移行する。進行中の旧実測は開始時snapshotの可能性があるため、そのまま新しい差分確定式へ流さず、再実測が済むまで確定を止める。force_fillでlegacy実測の再確認を飛ばさない。旧activeを新方式で確定する場合は、必要な再確認が解消した同TXでversion=1にする。

migrationは既存データの削除・過去の在庫補正を行わない。新しい証拠がNULLであることを安全と解釈しない。既存importから受領記録を作る場合も、過去の実測に受領cursorを後付けしない。

### SPEC-STK-TIME-D9: UIと失敗時の出口

画面の基準は既存UI-10の商品検索・数量入力とUI-07のpreview。新しい別アプリ風の画面は作らない。状態は日本語と非色シグナルで示し、hash・cursor・時計epochを通常の判断材料として露出しない。

| 場面 | 表示と次の操作 |

| 更新前の実測のため確定拒否 | 「更新前の記録です。今の数を確認してください」。対象明細を絞り、進行中の棚卸しの計数へ案内する。独立再実測でactiveを迂回しない |
| 保存済み | 当該行へ即反映。応答不明なら保存結果を照会してから再開 |
| 取込みで要再確認 | 対象商品と理由を表示。進行中明細があれば未計数でもその明細へ、なければ完了済み明細を参照する商品単位の再実測へ |
| 保留中に再起動・preview失効 | 同じfileを再選択して再preview。保存済み実測を使って残る対象を再生成し、未保存だけ新しく数える |
| 時計・期間が不明 | 「販売の前後を確認できません。今の数を確認してください」。資料は受領済みなので再実測が復旧になる |
| 資料欠落 | 欠けた精算を表示し、資料を追加する。現在庫を再実測で直しても過去売上の欠落表示を消さない |
| 記録詳細から訂正 | 「今の数を確認して直す」。過去の確定値の編集とは表示しない |
| 旧取込みの取消を保留 | 「この取込みを取り消す前に、対象商品の今の数を確認してください」。専用の再確認で現在庫と進行中明細を整え、取消を再試行する |

IME確定Enter、連打、商品切替、画面離脱・戻る、非同期応答の順序を既存UI契約どおり保護する。再previewや取込み完了後のrefetchで、保存済みの実測を未保存状態へ戻さない。Windows native L3で「数える開始→保存」「変更で拒否→数え直し」「保留→一部保存→再起動→残り」「記録詳細から訂正」を検証する。

## Rejected Options

- 日付だけの前後比較、初回の仮始端、連番抜けを0売上として確認解除する案: 証拠がない部分を安全と誤認する。
- 保存時刻だけ、または一律60分で計数中かを推測する案: 古い入力を見逃し、正しい再計数も止める。時間を経過させると解除されることは正しさの証明にならない。
- 全商品一括入力・一括補正: 入力時点が商品ごとに違うのに、commit時の現在庫へ古い値を適用する。
- EJの日計合計だけで完全性を保証する案: 相殺する取引や先頭・末尾の欠落を見逃す。
- 任意の在庫スキップ確認: 現物の再確認なしに二重減算と減算漏れを選択するだけになる。
- 生時刻を指定できる自由なバックデート: 実測時刻の自己申告を増やし、snapshot・取消の順序も壊す。
- 独立再実測を取込み取消で消す案: 取込みと別の現物確認を取り消すことになる。

## Consequences

通常処理、判定不能、初回、時計異常、EJ欠落の復旧を「取引期間と実測窓」「受領してから実測」という同じ規則で説明できる。一方、計数開始の操作と資料受領の永続化、版・cursor、旧DBの再実測移行が増える。これは誤入力の確認dialogを増やす代わりに、実際の状態変化と証拠を使うための費用である。

PLU本番はEJの取得・欠落時の拒否・再実測による復旧まで実機で検証してから有効化する方針を維持する。㉘の段階でEJがないことを「安全を保証済み」とは表現しない。時計情報の信頼条件、物理的な計数がcontext内に行われること、提出されていない資料の存在、商品別に記録されない移動は残存限界として明記する。

時計を信用できる精算系列もEJもなく、過去の実測がある商品を新しい資料が含む場合、原則その資料ごとに再確認・保留が発生する。受領後の再実測はその資料のbefore証明であり、次の日の資料のafter証明にはならない。この負担は恒常運用として推奨せず、EJ・時計・商品同定の検証を自動在庫連動の本番前提とする。設定前のpreflightで満たしていない条件を示し、再確認の手間が単に少し増えるだけと説明しない。

旧DBでは、過去の入力をlegacyへ分類することにより、アップグレード直後の最初のZ004から多数の商品が再確認・保留になり得る。preflightで在庫連動対象のうちlegacyが基準となる件数と商品一覧を表示し、新方式の実測で基準を作り直してから自動連動を始める。auto_filled自体はlegacy件数に含めず、実測基準にも使わない。ただし、その商品に別の有効なlegacy基準があればそちらで判定する。旧activeは必要な再実測後に新方式で確定する。完了済みlegacyの商品はD4の所有者ルールに沿う実測で移行できる。追加作業なしで従来どおり動く更新とは説明せず、実データでの件数確認は本番移行の受入条件にする。

本案は任意の時刻入力や追加の本番データ採取を要求しない。新たな実機操作が必要な確認は、対象と目的を限定した既存のowner-operated gateで行う。技術的な保存先・token・queryの選択を新たなowner判断へ細分化しない。

## Revisit Trigger

実機で精算番号の意味・期間・時刻対応が本案の条件と一致しない場合、取得済み資料の受領証拠を維持したまま外部時刻の最適化を止める。業務日付を持つ完全な商品別ledger、過去評価額の訂正機能、部門売りからPLUへの全面移行は別の要求が出た時点で再訪する。
