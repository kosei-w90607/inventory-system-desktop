## Context

棚卸しの数（実数）と、POS の商品別の売上（Z004）の前後が分からないと、数えた後に売れた分を引き漏らすか、数える前に売れた分を二重に引く。旧 ADR は、計数の開始の操作・資料の受領の順・全数読取りの順・EJ の取引で前後を証明しようとし、仕組みの中で多くの review の指摘を生んだ。見直しで、次の事実が分かった（事実の ID は repo 外の事実の一覧。tracked には要旨だけを置く）。

- Z004 は精算ごとの商品別の差し引き（売上 − 返品）で、精算の日時は持つが、商品別の取引の時刻を持たない。EJ は取引の時刻を持つが商品コードを持たない。同じ精算の中の「数える前か後か」はレジの資料だけでは決まらない。
- 精算回数は 4 年分の資料で減少・重複が無く、飛びは SD の本数の差と一致した（reset・再出力は資料に現れていない）。精算は日付をまたがない時刻に行われる。精算は閉店時に 1 日 1 回が基本で、同じ日の 2 回目は少なく、2 回目の多くは売上 0。締めの後に売ると、その日にもう一度精算することが月に数回ある（店主の回答）。
- 締めの後、店を閉める前に取込みと印刷をする。棚卸しは Excel に直接入れており、アプリがそれを代替する。年末の棚卸しの期間に、数え終わった商品が売れて数を直すのは 1 日に数品（店主の回答）。業務の PC は 1 台。
- 店に本番の DB と過去データは無い。今の正本（D-051）は既に「記録（`inventory_movements`）が原本、`products.stock_quantity` は写し」と決めているが、書く側は「保存した数 + 差分」で写しを進め、棚卸しの補正も保存した数から差を作る。STK-1・STK-2・取消の補償は、保存した数を差分の元にする所でだけ起きる。

owner の決定（repo 外の回答台帳。要旨）: 約束ではなく、アプリが「数え直さないと在庫が合わない」と知らせて数え直しを促す（TD-261）。数えた後に売れた分は、素描 第 3 版の形でアプリが要再確認を出し、店主がすぐ数え直す（TD-265・TD-266。締めの後の販売は量が分かるまで受け入れる）。残る穴は「黙ってずれなければよい」（TD-267）。同じ区間に売上が残った商品は要再確認にし、条件は個数 ≠ 0 または金額 ≠ 0、EJ の戻の一覧は足さない（TD-265）。精算回数を順序と欠けの知らせに使う（TD-261）。完了のとき未計数は「数を入れる」か「0 にする」（TD-263）。在庫数は記録を正とし、記録から求め直す写しにする（TD-268）。Z004 のファイルの経路は残し、精算回数の無い file は受けない（TD-261）。商品ごとの在庫連動の切替は残す（TD-298）。legacy 互換を外し、開発・試験 DB の作り直しは別の承認とする（TD-261。D-123 でリリースの前まで包括の承認に置き換えた）。評価額は棚卸しの範囲に残す（TD-261）。EJ は在庫に使わず、レシートの控えの閲覧に使う（TD-264。本 ADR の外）。共有 JAN は店内コードの lane まで在庫連動の外、停止は一括で外す、数える前／後を押して省く操作は置かない、要再確認は範囲で見せ、完了の後の要再確認は評価額を変えず差を示す、個別の穴埋めでなく 1 つの原理から導く（TD-296）。

## Decision

### 横断の約束の表

本 ADR の約束は、在庫を動かす全ての経路にかかる。経路ごとの当て方を 1 か所にまとめる（各節はこの表を引く）。求め直しの対象の原理（D2）: 求め直しの入力（その商品の計数・movement・取り込み済みの精算の一覧・在庫連動の設定）が変わる TX は、その入力に依る全ての商品を求め直す。

| 経路 | 並びの鍵（D1） | 求め直す商品（D2） | 要再確認の発火（D3） | 取消・やり直し |
|---|---|---|---|---|
| 計数の保存（「数を保存」・「入れ直す」・「0 にする」） | 既定の計数は日付 D、fresh な計数は今日と保存の時点の精算 | その商品 | D3 の窓 | 計数は消さない。後の計数で効かなくなる |
| 入庫・返品交換（レジ未処理）・手動販売・廃棄 | 業務記録の日付 | その記録の商品 | D3 の窓（判定表で計数にとって決まらないとき） | 業務記録の取消は今は無い（[65](../function-design/65-inventory-record-traceability.md) で同時に実装しない）。足すときは、逆向きの movement に元の記録の日付を持たせる |
| Z004 の取込みの確定・取消（欠けの後追いを含む） | 精算（精算日・精算回数） | 取り込み済みの精算の一覧が変わるので、計数を持つ全ての商品と、その取込みの売上か movement を持つ全ての商品（在庫連動の on / off を問わない） | D3 の窓 | 取消は movement と売上を無効にして求め直す（D7） |
| 商品の登録・一括 import の初期在庫 | 登録日（どの計数よりも前とみなす） | その商品 | 発火しない（D3） | — |
| 在庫連動の切替（D8） | — | その商品 | — | — |
| 整合性の確かめと補正（BIZ-07） | — | 全ての商品を読取りで求め、写しの数・要再確認の印・範囲のどれかが違う商品の写しを補正で書く | 補正で写しの印と範囲も直す | — |

### SPEC-STK-CNT-D1: 在庫を動かす記録を、精算と同じ一本の軸に並べる

在庫を動かす記録（計数・入出庫の movement・Z004 の売上の movement）は、次の鍵で並べる。鍵は静的で、精算の到着の遅れ・後入力で既存の記録の鍵は変わらない。

| 記録 | 鍵 `(business_date, phase, settlement_no, after_settlement)` |
|---|---|
| 精算 n（精算日 d_n）の Z004 の movement | `(d_n, 1, n, 0)` |
| fresh な計数（「入れ直す」。今日 T、保存の時点で取り込み済みの最大の精算回数 n〈鍵の n。保存した `settlement_no`〉。取込みが無ければ n は NULL） | `(T, 1, n, 1)`。n が NULL なら 3 つ目を −1 とみなす（精算回数は 0 以上なので、どの精算より前）。鍵の n は並びにだけ使い、計数に入っているかは D3 の判定の n で決める |
| 既定の計数（「数を保存」「0 にする」。日付 D）、入出庫の movement（業務日 D） | `(D, 0, NULL, 0)` |
| 初期在庫の movement（登録日 D。`reference_type` が NULL で `movement_type` が `receiving` の movement。D9） | `(D, 0, NULL, -1)` とみなす |

- 比べ方は辞書順。鍵は保存・表示の順と、在庫推移の並びにだけ使う。**記録が計数に入っているかは、鍵の大小を使わず、常に D3 の窓の判定表で決める**（鍵の前後と判定が一致しない記録がある。例: 既定の計数と同じ鍵の同じ日付の movement は決まらない、fresh な計数の後に保存された同じ日付の movement は鍵が前でも決まらない、計数の日付より後に登録した商品の初期在庫は鍵が後でも入っている）。
- 計数どうしの順も D3 の窓で決める。保存の順は、fresh な計数が、それより先に保存された計数を全て置き換える所でだけ使う（D3 の「計数どうし」）。
- 精算どうしの順は精算回数で決め、精算日は D3 の窓を日付で表すために使う。精算日と精算回数の順が食い違う Z004（精算回数が大きいのに、既に取り込んだ精算より精算日が前、またはその逆）は、窓が 1 つに決まらないので取り込まない（D4）。
- 店のレジは 1 台（machine_no は 1 種類）を前提にする。別の machine_no の Z004 は取り込まない（D4）。
- 理由: 時刻を使わずに、精算の日付と回数と保存の順だけで前後を決めるため（PC の時計とレジの時計を比べない。owner 2026-09-23）。手入力も同じ軸に置くのは、計数と入荷が日をまたいで消える・二重になる列を塞ぐため（素描の review）。

### SPEC-STK-CNT-D2: 在庫数は記録から求め直し、`products.stock_quantity` はその写しにする（D-051 の原則）

商品の在庫は、その商品の**効く計数**（D3 の「計数どうし」）の値 + D3 でその計数に「入っていない」記録の和。決まらない記録は写しでは適用し、範囲で両方を見せる。効く計数が無ければ、全ての有効な movement の和（初期在庫を含む）。

- 求め直しの原理: 求め直しの入力（その商品の計数・有効な movement・取り込み済みの精算の一覧・在庫連動の設定）が変わる TX は、その入力に依る全ての商品を、同じ TX で求め直す。経路ごとの当て方は横断の表の「求め直す商品」の列。精算の一覧が変わる TX（Z004 の確定・取消・欠けの後追い）は、精算の窓が変わるので、計数を持つ全ての商品を含む。
- 求め直しは BIZ の 1 つの関数が行い、写し（`stock_quantity`、要再確認の印、範囲の 2 値）を書く。`stock_quantity` を書くのはこの関数だけにする（整合性の補正も、この関数の結果を書く）。同じ規則で写しを書かずに求める読取りの関数を持ち、整合性の検査と完了の後の差が使う（[31](../function-design/31-biz-inventory-service.md)）。
- 写しの値: 決まらない記録は全て適用した側の値。範囲は、決まらない記録をそれぞれ適用する・しないを選んだときの最小と最大。計数どうしの衝突（D3 の 3）のときは、衝突する計数のそれぞれを土台に求めた範囲を合わせ、写しは計数値が最小のものを土台にする。決まらない記録も衝突も無ければ範囲は持たない。
- 不変条件（D-051 の Invariant の置換え）: `stock_quantity` と要再確認の印・範囲は、その商品の記録から求め直した値と等しい。
- `stock_after`（movement の変動後の在庫）は、その記録を保存した時点の写しの値と意味を定め直し、後入力で前に記録が入っても書き換えない。
- 理由: 保存した数を差分の元にしないので、確定が数えた後の入出庫を打ち消す（STK-1）、後着の Z004 の二重減算（STK-2）、取消の補償が構造上起きない。読む側（検索・一覧・低在庫・画面）は写しを読むまま変わらない。

### SPEC-STK-CNT-D3: 窓が重なる記録だけを要再確認にする

**原理**: 記録 R と計数 C は、それぞれ「物理的に起きた時刻が入り得る窓」を持つ。R の窓が C の窓より完全に前なら R は「数に入っている」、完全に後なら「入っていない」、重なれば「決まらない」。窓は店の事実だけから決める。

| もの | 窓 | 根拠 |
|---|---|---|
| 精算 n（精算日 d_n） | (精算 n−1, 精算 n]。日付では d_{n−1} から d_n まで | Z004 は精算ごとの差分、精算は日付をまたがない、精算回数は単調 |
| 入出庫の movement（業務日 D） | 日付 D の全体のうち、その記録の保存より前（事象は入力より前に起きている） | 手入力は同じ PC 1 台 |
| 既定の計数（「数を保存」「0 にする」、日付 D） | 日付 D の全体（紙の数の後入力があり得るので、保存の時刻を信じない） | — |
| fresh な計数（「入れ直す」= 今棚を見た。今日 T） | 保存の瞬間。保存の前に保存された全ての記録より後 | 「入れ直す」の操作の意味 |
| 初期在庫 | 窓を持たない申告。どの計数よりも前 | 計数は観測、初期在庫は観測の前の値 |

受け入れた近似は 1 つだけ（A1）: 精算日が計数の日付より後の精算は、計数の日付に精算が 1 本でもあれば、その計数に対して全部「入っていない」とみなす（窓の始まりはその日の締めの後で、締めの後の販売の穴。owner TD-266）。

原理から導いた判定（計数 C に対する記録 R）:

| 記録 R | 既定の計数（日付 D） | fresh な計数（今日 T、判定の n〈下の項。無ければ NULL〉、保存の時点の movement の最大 id m〈無ければ 0〉） |
|---|---|---|
| 入出庫の movement（業務日 E、id i） | E < D: 入る。E = D: 決まらない。E > D: 入らない | i ≤ m: 入る。i > m のうち E < T: 入る、E = T: 決まらない、E > T: 入らない |
| 精算 k（精算日 d_k） | d_k < D: 入る。d_k = D: 決まらない（D の全ての精算）。d_k > D: D に精算があれば入らない（A1）、無ければ d_k > D の最初の 1 本だけ決まらない、残りは入らない | n が NULL でなく k ≤ n: 入る。それ以外（n が NULL なら全ての精算）のうち d_k < T: 入る、d_k = T: 決まらない（T の n より後の全ての精算）、d_k > T: T に精算（n を含む）があれば入らない（A1）、無ければ最初の 1 本だけ決まらない |
| 初期在庫の movement | 入る | 入る |

- 「D に精算があるか」「最初の 1 本」は取り込み済みの精算で決める。欠けがあると過剰に決まらない側に倒れ、欠けを後追いで取り込んだ TX の求め直しで直る（D2）。
- fresh な計数の**判定の n** は、保存の時点の取込みのカーソル c（`seen_import_id`。保存の時点の Z004 の取込みの最大の取込みID で、取り消したものを含む。取込みが無ければ NULL）以下の取込みID を持つ、今 active な Z004 の取込みの最大の精算回数（無ければ NULL）。この表でも D6 の完了の条件でも、求め直し・完了の判定・記録の詳細の読取りのたびに今の取込みから求め、保存しない。保存した `settlement_no` は D1 の鍵の n で、判定に使わない（2026-10-23、b1 の Plan Review closure〈Codex〉の是正。round 3 の「n を使うのは精算回数 n の active な取込みがあるときだけ」を置き換えた）。理由: 「k ≤ n なら入る」は、計数の前に取り込まれた精算 n が今もあり、k がその系列で n より前であることに依る。精算回数は取消の後に別の取込み（D7 の正しい版、初期化の後の新しい系列）が再び使うので、番号だけでは計数の前に見た精算の証拠にならない（精算 1 の後に入れ直し、精算 1 を取り消してレジを初期化し、新しい精算 1 を取り込むと、番号 1 の active な取込みがあるだけで、計数の後の売上を数える前の売上と取り違えて黙ってずれる）。取込みID は使い回されない（AUTOINCREMENT で、取消は行を消さない。[POS](../db-design/pos-tables.md)）ので、c 以下の active な取込みは保存の前に取り込まれて今もある精算だけで、その最大が計数の前に起きたことの確かな精算になる。判定の n の精算を取り消すと、c 以下に残る active な取込みの最大へ下がり（無ければ NULL）、日付の判定に倒れる（過剰に決まらない側）。取り込み直した取込み（D7）は保存の後の取込みなので判定の n にならず、日付で判定する（Consequences の過剰側）。
- **計数どうし**: 計数 C2 の窓が C1 の窓より完全に後なら、C1 は効かない。既定どうしは日付で決め（D1 < D2 なら C2 が後、同じ日付は重なる）、fresh な計数は、それより先に保存された全ての計数より後。fresh な計数 F の後に保存された既定の計数 C（日付 D）は、D < T なら F が後、D = T なら重なる、D > T なら C が後。fresh どうしは保存の順。効く計数は、ほかのどの計数よりも前でない計数で、1 つならそれ、重なる複数で値が同じなら 1 つとみなし、値が違えば衝突（下の 3）。値が同じで既定の計数と fresh な計数が重なるときは、fresh な計数を代表にし、その窓とカーソルで判定する（窓が狭く、保存の前の記録を全て含む観測のため）。
- 要再確認の理由（どれかに当たれば要再確認）:
  1. **決まらない精算の行**: 効く計数にとって決まらない精算の取込みに、その商品の有効な Z004 の movement がある、またはその取込みのときに在庫連動だった（`sale_records.stock_linked=1`）その商品の行が個数 ≠ 0 または金額 ≠ 0 で現れた（owner TD-265。同じ精算で売れて戻り、個数・金額とも 0 になった分は見つからない）。判定は取込みのときの連動で決まり、今の `pos_stock_sync` に依らない（連動を切っても、連動中に作った movement と行は残り、理由と範囲も残る。D8）。
  2. **決まらない入出庫**: 効く計数にとって決まらない、その商品の入出庫の movement がある（初期在庫は入らない）。
  3. **計数の衝突**: 効く計数の候補が重なり、値が違う。
- 要再確認の間の在庫は範囲で見せる（例「4〜5」。D2。owner の決定 TD-296）。
- 解け方: 棚を見て「入れ直す」（fresh な計数）。それより先に保存された全ての記録を含む数になるので、保存の後に起きうる記録（今日のこれからの精算・今日の日付で後に入れる入出庫）だけが残る。売り切れて棚に無ければ 0 を入れれば解ける。精算日が D より後の S（休業日・締めを翌日にした日に数えた）が決まらないときは、S を取り込んだ後の入れ直しで解ける。
- 要再確認は保存した flag ではなく、求め直しの結果である（解け方も求め直しで自然に満たす）。
- 文言: 「○○は数えた日に売り買い（入出庫）がありました。棚の数を確かめて入れ直してください」。取込みの結果と棚卸しの画面（要再確認の一覧）に出す。
- 「売れたのは数える前／後と分かっている」を店主が押して入れ直しを省く操作は置かない（記憶に頼る形にしない。owner TD-261 の「約束より警告」、TD-296 で確認）。

### SPEC-STK-CNT-D4: Z004 は精算回数で識別し、並べ、欠けを知らせる

- 取り込む Z004 は、マシンNo. と精算回数（10 進の整数）と精算日を持つものに限る。持たない file（従来の形）は preview で「精算回数の無い file は取り込めません」とし、確定しない（owner TD-261 の Q9 = c。ファイルを選ぶ経路は残す）。
- 正常な行が全て 0 の Z004（その精算で PLU の売上が無かった）は、売上と movement を作らず、精算の識別メタだけを持つ取込みとして受ける（精算の並び・D3 の窓・欠けの判定に入る）。
- 同じ machine_no・精算回数の active な取込みが既にあり、hash が違う file は、同じ精算の別の版として取り込まない（「同じ精算と思われる別の資料が既に取り込まれています」）。同じ hash は今までどおり重複として拒む。取り消した取込みは比べる先にしない（誤った版を取り消して、正しい版を取り込める）。
- 同じ精算日の別の精算は、確認なしに別の取込みとして入る（D-071 の Z004 の側の「同日別 hash の利用者確認」を、精算回数の照合で置き換える）。
- 並び: D1。精算日と精算回数の順が既に取り込んだ（active な）精算と食い違う Z004 は取り込まない（「レジの日付か番号が前の精算と合いません。レジの時計か、レジの入替・初期化を確かめてください」）。別の machine_no の Z004 も取り込まない（「レジの番号が前の精算と合いません。レジの入替・初期化を確かめてください」）。machine_no は取り消した取込みとも比べる（版でなくレジを示すので、誤った版を取り消して取り込み直す D7 を妨げず、全ての取込みを取り消した後に別のレジの精算回数を同じ系列とみなさない。2026-10-22、b1 の Plan Review round 3 の是正）。取り消した取込みとだけ合わないときは、拒否の文で原因の取り消した取込み（取込みID・精算回数・取込み日・レジ番号）を名指す（最初に別のレジの file を取り込んで取り消した DB で、店のレジの file が拒まれる理由を利用者が分かるように。照合の基準を入れ替える操作は持たない。2026-10-23、owner の決定〈repo 外の回答台帳 TD-388〉。文は [32](../function-design/32-biz-csv-import-service.md) の表の順 2）。これらは reset・時計の戻りの検知を兼ねる（レジの日時は検知と窓の日付にだけ使い、時刻を PC の時計と比べない）。
- 欠けの知らせ: 取り込んだ精算回数の最小から最大の間に欠けた番号があれば、取込みの画面に、欠けを連続した区間で「精算 n〜m が取り込まれていません」（1 つなら「精算 n が取り込まれていません」）と出す（欠けた精算の売上は在庫に入っていない）。知らせの数は区間の数で、欠けた番号の数に依らない（壊れた大きな精算回数を受けても止まらない）。後から欠けを埋める Z004 は普通に取り込める（求め直しで反映する）。
- 精算日が PC の今日より後の Z004 は、取り込むが「レジと PC の日付がずれている可能性があります」と知らせる（素描 R2。時刻の同期は求めない）。
- 同じ JAN を複数の商品が持つ行（色違い・サイズ違いで同じ JAN）: 店内コードの lane ができるまで在庫連動の外に置き、売上だけを今の規則（先頭の商品）で記録し、どの候補の在庫も動かさない（owner の決定、repo 外の回答台帳 TD-296。旧 ADR の「file 全体を保留して全候補を数え直す」は持たない）。候補に在庫連動の商品があっても同じで、行エラーにしない。その商品は要再確認にもならない（在庫は計数と手入力だけで求まる）。BIZ-01 の不変条件: 変更の後に、在庫連動の商品と同じ JAN を持つ別の商品があってはならない（どの経路〈商品の登録・修正・一括 import・在庫連動の切替〉で、どちらの商品を変える場合でも、既存の `validation` で拒む。[30](../function-design/30-biz-product-service.md)）。共有 JAN の商品が在庫連動に見えないようにする（旧 ADR の本番前の設定検査を引き継ぐ）。

### SPEC-STK-CNT-D5: 計数の入力（既定の計数と fresh な計数）

- 計数は商品ごとに即保存する（1 商品 1 TX）。計数の開始の操作（begin）・token・計数 context は持たない。
- **既定の計数**（棚卸しの画面の「数を保存」と、完了の前の「0 にする」）: 日付 D の既定は PC の今日。「前の日の分を入れる」を選ぶと日付を選べる（後入力。今日より後は選べない）。保存の画面に D を常に出し、同じ画面を開いたまま PC の日付が前の保存から変わったら（深夜の 0 時をまたいだ等）、保存の前に確かめる。
- **fresh な計数**（要再確認の一覧の「入れ直す」と、棚卸しの画面の商品の「入れ直す」）: 今棚を見た数。日付は今日だけ（選べない）。保存の時点の、取り込み済みの最大の精算回数（D1 の鍵の n）と、movement の最大 id m と、Z004 の取込みの最大の取込みID c（取り消したものを含む。無ければ NULL）を一緒に残す（D3 の窓と判定の n）。打ち直し（誤った数を直す）もこの操作で行う。
- 後入力の既定の計数で、その商品に、それより後の計数（D3 の「計数どうし」）が既にあれば、保存の前に「後の数が既にあり、そちらが効きます」と示す（保存は拒まない）。
- 残る穴（受け入れ。素描 R6）: 紙やメモに数えて後で入れるときに日付を選び忘れると、数えた後の売上が引かれず過大になる。日付の表示と変わり目の確認で減らすが、消えない。

### SPEC-STK-CNT-D6: 棚卸しの完了と評価額

- 棚卸しは、対象の商品の一覧（明細）と、完了のときの評価額を持つ。明細の計数は、棚卸しの画面から保存した計数（明細を参照する）。
- 完了の条件（全て満たしてから）:
  1. 明細の効く計数（日付 X、fresh なら D3 の判定の n）について、決まらない精算になりうる精算が取り込まれている。次のどちらかなら未取込み（`settlement_pending`）: (i) 精算日が X 以上の取り込み済みの精算が無い。(ii) 取り込まれていない精算回数 k（fresh で n が NULL でなければ k > n）で、隣の取り込み済みの精算 a < k < b の精算日が d_a ≤ X ≤ d_b のものがある。(iii) 既定の計数（と判定の n が NULL の fresh な計数）について、精算日が X より前の取り込み済みの精算が無い（その日の最初の精算が抜けていても判定できないため。導入の初めは、X より前の日の精算を 1 本取り込めば (iii) は解ける。その間に欠けた精算があれば、(ii) の pending はそれを取り込むまで続く）。大晦日に数えて締めや取込みが翌日なら、完了もその取込みの後。
  2. 明細の商品に要再確認が 0。
  3. 未計数の明細に「数を入れる」か「0 にする」を済ませた（owner TD-263 の Q7 = b。帳簿の数とみなす force_fill は持たない）。「0 にする」は値 0 の既定の計数を保存する（日付は「前の日の分を入れる」と同じく選べ、既定は今日。休業日に押して次の営業日の精算まで完了できなくなるのを避ける）。まとめて 0 にする操作を置く。完了の時点で廃番かつ在庫 0 の商品の明細は、未計数でも完了を止めない（数える対象外。計数の記録を作らない）。
- 取り込み済みの最後の精算より後の精算（その日の最後の締め）をまだ取り込んでいないことは、アプリには分からない。完了の確認の文で「その日の最後の精算を取り込みましたか」を確かめる（受け入れた穴 H2。Consequences）。
- 評価額（owner TD-261 の Q12 = 残す）: 完了の TX で、各明細の評価数量を `max(その時点の在庫, 0)`（`valuation_quantity` に保存）、評価原価をその時点の原価に固定し、[35 §20.5a](../function-design/35-biz-stocktake-service.md#205a-評価額の計算価格の基準数量と店の丸め) の関数（価格の基準数量と店の丸め、SPEC-STK-VAL-D1〜D6）で総額を求めて保存する。完了は在庫を動かさない（計数の保存で既に在庫に入っている）。
- 完了の後の差（owner の決定 TD-296）: 完了した評価額は変えず、差を示す（確定済み評価額の非遡及は owner 2026-09-16 の判断）。完了の TX で、完了の時点のカーソル（Z004 の取込みの最大の取込みID〈取り消したものを含む。無ければ NULL〉・計数の最大 id・movement の最大 id）を棚卸しに保存する。棚卸しの記録の詳細は、明細ごとに「完了の時点の在庫」を今の記録から求め直す。範囲は、完了の評価に入れた記録（完了の時点にあった記録。日付によらない）に、完了の後に入れた完了の前の入出庫・初期在庫・精算の記録を足したもの（計数は除く: 完了の後に保存した計数は、完了の前の日付を選んだものも次の観測で、完了の時点の在庫を置き換えない。2026-10-23、b1 の Plan Review closure の是正）（2026-10-22、b1 の Plan Review round 3 の是正で、未来の日付の精算と入出庫が評価に入り比較から外れて偽の差を出す穴を閉じた）: 入出庫と初期在庫の movement は id がカーソル以下か業務日が完了日以前のもの（完了の後に入れた完了日以前の日付の記録が差になる）。精算は精算回数が完了の時点の精算の n（取込みのカーソル以下の取込みID を持つ、今 active な取込みの最大の精算回数。無ければ NULL。D3 の判定の n と同じ求め方で、取消の後に別の取込みが同じ番号を使っても数えない。2026-10-23、b1 の Plan Review closure〈Codex〉の是正）以下のもの（精算日によらない。完了の後に埋めた欠けを含む）と、精算日が完了日より前のもの。計数はカーソル以下。その `max(…, 0)` と `valuation_quantity` を、凍結した評価原価でそれぞれ §20.5a の関数で評価し、丸めた後の総額を差し引いて参考として示す（負の数量を関数に渡さない。読取りで求め、保存しない）。求め直した完了の時点の在庫が要再確認（範囲 lo〜hi）の明細は、差を確定の差と分け、「要再確認」の印と差の範囲（`max(lo,0)` と `max(hi,0)` をそれぞれ `valuation_quantity` と比べた幅、評価額も同じ 2 端で評価した幅）で示し、確定の差の合計に入れない（決まらない記録による差を確定の数として出さない）。完了した `total_cost`・`valuation_cost_price`・`valuation_quantity` は書き換えない。
- 棚卸しの中断・再開、進行中は 1 件だけ、棚卸し中の商品登録で明細を足す、は今のまま。

### SPEC-STK-CNT-D7: 取消と取り込み直し

- Z004 の取込みの取消は、その取込みの movement と売上を無効にし（`is_voided`、今のまま）、横断の表の「求め直す商品」を求め直す。補償の movement は作らない。
- 計数は消さない（誤った数は「入れ直す」で直す）。入出庫の業務記録の取消は今は無い（65）。足すときは、逆向きの movement に元の記録の日付を持たせる。
- 取り込み直しは、取り消した精算と同じ精算回数の file を新しい取込みとして確定する（D4 の同じ精算の版と順の比べる先に取り消した取込みは入らない。machine_no は取り消した取込みとも比べるが、取り込み直す正しい版は同じレジの資料なので妨げない）。取り込み直した取込みは、それより前に保存した fresh な計数と完了の時点のカーソルにとって後の取込みなので、判定の n・完了の時点の精算の n にならず、日付で判定する（番号では取り消した版と同じ精算かを確かめられない。D3。Consequences の過剰側）。

### SPEC-STK-CNT-D8: 在庫連動の切替

- 商品ごとの在庫連動（`pos_stock_sync`）は残す（owner TD-298 で、Q9 = c が切替を外す意味を含まないことを確かめた）。連動していない商品の Z004 の行は売上だけで movement を作らない（今のまま）。切替の TX はその商品を求め直す。
- 連動をやめる（true → false）に記録や確認は要らない（旧 ADR の非連動化の記録・未調整の issue は持たない）。
- 連動を始める（false → true）は、連動なしで取り込んだ Z004 の売上（`sale_records`、`stock_linked=0`、個数 ≠ 0 か金額 ≠ 0）が全て効く計数に確実に「入っている」（D3）ときだけ許す。「入っていない」か「決まらない」売上が 1 件でもあるとき、効く計数が衝突しているとき、効く計数が無く連動なしの売上が 1 件でもあるときは拒否し（`recount_required`）、「連動しない間の売上があります。今の数を入れてから在庫連動にしてください」と案内する（連動しない間の売上は movement が無く、写しに出ないため）。
- 連動の切替は、それより後の取込みにだけ効く（取込みのときの連動を `sale_records.stock_linked` に残し、過去の movement と行の扱いを変えない）。

### SPEC-STK-CNT-D9: 保存の形

- `inventory_movements` に並びの鍵の列 `business_date`・`phase`・`settlement_no` を足す。初期在庫は `reference_type` が NULL で `movement_type` が `receiving` の movement で見分ける（商品の登録と一括 import だけが作る）。demo の seed（`src-tauri/src/seed_demo.rs` の `seed_sales`）の売上の movement（`sale_auto`、`reference_type` が NULL）は初期在庫にせず、業務日で窓を持つ入出庫の movement として判定する（2026-10-22、(b) の最初の lane〈b1〉の起票で決めた。(a) の Plan Review の申し送り。理由: `reference_type` だけで見分けると、seed の売上が計数のどれよりも前とみなされ、計数の後の売上が引かれない。seed を Z004 の取込みの形に作り直す案は、開発・試験 DB の作り直しと seed の書き直しを要し、得るものが無い）。
- 計数は append-only の新しい表（`stock_counts`）に置く: 商品、値（非負の整数）、種類（既定 / fresh）、日付、`settlement_no`（fresh だけ。保存の時点の最大の精算回数、取込みが無ければ NULL。D1 の鍵の n）、`seen_movement_id`（fresh だけ。保存の時点の `MAX(inventory_movements.id)`、無ければ 0）、`seen_import_id`（fresh だけ。保存の時点の `MAX(csv_imports.id)`〈取り消したものを含む〉、取込みが無ければ NULL。D3 の判定の n を求める。b1 の migration が足す）。fresh の `settlement_no` は取込みが無ければ NULL（0 は実際の精算回数として使える値なので印に使わない）、棚卸しの明細への参照（任意）、保存の連番、保存時刻（表示用）。`stocktake_items` は対象の一覧と評価の保存に残し、計数の値の正本にしない。
- `csv_imports` に `machine_no`・`settlement_no` を足す。`sale_records` に取込みのときの連動 `stock_linked`（0/1）を足す（D3 の理由 1・D8）。
- `products` に写しの `stock_recheck`（0/1）・`stock_range_low`・`stock_range_high` を足す。
- 完了の後の差のために、`stocktake_items.valuation_quantity` と、stocktakes に完了の時点のカーソル（`cutoff_import_id`・`cutoff_count_id`・`cutoff_movement_id`）を足す（D6）。
- 外すもの（旧 ADR の設計と、D-109 で `#[cfg(test)]` に置いた時点証拠の schema・code）: `pos_import_sources`・`pos_source_scans`・`stocktake_recounts`・`stocktake_recount_flags`、`stocktakes.reconciliation_version`、`stocktake_items` の observation_kind 以下の証拠の列、`products.stock_revision`・`pos_sync_disabled_revision`、`inventory_movements.stocktake_adjustment_kind`・`stocktake_recount_id`、app_settings の `stocktake_legacy_movement_ceiling`、準備照会（`get_pos_stock_readiness` と issue）。
- 詳細の正本は [tracking](../db-design/tracking-system-tables.md)・[POS](../db-design/pos-tables.md)・[master](../db-design/master-tables.md) の「計数の置き場と在庫の求め直しの契約」。

### SPEC-STK-CNT-D10: 移行（legacy 互換を持たない）

- legacy 互換（旧方式の実測を区別する kind・上限・再確認の状態機械）は持たない（owner TD-261 の Q11 = b）。本番の DB は無い。
- runtime の migration は、棚卸しの明細か Z004 の取込みを 1 件でも持つ DB では止まる（失敗にして何も変えない）。そうした開発・試験 DB（owner の PC の L3 用の DB を含む）は作り直す（リリースの前まで包括で承認済み。古い file は消さずに移す。[decision-log](../decision-log.md) D-123、[22 §16](../function-design/22-mnt-migration.md) の作り直しの手順。対象と保全の範囲は作り直しを伴う配布の単位の packet が書く。2026-10-18 に D-119 (8) の「作り直しを 1 回にまとめる順」を置き換えた）。棚卸しと Z004 の取込みが無い DB では、既存の movement の `business_date` を参照先の業務記録の日付（初期在庫は登録日）から埋め、求め直しで写しを書く。求め直した値が移行の前の `stock_quantity` と違う商品は、黙って書き換えず、件数と商品ごとの old / new を操作ログ（`integrity_fix` と同じ形）に残し、起動の後に整合性の画面で知らせる。D4 の共有 JAN の不変条件に既に違反している組（在庫連動の商品と同じ JAN を持つ別の商品）は、自動では変えず、整合性の画面で知らせる: 整合性の検査（[36](../function-design/36-biz-integrity-check.md)）が今の DB から組を求めて JAN ごとに商品コードを並べ、直し方（どちらかの JAN を直すか、在庫連動を外す）を示す。違反は BIZ-01 の不変条件で新しく作られないので、直すと一覧から消える（2026-10-22、b1 の起票で、「件数と商品コードを操作ログに残す」を置き換えた。理由: 操作ログの記録は直した後も残り、直したかを示せない。組を移行の時点に記録しなくても、今の DB から同じ組が求まる）。
- 理由: 旧行を新しい軸へ黙って移す規則を持たない（旧行の位置は時刻からしか推せない）。

### SPEC-STK-CNT-D11: EJ は在庫に使わない

- 売上と返品の打ち消し合いの判定、EJ の区間と Z004 の対応づけ、EJ の完全性を在庫の前提にすること、`ej_unverified` は持たない（owner TD-265 の Q2 = A＋B）。
- EJ は同じ SD の走査で取り込み、レシートの控えの閲覧に使う（owner TD-264 の Q13。設計は後続の lane。[backlog](../backlog.md)）。EJ parser（IO-08）は残す。

### SPEC-STK-CNT-D12: 停止 ADR との関係

本 ADR の runtime は 2 つの配布の単位に分ける。

- (a) 停止に触れない単位: 並びの鍵・求め直しの関数・入出庫と商品登録の切替・整合性の突合の相手の変更。計数が無い間は値が今と同じ。(b) の前に入れてよい。
- (b) 停止を外す単位: 計数・完了・Z004 の確定と取消を新しい経路で置き換え、[停止 ADR](2026-09-23-legacy-stocktake-z004-write-stop.md) の 5 つの入口（棚卸しの開始・保存・確定、Z004 の確定・取消）をまとめて外す（SPEC-STOP-D6 のとおり部分的に外さない。owner の決定 TD-296 で確認）。停止 ADR の「⑤」は、この (b) の単位を指すと改めた。
- (a) と (b) の境の細部（2026-10-18、(a) の起票〈Plan Packet `docs/archive/plans/2026-10-18-stocktake-count-runtime-a.md`〉で決めた）: (a) は精算（Z004、`phase = 1`）を含まない記録の全部を持つ。並びの鍵の 3 列（`business_date`・`phase`・`settlement_no` と `phase` と `settlement_no` の対の CHECK）・`stock_counts`・写しの 3 列の migration（[22 §19](../function-design/22-mnt-migration.md)）、求め直しの関数のうち計数・入出庫・初期在庫の窓（D3 の判定表の「入出庫」「初期在庫」の行と「計数どうし」、要再確認の理由 2・3）、入出庫 4 業務と商品登録・一括 import の切替、整合性の突合の相手と画面。(b) へ回すもの: Z004 の movement と `phase = 1` を結ぶ CHECK（`inventory_movements` の 2 回目の作り直し）、`csv_imports` の machine_no・settlement_no と `sale_records.stock_linked`、棚卸しの完了の列（`valuation_quantity`・カーソル）と fresh な計数の取込みのカーソル（`stock_counts.seen_import_id`）、求め直しの「精算 k」の行と要再確認の理由 1、D4 の共有 JAN の不変条件と、移行の前から違反している組の知らせ（D10 の最後の文）、D8 の在庫連動を始める検査、商品の結果・在庫推移の要再確認と範囲の表示、`MovementRecord` の並びの鍵。理由: 停止中の旧本体（test だけが呼ぶ Z004 の確定と取消。SPEC-STOP-D3）の fixture は精算回数を持たず、(a) で Z004 と phase を結ぶ CHECK を入れると、旧本体の回帰 test が (b) で旧本体ごと外れるまで書けない。(a) の間、`phase = 1` の movement を作る経路は無い（Z004 の確定は停止中。旧本体は `phase = 0` で書く）ので、求め直しは `phase = 1` の行を見たら誤りで止まる。
- (b) を 2 つの lane に分けた（2026-10-22、(b) の最初の lane の起票〈Plan Packet `2026-10-22-stocktake-count-runtime-b1`〉で決めた）: b1 は停止を外す単位で、上の「(b) へ回すもの」と本 ADR の (b) の契約のうち、次の b2 の分を除く全部を持つ（計数の保存・要再確認の一覧・完了と完了の後の差、Z004 の識別・確定・取消、精算の窓と理由 1、D4 の共有 JAN の不変条件と移行の前からの違反の知らせ、D8 の在庫連動を始める検査、停止 ADR の 5 つの入口・旧本体・D-109 の時点証拠の schema と code の撤去、2 回目の `inventory_movements` の作り直し）。b2 は要再確認の範囲と計数の履歴を商品の画面で見せる単位で、商品の結果の写しの 3 列（[40](../function-design/40-cmd-product.md) の商品の get / search の結果、[20](../function-design/20-io-product-repo.md) の商品の読取り）と、商品一覧・在庫照会・商品フォームの在庫の欄の範囲の表示（[50](../function-design/50-ui-product-list.md)・[58](../function-design/58-ui-stock-inquiry.md)・[51](../function-design/51-ui-product-form.md) の「在庫数の表示」の項）、在庫変動の履歴に計数の行を混ぜること（[65](../function-design/65-inventory-record-traceability.md) の D-118 の節の 1 つ目の項、[66](../function-design/66-ui-stock-movements.md)）と `MovementRecord` の並びの鍵（[21](../function-design/21-io-inventory-repo.md)）を持つ。理由: 停止を外して黙ってずれないために要るのは、書く経路・守り（D4・D8）・要再確認を見せる所（棚卸しの画面の一覧・取込みの結果・整合性の検査）で、b2 は読取りの表示だけ。b1 の後・b2 の前の版では、商品の画面は写しの値だけを出し（要再確認の範囲を出さない）、在庫変動の履歴に計数の行が無いので、計数を保存した前後で変動後の値が履歴の差分と合わないことがある（記録と写しは正しい）。初めて店へ入れる版は b2 まで含む（[Plans の導入の前の関門](../Plans.md#導入の前の関門) の 2.）。

## Rejected Options

- 旧 ADR の形（計数の開始の操作と受領の順・全数読取りの順で前後を証明し、判定不能を要再確認にする）を続ける: 仕組みが review の P1・P2 の大半を生み、数えた商品が売れるたびに要再確認が続く（D-116 の限界）。owner は Q1 で素描の形を選んだ。
- 「数えたらその場で保存する」「締めの後に売ったら 2 回目の精算をする」を店の約束にする: 約束に頼らず、アプリの知らせで促す（owner TD-261）。
- 締めの後の販売を、計数の日付より後の精算でも決まらない扱いにする（素描 R1 の (b)）: 毎日売れる商品の入れ直しが続く（D-116 の限界と同じ連鎖）。owner は (a) 受け入れを選んだ（TD-266。A1）。
- EJ の戻の行の名前とその区間に数えた商品を突き合わせる（第二意見の案 D）: 頻度に対して重い。owner は足さないと決めた（TD-265）。
- 在庫数を保存し続け、各 writer に前後の分類と補償を足す（Q8 の (a)）: 求め直しの関数を部分的に持ったうえで、writer の数だけ分類と補償の誤りの余地が残る（(a) ⊇ (m)）。
- 写しも持たない（Q8 の (b)）: 一覧・並べ替え・低在庫で毎回全商品を求め、同じ規則を SQL と Rust の 2 か所に書く危険が出る。得るものが少ない。
- 要再確認を保存した flag の表で持つ: 求め直しと同じ入力から同じ TX で求まり、保存すると解消の規則を別に持つことになる。
- 鍵の大小だけで計数に入っているかを決める（round 1 の前の形。同じ鍵の中の順を使わない）: fresh な計数が、先に保存した同じ日付の入出庫を決まらないとし（過剰）、同じ日の 3 回目の精算を二重に引き（過小）、打ち直しの方法が無かった。窓の原理で 1 つにまとめた。
- fresh な計数が吸収した記録の集合を保存する: 1 列のカーソル（`seen_movement_id` と精算回数）と同じ強さで保存が多く、欠けの後追いで過剰に要再確認になる。
- 重なる既定の計数（同じ日付）は保存の新しい方を効かせる: 紙の古い数を後から同じ日に入れると、棚の新しい数が古い数に戻る（過去の review の反例）。fresh な計数だけが先の計数を置き換える。
- 計数の置換えを記録や UPDATE で持つ: append-only のまま、効く計数の選び方で足りる。
- 精算回数の無い Z004 を、同日追加の利用者確認で通す: 確認だけでは同じ精算の二重計上を防げない（過去の review の反例）。owner は Q9 = c を選んだ。
- legacy の行を新しい軸へ移す: 旧行の位置は時刻からしか推せない。本番の DB は無い（Q11 = b）。

## Consequences

- 楽になること: 計数は「数えたら保存」、直すときは「入れ直す」。計数の開始の操作・token・版・受領の記録・全数読取り・EJ の完全性・legacy の状態機械・取消の補償が無くなる。STK-1・STK-2 は構造上起きない。整合性の検査は「写しと求め直しの比較」に縮む。
- 店主の手間: 普段は数えたら保存し、前の日の分を入れるときだけ日付を選ぶ。締めは SD → 取込み → 要再確認の数個を棚で見て一覧から入れ直す → 印刷。大晦日は締め → 取込み → 入れ直し → 完了（締めが翌日なら完了も翌日）。
- 残る穴（owner は「黙ってずれなければよい」と受け止めた。TD-267）:
  - 締めの後の販売（A1、素描 R1、受け入れ。TD-266）: その日の精算がある日に、最後の精算の後に客へ売り、その日にもう一度精算しないと、その売上は翌日の精算に入り、その日の計数に対して「入っていない」とみなされる。数える前に売れていれば二重に引かれて過小になる。その日にもう一度精算すれば、その精算はその日の計数にとって決まらない精算になり要再確認で拾える（店は締めの後に売るとその日にもう一度精算すると答えた。TD-279）。
  - 日付のずれ（素描 R2）: PC の日付とレジの日付がずれると、手入力と精算の窓が 1 日ずれる。精算日が PC の今日より後なら知らせ、精算日と精算回数の順の食い違いは取り込まない（D4）。
  - 打ち消し合い（素描 R3）: 同じ精算の中で売れて戻り、個数・金額とも 0 なら見つからない（TD-265 で受け入れ）。
  - 共有 JAN（素描 R4）: 店内コードの lane ができるまで在庫連動の外で、売上だけを記録する（D4、TD-296）。その商品の在庫は計数と手入力だけで、レジの売上では減らない。
  - 部門キーで売った商品（素描 R5）: Z004 に出ないので要再確認にもならず、在庫は過大のまま次の計数まで残りうる。今の売上は大半が部門キーで、本規則が効くのは PLU（スキャン）で売るようになった商品だけ。
  - 日付の選び忘れ（素描 R6）: D5。
  - 入出庫を事象の前に入力した場合: 届く前に入庫を入力してから、棚を見て「入れ直す」と、その入庫は数に入っているとみなされ、品が届いた後に在庫が実物より少なくなる（例: 棚 5、未着の入庫 +3 を入力、入れ直して 5、届いて実物 8・写し 5。窓の「事象は入力より前」の前提が崩れる）。頻度は店に確かめる（[backlog](../backlog.md) の問い）。
  - 最後の精算の取込み忘れ（H2）: その日の最後の精算を取り込まずに完了すると、アプリは決まらない精算が残ることを知り得ない。完了の確認の文で確かめる（D6）。
  - この列挙（締めの後の販売（A1。その日にもう一度精算しない場合）、日付のずれ、同じ精算で個数・金額とも 0 に打ち消し合う売りと戻り、共有 JAN（在庫連動の外）、部門キーの販売、日付の選び忘れ、入出庫を事象の前に入力した場合、その日の最後の精算の取込み忘れ（H2））が受け入れた穴の全てで、D-118 の Guarantee range と packet の Design Readiness も同じ列挙を引く。
- 過剰側（安全な側）に倒れる所: 休業日に数えた計数は、翌営業日の精算の全体が決まらない精算になる（H4。実際には休業日に売上が無くても、その精算で売れた商品は要再確認）。入出庫の業務記録の取消を足したとき（今は無い。65）、逆向きの movement は元の記録の日付を持つので、同じ日付の計数があると要再確認になる（H5。取消で元に戻っただけでも出る）。fresh な計数の保存の前に取り込んだ精算のうち判定の n の精算を取り消して取り込み直すと（D7）、取り込み直した精算は保存の後の取込みとして日付で判定され、精算日が計数の日なら、その精算に行のある商品は要再確認になる（入れ直すと解ける。2026-10-23、owner の決定〈repo 外の回答台帳 TD-400〉）。完了の時点の精算の n の精算を完了の後に取り消して取り込み直したときも同じく、取り込み直した精算は精算日が完了日より前でなければ完了の後の比較の範囲に入らず、記録の詳細の参考の差に出ることがある（評価額は変わらない）。
- 難しくなること: 在庫を動かす全ての writer が日付を渡し、求め直しの関数を呼ぶ。精算の一覧が変わる TX は計数を持つ全ての商品を求め直す（棚卸しの期間は数千点。1 商品の求め直しは合成データで 0.01 ms 未満。店の PC の値は runtime の lane が測る）。test の fixture の多くが `stock_quantity` を直に入れているので、商品を作る test helper を「初期在庫の記録を作る」形へ直す（runtime の lane）。
- 意味の変わる所: 計数がある商品では、日付を計数より前にした手入力（例: 入庫の日付を計数より前にした）が在庫に足されない（数えた数に入っているとみなす）。`stock_after` は保存した時点の写しの値。
