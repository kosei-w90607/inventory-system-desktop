## 視覚設計と利用者心理の出典

**① refactoring-ui** (Steve Schoger & Adam Wathan) — **視覚設計**
- 採用: §1 ヒエラルキー原則 / §2 タイポグラフィ階層 / §3 スペーシングシステム / §4 カラー理論（subtle saturation）
- 取り入れ方: 全ての視覚決定（カラー・タイポ・スペース・アイコン）の一次根拠
- 制約: 書籍由来で一般論に寄る場面あり。業務アプリ固有の深さは他の出典で補う

**② ux-principles** (Nielsen基盤) — **利用者心理 + A11y**
- 採用: Nielsen 10 ヒューリスティクス全て、WCAG 2.1 AA 準拠
- 特に強調: #1 System status visibility（処理中は必ずプログレス表示）、#5 Error prevention（確定ダイアログ）、#9 Help users recognize errors（エラーメッセージは「原因 + 解決策」）
- 制約: 一般原則なので、本プロジェクトの「手芸店1人運用」に最適化された追加原則は他の出典で補う

**③ GOV.UK Design Principles** — **作らない勇気**
- 採用: *Start with user needs* / ***Do less*** / *Make things open*
- 取り入れ方: 機能肥大化の歯止め。「あったら便利」ではなく「なければ業務が止まる」で判断
- 典型適用: ダッシュボードのウィジェット数、設定画面のオプション数、レポートのフィルタ組合せ
- 制約: 公共機関発想のため「コミュニティ駆動」等は本プロジェクトに不要

**④ IBM Carbon Foundations** — **A11y基盤 + 密集情報**
- 採用: A11yをインフラ化（装飾でなく基盤） / Progressive disclosure（段階的開示）/ データテーブル設計パターン
- 取り入れ方: 在庫少一覧・変動履歴・日次売上明細の「大量行 + 複数列 + A11y」の設計パターン
- 制約: エンタープライズ向けの密度は本プロジェクトには強すぎる場面あり。密集させるのは業務データのみ、ナビやヘッダーは余白を取る

**Laws of UX（日本語版『UXデザインの法則』第 2 版、2025-01）** — **見る人の受け取り方**
- 採用: 00 の色の役割・強調の段階・ラベルと値の「受け取り方」「狙う効果」「根拠」の列と、DSR-19 / 20 / 21 / 22 の Why が引く法則
- 取り入れ方: 規則を「見せ方 → 受け取り方 → 狙う効果 → 根拠」の順で書くときの根拠。法則名と、規則にどう落としたかを併記する
- 制約: 理論書の主張をそのまま規則として転記しない。狙った受け取り方になったかは実機の L3 で確かめる（04 原則 11）

## 業務語彙・装飾の強さ・Windows らしさの出典

**⑤ Shopify Polaris** — 業務ドメインの語彙設計
- 採用: *情報アーキテクチャを基盤に置く* / リソースページ + アクションページのパターン
- 取り入れ方: 「商品」「在庫」「入庫」「売上」の語彙を画面・ボタン・通知で統一。シノニム（「アイテム」「ストック」等）を使わない
- 不採用: マルチ通貨・多言語・グローバル対応（1店舗JSTローカルのため）

**⑥ Atlassian Design System** — 装飾強度の文脈依存
- 採用: *Foundational / Harmonious / Bold-Optimistic-Practical with a wink* のうち、**業務画面では Practical 強め・Bold 抑制**
- 取り入れ方: マーケ文脈（ヒーロー・ランディング）なら華やか、業務画面なら地味、の使い分け。本プロジェクトは全画面業務なので全体的に落ち着いた表現
- 不採用: 大規模チームコラボ機能（個人1人運用）

**⑦ Microsoft Fluent 2** — Windowsらしさ（Tauri+WebView2親和性）
- 採用: *Effortless / Coherent / Relevant* の3語をプロジェクト憲法化
  - *Effortless*: キーボードショートカット、コンテキストメニュー等の Windows 慣習を踏襲
  - *Coherent*: 画面間で視覚階層と配置が一貫、どの画面でも同じ場所に戻るボタン
  - *Relevant*: 予測通り動く、驚きを与えない
- 不採用: Signature experiences（Mica / Acrylic 等の装飾マテリアル）— 業務集中の邪魔 + WebView2 での再現コスト大

## 観点借用: japanese-webdesign（Anshin 哲学）

**明記**: `ronantakizawa/japanese-webdesign` (Claude Skill、現時点DL 111) の **Anshin哲学**（*情報密度＝信頼*）を**観点として借用**する。Skill そのものはインストールしておらず、「原則の視点」だけ取り入れる形。

**Anshin哲学の要旨**:
> 日本のビジネスUIでは、欧米的な「空白 = 洗練」よりも「情報密度 = 誠実・信頼・網羅」が利用者の安心感を生む。POS帳票、役所フォーム、鉄道時刻表等に根付いた期待値。

**取り入れ方**:
- **在庫一覧・売上明細等の業務データ表示で、refactoring-ui の「余白原則」と衝突する場面の判断基準**にする
- 具体例: 売上明細テーブルで「JAN / 商品名 / 部門 / 単価 / 数量 / 小計 / 記録元 / 時刻」の8列を一度に見せる判断。欧米的には列減らし推奨だが、日本の店主は「一度に把握したい」期待値が強い
- 適用境界: **業務データ**は密度高め、**ナビゲーション・ヘッダー・通知**は refactoring-ui の余白原則を守る

**将来の正式採用への道**: DL数と第三者評価が成熟したら、Skill 本体のインストール + プロジェクト設定への組込みを検討。再検討トリガーは `docs/UI_TECH_STACK.md` §7.3 に記載。

## 観点借用: NN/g Common Region + GOV.UK Summary List（同型情報の比較可能性）

**明記**: Nielsen Norman Group の *Common Region*（近接した要素を共有の境界で囲むと 1 グループとして知覚される強いグループ化原理。ただし境界の多用は clutter を生み、かえって比較を妨げる）と、GOV.UK Design System の *Summary list* パターン（少量の関連する key-value は per-card の反復でなく、列を揃えた定義リストで示し同型レコードの比較を容易にする）を**観点として借用**する。DSR-16（同型情報のグループ化と囲みの階層）の判断根拠に用いる: 囲みは比較目的の反復に使うと逆効果になり、単一レコードの key/value 確認にのみ適切という整理（2026-08-29 owner L3-lite 可読性 FAIL の是正で採用）。

## owner の受け取り方（L3 の原文から）

**出典**: owner の L3 の原文 [2026-09-04-owner-l3-feedback-raw.md](reference/2026-09-04-owner-l3-feedback-raw.md)（下の「」は原文の節の名）と、それを受けた decision-log の D-091・D-094。デザインの判断の一次の出典の 1 つとして、owner が画面をどう受け取ったかを要約で置く。原則と規則にはしない（原則は 04、規則は 01）。各項に、読んで当たる 04 の原則・DSR を添える。

- **壊さない優先**: 今の導線は良くできていて壊す必要を感じない、と受け取る（「run 3 原文」の Backup）。一方で、今の形が目に馴染んだだけかもしれないと慣れも自覚している（同、日次売上の日付の送り）。新しい案は実機で今の形と並べて見せる（D-091 の Alternatives の「壊さない優先」、04 原則 11）。
- **共通化は道具**: 何でも共通にして統一感を出しても、見やすくなるとは限らない（「run 3 原文」の日次売上）。画面の構造はその画面の意味を優先し、文言・囲み・色の token は揃える（「直回答」の A・D、「Lane 5 L3 所感」）。backlog の「移送照合で補足した経緯」の明示不採用「画面固有の意味を壊す共通化」も同じ向き。04 原則 6・7。
- **列見出しは要る所を選ぶ**: 価格履歴のような一覧には列見出しを付ける（「直回答」の A）が、日次・月次の集計や操作ログの開いた中身へ一覧用の列見出しを持ち込むのは過剰と受け取った（「run 3 原文」）。比較のための表は DSR-16 に従う。
- **飾りより情報**: データに無い field（操作ログの実行者）、出どころの分からない欄（入庫の伝票番号）、押せると誤解させる文言（「すぐ確認」）、説明の無い内部の名（`pos_stock_sync`）は採らない（「run 4」「run 3 原文」）。04 原則 5。
- **色は意味を運ぶときに使う**: 状態の badge と増減の数値は色が付いているほうが目が滑らない（「Lane 3 L3 run 2 原文」「Lane 3 L3 run 3 原文」）、前日比を出すなら増減の色が要る（「run 3 原文」）、返品・交換の方向の badge は成立しない（「直回答」の C）、badge の色付けはアプリの中で規則を作る（「Lane 5 L3 所感」）。読んで当たるのは 00 の色の役割表と 04 原則 2（1 色 1 役割）で、DSR-08（色だけで意味を伝えない）は色と一緒に文言・icon を置く側の規則。
- **線と塊は少なく、角は丸く**: 件数行と列見出しの塊は角が角ばって見栄えが悪く、やっても下に線を 1 本引くくらい（「run 4」）。角を丸くし上端の線を外して PASS（「run 5」〜「run 7」）。灰色の地の塊（summary の stone-100）を野暮ったいとする所感は backlog の「card の面色を白へ寄せる」の項目が持つ。04 原則 9。
- **説明文を歓迎する**: 画面が何をするかの説明（Home の入口）、集計の説明書き（月次の公式部門集計）、何件を出すか（「直近 10 件」）、ページの上の説明（商品一括インポート・PLU 書出し・バックアップ）を求める（「run 3 原文」、「直回答」の A、「⑧ PR #38 L3 結果 原文」）。04 原則 5。
- **配置の常識**: 金額は右端（「run 3 原文」の月次）、在庫少一覧は状態 → 在庫数 → 売価（同）、CSV 出力と印刷はページか囲みの右下（同、日次売上）、開始日・終了日は「期間」にまとめる（同、操作ログ）。
- **決まりは受け取り方から組む**: 規則を「どう見せるか」でなく「見る人がどう受け取り、何を狙うか」から組む（D-091。00 の各表の「受け取り方」「狙う効果」「根拠」の列、本書の Laws of UX の項）。
- **分からないときは分からないと言い、実機を見てから決める**: 何とも言えないものは決めずに残し（「直回答」の H、「run 3 原文」）、まず試して見てから決める（「Lane 4 L3 run 2 追記」「Lane 4 GA3 方向確認」、⑦ の緑の Alert の保留）。04 原則 11。
- **2026-09-24 の canvas での判断**: 操作と進行中は同じ色の仲間にそろえる（D-091 の Decision (1)。D-094 の token は操作 `--primary` #1d5c63、進行中 `--ongoing` #2f7f86）。新しい案は今のアプリの外枠の中で描く（棚卸し画面の案 D1。backlog の「棚卸し画面 D1 の実装」）。書体は Noto Sans JP が owner の好みで、採用は同梱と実機での読み分けで決める（00 の書体の節、backlog の「デザインの決まり runtime lane B（書体）」）。キオスク型の画面は採らず、業務端末型で部門分けとスキャンを上部に置く（repo に記録なし〈owner の canvas 2026-09-24、未照合〉）。
- **ランキング 1 位**: 1 位のバッジは良いと受け取った（「run 3 原文」の月次）。2026-09-24 に順位と太字だけで示す試しを了承したが、2026-09-28 の L3 で採らず、今は琥珀の pill と行の地（D-094 の「試し 8 点の採否」）。2 位・3 位の見せ方は backlog の「月次の商品別ランキングの 2 位・3 位の見せ方」。
