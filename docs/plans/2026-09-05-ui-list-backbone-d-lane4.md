### 識別列固定の実装方式：新規 scroll 容器を作らない（Contract Probe、round 1 の CSS 根拠を維持しつつ新方式を確定）

- **E12 当初案（新規 `overflow-x:auto` box + 識別列 sticky）は引き続き不採用**: CSS Overflow の仕様上、要素の `overflow-x` と `overflow-y` の一方が `visible` 以外（例: `auto`）のとき、`visible` のままのもう一方は `auto` へ computed される。したがって「表を新規の横 scroll 容器（`overflow-x: auto`）に包む」設計は、その要素を**縦方向にもスクロール可能な独立 scrolling ancestor**に変え、DSR-17 `:292` が `<main>` を唯一の scroll container と定める契約と衝突し、sticky thead の `top` 基準（`<main>` 相対）と両立しない。この結論は CSS 仕様から静的に導けるため、Playwright / headless Chromium での実行時 probe は不要（Contract Probe = 本節の記述そのもの、追加実験なし、N/A）
- **owner が採る新方式は「新規容器を作らない」**: `RootLayout.tsx:65` `<main data-scroll-restoration-id="main" className="min-h-0 min-w-0 overflow-auto">` は Tailwind `overflow-auto`（= `overflow: auto`、両軸）を既に持ち、`<main>` は**縦・横どちらの overflow でも既に scroll 可能**（実装確認済み、追加実験不要）。したがって table の内容幅が toolbar 幅を超えたとき、`ListShell.tsx:141` の wrapper が広がった分だけ `<main>` 自体が横スクロールする——これは E12 案のような「新規のローカル scroll 容器」ではなく、sticky thead が既に前提としている scrolling ancestor（`<main>`）と**同一**である
- CSS の `position: sticky` は `top`/`left`/`right`/`bottom` を独立に指定でき、1 要素が複数軸で sticky になることは仕様上問題ない。したがって識別列（`thead th`/`tbody td` の先頭 1・2 列目）に `sticky left-*` を追加しても、既存の `sticky top-*`（thead 全体）とは独立して共存する——`<main>` が縦に scroll すれば `top` 基準で、横に scroll すれば `left` 基準で、それぞれ独立に固定される
- 結論: 識別列 sticky そのものは Non-scope ではなくなった。Non-scope のまま残るのは「新規 scroll 容器を作る」実装方式（E12 当初案）のみ

#### GA4a: 箱内件数帯の横固定

**機序（round 1 是正、Opus P1: 当初案は no-op + regression と判明、下記「却下した代替案」参照）**: `position: sticky` は自身の containing block の内側でしか動けない。当初案（帯を box 直下・wrapper の外に置き `sticky left-0`/`top-0` を付ける）では、帯自身が `w-full` の block 要素として box の content box を containing block にするため、横方向の余地はゼロ（box 幅 = 帯幅、`left-0` は動く余地が無く no-op）——加えて縦方向も containing block の高さが box の `clientHeight`（可視高）になるため、`top-0` は「box の可視領域の先頭」までしか保持できず、box を 1 画面分 scroll した時点で帯が box の外（構造的に box の子である以上、box の scrollport を超えては留まれない）へ流れてしまう。これは現状 PASS している縦方向の張り付き（AC-L3-1「見出しが箱の上に残る」）の**regression**になる。識別列（`sticky left-*`）が機能するのは、その containing block が `<td>`/`<th>`（table row、box より横に広い）であり、box の可視幅を超えて左右に動ける余地があるためで、帯にはこの余地が無い。

**Design（Coordinator 決定、round 1 是正）**: 帯を box の**外**（`ListShell` root の直下、box の直前の兄弟）へ完全に移す。box の scrolling ancestor 自体から外れるため、帯は縦横どちらの scroll にも一切追従せず、構造的に固定される（新しい CSS 機構は導入しない、ponytail: `sticky`/`overflow` の依存を無くすほうが `left-0`/`top-0` の当てはめより単純）。
- root（`cn("space-y-3", ...)`）の子を `toolbar frame` → `帯`（`stickyHeader && showTopSummary && pagination` のときのみ） → `box` → `Pagination` の順に並べる。帯自身の class は現行の `sticky top-0 z-20 flex h-10 w-full items-center overflow-hidden bg-background px-2 [&>div]:min-w-0 [&>div]:truncate` から `sticky`/`top-0`/`left-0` を含む scroll 追従系の class を全部外し、`z-20 flex h-10 w-full items-center overflow-hidden bg-background px-2 [&>div]:min-w-0 [&>div]:truncate` へ縮める（box の外に出た時点で「sticky で box 基準に留める」必要自体が消える——box に追従させたいのではなく、そもそも box の scroll と無関係な場所に置くのが解、ponytail: 要らない子は消す）。`z-20` は帯が視覚的に thead より前面に来る既存の意図を維持するための保険として残す（thead 自体は帯の外に出るため重なりは実質発生しないが、削除して regression を作るより残すほうが安全）。
- box の class（root の 3 番目の子、`:201`）に `mt-0` を追加する。root の `space-y-3` は `> * + *` に `margin-top: 0.75rem` を課すため、帯を新しい直前の兄弟にすると帯と box の間にも同じ 0.75rem の隙間が入ってしまう——帯と box は「1 つの一覧ブロック」として隙間なく連続させたいため、box にだけ `mt-0` を足して打ち消す（Tailwind の `space-y-*` は `:where()` でゼロ specificity のため、通常の utility class 1 つで確実に上書きできる、ponytail: 新規 wrapper 要素を足さず既存 utility の組合せで済ませる）。`mt-0` は帯が描画されるとき（`stickyHeader && showTopSummary && pagination`）だけ box に付け、帯が無い場合（`stickyHeader` のみ、または `topSummary` 無し）は付けない——帯が無ければ toolbar–box 間の通常の 0.75rem gap を維持する必要があるため。
- box 内部からは帯が消えるため、box が唯一の内容（`w-min min-w-full` wrapper + table）に戻る——GA1 以前の構造に近い形へ実質的に単純化される。wrapper（`w-min min-w-full`）自体・識別列・`STICKY_TABLE_CLASSES` は無変更。
- **`[&_thead_th]:top-10` → `top-0` に統一する（`:183` の三項演算子を撤去）**: この offset は「box 内に帯（`h-10`）があるぶん thead を 2.5rem 分下にずらす」ためのものだった。帯が box の外に出た今、box の内側にはもう帯が無い（`topSummary` の有無に関わらず）ため、thead の sticky offset は常に `top-0` でよい。`showTopSummary ? "top-10" : "top-0"` の三項演算子ごと `"top-0"` の固定値へ置き換える。

## Residual Risk

- **（解消済み）⑧ 未 merge のまま実装した場合の既知残件**: round 2 是正時点で記録した懸念——S4b が `PriceRevisionFilters.tsx` の取引先 native `<select>` に依存する前に ⑧ が merge されない場合の残件——は、2026-09-06 に lane ⑧（tip `885c10d`、human-confirm）への単段 merge（merge commit、下記 Stacked train 参照）を完了し、取引先が shadcn `Select`（id `price-revision-supplier`）に置換済みであることを実読で確認したため解消した。以降の Writer 実装は native `<select>` を意識しなくてよい
- **固定列の行 hover/選択背景が追随しない（識別列固定、owner 決定 2026-09-05 第 2 便）**: `tbody td` の識別列（1・2 列目）は不透明化のため `bg-background` 固定にする（S9）。行 hover（`TableRow` の `hover:bg-muted/50`）・選択行（`data-[state=selected]:bg-muted`）・将来の現在行背景（`--row-current`）は、これらの class が `TableRow`/`TableCell` に付き `ListShell` の descendant variant より詳細度が低いため、固定列の 2 セルだけ hover/選択の色が乗らない見た目になる。動的な背景注入は `children`（`ProductTable`）へ prop を渡す必要があり、`ListShell` の「children に className を渡さない」既存方針（D-9）と衝突するため本 lane では対応しない。owner L3 で許容可否を確認し、気になる場合は後続 lane で `TableRow`/`TableCell` 側からの背景伝播を設計する。**代替案（L4-D11、round 3 追加、Opus P2）**: `[&_tbody_tr]:bg-background` を root に追加し（`[&_thead_tr]:bg-list-head`、`ListShell.tsx:53` と同型のパターン）、識別列 `td` は `bg-inherit` にする——`tr` の背景が hover/選択/現在行で変わればそれを識別列も継承する。caveat: `hover:bg-muted/50` のような半透明色を `tr` にそのまま使うと、識別列とその他列で背景の合成層数が異なり二重合成の見え方になり得る。owner が L3 で許容可否を判断し、必要なら後続 lane でこの代替案を採用する
- **toolbar が横 scroll で左へ流れる（識別列のみ固定、round 3 是正、Opus P1）**: `ListShell.tsx:130` の toolbar frame に `sticky left-0` を追加しても、containing block chain がいずれも `<main>` 幅を超えないため sticky range が 0 になり no-op（Scope S9 参照）。したがって商品一覧の窓を狭めたとき、識別列（商品コード・商品名）は固定されるが toolbar/filter 枠は他の非固定コンテンツと同様に左へ流れる。**owner L3 で気になる場合の後続案**: toolbar を `w-min` wrapper 内に置き、`<main>` を `container-type: inline-size` にして toolbar に `w-[100cqw]` + `sticky left-0` を与える（container query 基準の幅を `<main>` の可視幅に固定し、そこに対して sticky left を効かせる）——これは新たな CSS container query の導入を伴う design 判断であり、本 lane では扱わない（別 lane 候補）

## 実装原則（ponytail、full）

書く前に順に問う: (1) そもそも要るか（推測需要は書かず 1 行で理由）(2) この codebase に既に helper / util / pattern があるか（再実装しない）(3) 標準ライブラリで済むか (4) platform の素の機能で済むか（`<input type="date">`、CSS、DB 制約）(5) 導入済み依存で済むか（数行のために新規依存を足さない）(6) 1 行で済むか (7) それでも要るなら動く最小 code。
規則: 実装 1 つの interface / 製品 1 つの factory / 変わらない値の config を作らない。将来用の scaffold を作らない。追加より削除、賢さより退屈さ。file 数は最少、動く最短 diff（ただし問題を理解してから。正しい場所の小さな変更 > 間違った場所の最小変更）。同サイズの選択肢は edge case に正しい方。意図的に角を落とした箇所（上限のある近似・O(n²)・global lock 等）は `ponytail:` comment を残す。
例外: 正しさ・データ安全・既存 test の契約・packet の AC を削る方向には使わない。

本 lane での適用例: S2 は `Pagination.tsx` 1 箇所の修正で 8 画面全 caller に反映する（画面ごとに個別ロジックを複製しない）。S4 は起票時実測で既に条件を満たす 5 画面には触れず、満たさない 2 画面のみを直す（満たしている契約への冗長な書き換えをしない）。S9（識別列固定）は既存の予約 prop `identityColumns` をそのまま使い、値は DSR-22 mapping 表が要求する 1・2 のみに対応するリテラル class 配列で足りるため、任意 N 列の generator は作らない（YAGNI）。配線も症状のある商品一覧 1 画面に限定し、症状のない 7 画面への投機的な配線をしない。
