## Goal

Goal Invariant:

### 最小完了条件

- 新方式の棚卸し（開始 → 商品ごとの「今から数える」→ 保存 → 確定）と、確定済みの商品の独立再実測が、試験 DB の上で ADR D1・D7・D8 どおりに動くことを自動 test が示す。特に STK-1 の 4 つの操作列（保存の後の入庫 3・手動販売 2・廃棄 1・返品 1）が確定で 13 / 8 / 9 / 11 になり、計数を始めた後に受領した資料の要再確認は数え直しでだけ解消する。
- 通常の起動・画面・command の振舞いは ① の停止のまま変わらない。

### 失敗定義

- 保存の後の入出庫を確定が打ち消す（確定が保存済みの N で在庫を上書きする）、または保存の前に動いた在庫で保存を通す（版の検査が効かない）。
- 保存の時点で `source_cursor` を取り直す、計数を始めた後に受領した資料の flag を保存で消す（ADR D2・D4）。
- 未解消の flag か legacy の明細がある商品の確定を force_fill で通す。
- 拒否・失敗のときに数量・flag・版・movement が一部だけ書かれる。同じ要求の再送で補正を二重に行う。
- 新しい関数・型が production から呼べる（D-109 (3)）。既存 test を削除・skip・弱体化する。

### 非目的

- 棚卸しを店で再開すること（⑤。④ が TD-190 で Square か CASIO かの判断を待つので、③ の完了で停止は解けない）。
- 取込みの受領・判定・flag の作成、取消の補償と legacy の取消の保留、準備照会、在庫連動の有効化の拒否（④）。
- command・bindings・画面・CMD の token の保管と DB 世代の採番（⑤）。

Priority: `Goal Invariant > Acceptance Criteria > supporting evidence`。AC や証跡作業が Goal Invariant を前進させない場合は、Goal を置き換えず簡略化・defer・削除する。

save の順序（35 proposed の 3〜8、SPEC-STK-TIME-D1-R1）:

1. `count_token` を request ID として明細と recount から照会する。見つかれば、同じ N は書込み 0 で `Replayed`（保存済みの L・N・差、`stock_after` は明細なら照会時の在庫・recount なら保存した N）、違う N は `BizError::IdempotencyConflict`、両方に見つかれば `BizError::DatabaseError`（書込みなし）。
2. 見つからず `context` が None、`context.count_token != count_token`（CMD が別の要求の context を渡した誤り）、または `context.db_generation != db_generation` なら count_context_invalid（「最新の記録を確認してください」）。保存先の明細は `context.stocktake_item_id` だけで決め、引数に明細 ID を持たない（引数と食い違う所を作らない）。
3. N が負、または JavaScript の安全な整数（`9_007_199_254_740_991`）を超えれば `ValidationFailed`。
4. 業務 TX を開き、`context.stocktake_item_id` の明細・親の状態・同じ商品の active 明細を読み直す。明細の `stocktake_id`・`product_code` が context の値と違う、または用途と合わなければ count_target_changed。進行中の明細が measured で、request ID が `count_token` と違い、`observation_revision` が `context.stock_revision` より大きければ（この begin の後に別の要求で保存し直された古い要求、ADR D8 `:294`）count_context_invalid（「最新の記録を確認してください」）。begin より前の保存を数え直す新しい token の保存（`observation_revision` が `context.stock_revision` 以下）はこの条件に当たらず、通常の保存になる（Gated Amendment 1、2026-10-08）。商品の `stock_revision` が `context` の値と違えば count_context_invalid（「数えている間に記録が変わりました。もう一度数えてください」）。どちらも書込み 0。
5. L = 現在の在庫、ledger_cursor = その商品の movement の最大 ID（補正の INSERT より前）。
6. 進行中の明細: その商品の flag のうち `source_id <= context.source_cursor` を消し、`bump_stock_revision` の増分後の値を observation_revision として、明細を measured・N・L・S（begin の時刻）・E・両 cursor（source_cursor は begin の値のまま）・版・request ID（= token）で 1 文の UPDATE（親が進行中を条件、0 行なら count_target_changed）。在庫は変えない。
7. 独立再実測: 補正 = N − L（checked、補正後の在庫 = N が安全な整数の範囲）。補正が 0 でなければ `update_stock_quantity_with_revision(N)`。flag を 6 と同じ条件で消し、`bump_stock_revision` の値を observation_revision として recount を INSERT し、補正が 0 でなければ movement（`movement_type=stocktake`、`stocktake_adjustment_kind=recount`、`stocktake_recount_id`、`reference_type=stocktake`・`reference_id` = 参照明細の header）を INSERT する。差 0 でも recount の行は残す。確定済みの header・明細・評価額は変えない。
8. commit し、`Saved` と L・N・差（L − N）・`stock_after` を返す。途中の失敗は TX ごと戻す。

確定の順序（35 proposed「確定・legacyの取消の保留」、SPEC-STK-TIME-D1-R1）:

1. 業務 TX で header を読み、無ければ `NotFound`、完了済みなら `StocktakeNotInProgress`。
2. 確定対象の棚卸しに明細がある商品に未解消の flag があるか、確定対象の棚卸しに kind=legacy の明細があれば、force_fill によらず recount_required（対象の明細ごとの target、書込み 0）。同じ商品の完了済みの棚卸しの legacy の明細は数えない（`seed_legacy_fixture` の LG-MEAS は header 1 と 2 の両方に legacy を持つ）。旧 active（版 0）の legacy・uncounted の明細を save で measured にし直すと、L はその保存 TX の帳簿になる（SPEC-STK-TIME-D8-L1、明細を作った時の L を使わない）ので、4 の補正 N − L は保存の後の移動だけを残す。
3. uncounted が残り force_fill が false なら `ValidationFailed`（旧本体 §20.5 の文言）。
4. 明細ごと: measured は補正 = N − L、補正後の在庫 = 確定直前の在庫 + 補正（checked、安全な整数の範囲）。補正が 0 でなければ `update_stock_quantity_with_revision` と movement（`stocktake_adjustment_kind=completion`、`reference_id` = header）。uncounted（force_fill）は auto_filled・N=L=`max(現在の在庫, 0)`・counted_at NULL にし、負の在庫を 0 へ書き換えない。補正が 0 の商品も `bump_stock_revision` で版を進める（古い context を失効させる）。評価原価 = 確定時の `products.cost_price` を、既存の `stocktake_repo::update_stocktake_item_valuation(conn: &DbConnection, item_id: i64, valuation_cost_price: i64) -> Result<(), DbError>`（`stocktake_repo.rs:284`、旧本体 §20.5 の 5d と同じ関数、signature を変えずに呼ぶ）で全明細（measured・開始時と force_fill の auto_filled）の `valuation_cost_price` へ固定保存し（tracking §16-17 の valuation_cost_price の設計意図）、評価数量 = `max(補正後の在庫, 0)` と合わせて §20.5a の関数で求める。
5. header を completed・total_cost・completed_at・`reconciliation_version=1` にする（旧 header〈0〉も、2 を通れば同じ TX で 1 にする）。commit。2〜5 のどこで失敗しても TX ごと戻し、商品ごとに commit しない（Matrix C20）。
