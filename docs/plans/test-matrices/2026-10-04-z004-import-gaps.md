## Contracts Under Test

- SPEC-Z4A-D7: 個数・金額は `-?[0-9]+` と `-?[1-9][0-9]{0,2}(,[0-9]{3})+` だけを受理し、カンマを除いて i32 にする。カンマなしの値も式で判定する（`+5` を拒む）。それ以外は `InvalidNumber`。
- SPEC-Z4A-D8: 個数・金額を先に読み、売上の有無で行を分ける。コード全桁 0 で売上あり → `InvalidJan`（「商品コードの無い枠（メモリNo.{record_no}）に売上があります。…」）。コード全桁 0 か 13 桁 JAN にならず 0/0 → `Ok(None)`。13 桁 JAN → 0/0 でも `Ok(Some)`。
- SPEC-Z4A-D5（改訂）: 8 桁独自コード + `EEEEEE` は売上のある行だけ `InvalidJan`。
- SPEC-Z4A-D6（改訂）: 全スロットダンプを受理し、売上の無い枠だけ skip。
- SPEC-Z4A-D4（不変）: `total_data_lines` はヘッダ後の非空行の試行数（Ok(Some) / Ok(None) / Err すべて）。
- 32 §15.3 4a / 4b / 4c / 4d（不変の経路）: 正常 JAN の 0/0 は BIZ で除外、parse_errors は `invalid_jan` 等の ErrorRow に写像し raw 値は分割後の文字列（取得できなかった field は `""`）、4b の `unmatched_product` の raw 値は整数の文字列表現。
- 32 §15.2 ErrorSummary・§15.3 手順 5c（改訂）: `error_summary.count` は全件。`items` は最大 100 件で、`invalid_jan` の行を line_no の昇順で先に選び、残りの枠を他の行から line_no の昇順で埋め、選んだ items を line_no の昇順で並べる。
- 32 §15.4 手順 8（不変）: error_rows が空でなければ `completed_partial`。
- SPEC-PLS-D2（不変）: `parse_plu_register_snapshot` は本変更の影響を受けない。

## Failure Modes

- F1 カンマ付きの金額（`1,234`）が `InvalidNumber` のまま残り、1,000 円以上の PLU の売上が在庫に反映されない。
- F2 カンマの除去が緩く、`1,23`・`12,3456`・`1,,234`・`,123`・`1,234,`・`0,123` を数として読む（区切りの崩れを黙って別の数にする）。カンマなしの値を `parse` だけで読み、`+5` を受ける。
- F3 負の値のカンマ付き（`-12,345`）を受理しない、または符号を落とす。
- F4 コード全桁 0 で個数か金額が 0 でない行が従来どおり読み飛ばされる（clear 行の売上が黙って消える）。個数だけ・金額だけが 0 でない片側の場合を取りこぼす。
- F5 clear 行のエラーが `InvalidJan` 以外の種別になる、文言に「商品コードの無い枠」とメモリNo. が無い、raw_quantity / raw_amount が元の文字列でない。
- F6 8 桁独自コード + `EEEEEE` の 0/0 の枠が従来どおり毎回 `InvalidJan` になり、取込みが毎回 completed_partial になる。
- F7 売上の無い枠の skip を広げすぎ、13 桁 JAN の 0/0 の行まで IO で捨てる（ADR D4 の相殺の判定の入力が消える）。
- F8 8 桁独自コードで売上のある行まで skip する（SPEC-Z4A-D5 の可視化を失う）。
- F9 数値を先に読むようにした結果、`total_data_lines` の数え方が変わる、または全桁 0 の 0/0 の枠が `InvalidNumber` になる（実データの空スロットは `"0"`。Contract Probe P3）。
- F10 BIZ-03 が clear 行の ParseError を ErrorRow にしない、`normalized_jan` に値を入れる、または error_rows に入らず status が `completed` のまま。
- F11 `ParseErrorType` / `CsvImportErrorType` / `csv_import_errors` の CHECK / bindings を変えてしまう（wire の互換を壊す）。
- F12 新しい test に REQ-401 / SPEC ID が無く、traceability が T4 / T1 で落ちる。
- F13 プレビューの `items` が error_rows の先頭 100 件のままで、4b の未登録 JAN の行が 100 件を超えると clear 行の `invalid_jan` が items から落ち、commit の停止中は知らせ先が無くなる。選んだ後に line_no の昇順へ並べ直さない。
- F14 売上のある非 JAN の行（8 桁 + `EEEEEE` 等）の文言を全桁 0 の分岐と 1 つにまとめ、clear 行の文言（「商品コードの無い枠」）を出す。

## Negative Paths

- 区切りの崩れたカンマ、小数、空の値 → `InvalidNumber`（F2、AC1）。
- コードが全桁 0 で個数か金額のどちらかだけが 0 でない → `InvalidJan`（F4、AC2）。
- コードが全桁 0 で、個数・金額のどちらかが数でない → `InvalidNumber`（数値を先に読むため。実データの空スロットは `"0"` で到達しない。Contract Probe P3）。`test_parse_z004_req401_malformed_comma_invalid_number` の全桁 0 の 2 行（(`1.5`, `500`) と (`0`, `1,23`)）が持つ。
- ファイル内の売上が商品コードの無い枠だけで、正常 JAN の行が 1 行も無い → parsed_rows が空・parse_errors が非空で、既存どおり「有効なデータがありません」の致命的エラー（32 §15.3 手順 2）。実データの layout A は 13 桁 JAN の枠を毎回持つため到達しにくい。新しい test は足さない（既存の分岐、`test_parse_and_validate_req401_no_valid_data` の隣の契約）。

## Boundary Checks

- i32 の範囲: `2,147,483,647` は受理、`2,147,483,648` は `InvalidNumber`（`parse::<i32>` の範囲。AC1 の malformed の test に足してよい。必須ではない）。
- 3 桁区切りの先頭グループは 0 で始まらない 1〜3 桁（`1,234` 可、`1234,567` 不可、`0,123` 不可）。カンマなしの値に符号 `+` は付けない（`+5` 不可）。

## Compatibility Checks

- `ParseResult` / `ParsedRow` / `ParseError` の型、`ParseErrorType` の 3 値、`CsvImportErrorType` の 4 値、`csv_import_errors` の CHECK、`src/lib/bindings.ts` を変えない（AC7）。
- 既存の IO / BIZ の test を弱めずに全 PASS（AC6）。

## Data Safety Checks

- fixture は合成のコード（`9999999999990E`・`12345678EEEEEE`・全桁 0 等）と合成の名前・値だけ。実データの金額・商品名・JAN・部門名・生の行を入れない。
- packet・Matrix・設計正本に持ち帰りデータの件数を書かない（形の存在だけ）。

## Main Wiring / Integration Checks

- `parse_and_validate`（BIZ-03）→ `parse_z004`（IO-02）の実経路を BIZ の test で通す（mock なし）。CMD・画面は変えないため、既存の CMD / 画面の test が通ることで足りる。

## Residual Test Gaps

- 実データの Z004 での end-to-end（カンマ付きの金額・clear 行・8 桁の枠を含む実ファイル）は、実データを repo に入れないため自動 test にしない。packet の L3 / 非対象の列のとおり、owner の実機の確認も本 lane では求めない（画面の code を変えず、停止 ADR で commit に到達しないため）。停止の解除（㉘ ⑤）の受入れで実ファイルを通す。
- 数量欄のカンマは実データで観測されていない（Contract Probe P2）。受理の test は合成の値だけで行う。
