## Risk

Risk: R3

Reason:
`docs/DEV_WORKFLOW.md` Risk Tiers の R3 の行の「operator workflow」（管理者が MSI を入れる・更新する流れ。手順書の流れ 1・2・4）に当たり、同節の R2 と R3 の迷いの規則（「data safety boundary」「config」に触れるなら R3）にも当たる: `identifier` はデータの folder・WebView の保存の folder・二重起動の防ぎ（下の Contract Probe の P3・P6）の鍵で、upgrade code は新しい MSI が前の版を置き換えるか別のアプリとして並ぶかを決める。設定の変更は `src-tauri/tauri.conf.json`（`docs/DEV_WORKFLOW.md` Plan Packet Rules の「config, manifest」→ 下の Boundary / Wire Contract）。

R4 でない理由: 推奨の J2 = A（`identifier` を据え置く）ではデータの folder が変わらず、DB・backup・設定を動かさない。店の PC にはまだ入れていない（関門 4 は初回の導入の前の関門）ので店のデータは無く、開発・試験 DB はリリースの前まで作り直してよい（D-123）。J2 = B を選んでも、移すのは開発・L3 の folder で、消さずに移す（22 §16 の作り直しの手順）ので R3 のまま、Data Safety に行を足す。

この lane で防ぐ危険（upgrade code を固定しないまま製品名を変えたときの経路）:

- 今の upgrade code は `productName` から作られる（P1）。初回の導入の後に製品名を変えると、次の MSI の upgrade code が変わり、Windows は前の版を置き換えずに別のアプリとして並べて入れる（Tauri の config の reference の `upgradeCode` の説明「must stay the same across all of your updates, otherwise, Windows will treat your update as a different app」）。2 つのアプリは `identifier` が同じなので同じデータの folder の同じ DB を開く（P3）。新しい版の migration が DB を上げた後に古い方を起動すると MNT-03-D11 で止まり、古い方の起動は店主には壊れたように見える。どちらを外すか・どちらのショートカットを使うかの判断を店に押しつける（D-127）。
- 開発用の Windows に雛形の名の MSI が入っていると（予行演習の前に試した場合）、名前を変えた MSI は同じ形で並ぶ。この lane は名前を変える前の upgrade code を固定するので、雛形の名の MSI も置き換える。
- `bundle.targets` が `all` のままだと NSIS の setup.exe もでき、NSIS は既定で利用者ごとに `%LOCALAPPDATA%` へ入る（Tauri の Windows Installer の資料、P5）。誤って setup.exe を配ると MSI の版と別の場所に 2 つ目が入り、同じデータの folder を開く。

この変更でどれかの required gate の green / red が変わるか: 変わらない。classifier の workflow の一覧（`scripts/ci/classify-changes.sh` の `.github/workflows/*|…|scripts/pr-gate.py|…` と `AGENTS.md|CLAUDE.md|docs/DEV_WORKFLOW.md|…|docs/templates/*|…` の 2 つの case）に当たる file を Scope に持たない（Scope は `src-tauri/tauri.conf.json`・`src-tauri/tests/` の新しい test・`docs/` の 2 file と本 packet・Matrix）。`src-tauri/*` で rust・generated・traceability の既存の job が走るだけで、gate の構成と required の名前を変えない。Final Review Minimum 1。

## Goal

Goal Invariant:

### 最小完了条件

- 店の PC のスタートメニューと「設定 → アプリ」に、owner が決めた製品名で 1 つだけ出る MSI を、開発用の Windows で作れる。
- 版を上げた MSI と、製品名を変えて版を上げた MSI が、どちらも前の版を置き換え（「設定 → アプリ」に 1 つだけ）、データの folder の DB とその中身が残る（L3、手順書の M4）。
- `identifier` が J2 の答えの値で、手順書・設計正本の書くデータの folder と一致する。
- build で MSI だけができる（J3 = A のとき）。
- 決めた 4 値（製品名・upgrade code・`identifier`・`bundle.targets`）と理由が decision-log（D-132）と手順書にあり、値を変えると test が赤になる。

### 失敗定義

- 製品名を変えた MSI が前の版と並んで入る（upgrade code の固定が効かない）。版を上げた MSI の後にデータの folder の DB が空になる・中身が変わる。
- `identifier` が変わり、開発・L3 のデータの folder を見失う（J2 = A のとき）。J2 = B で、手順書・設計正本に古い folder の名が live で残る。
- 日本語の製品名で MSI が作れない・文字化けした名がスタートメニューに出る（J1 = A のとき。P4）。
- 店の名が公開 repo に入る。

### 非目的

- Cargo の package 名・lib 名・`package.json` の `name`・`mainBinaryName`（実行 file の名。スタートメニューと「設定 → アプリ」には出ない）。
- 署名・WebView2 の入れ方・`allowDowngrades`・版の付け方の規則（手順書の「初回の導入の前に決めること」の版の段のまま）。
- 店の PC の M9（WebView2 の有無。店で確かめる。関門 4 に残る）。
- 自動更新の仕組み（updater）。
- 予行演習の結果で手順書の「未確認」を書き換えること（L3 の後に head を変えないため closeout で行う。下の Scope の「予行演習の扱い」）。

Priority: `Goal Invariant > Acceptance Criteria > supporting evidence`。AC や証跡作業が Goal Invariant を前進させない場合は、Goal を置き換えず簡略化・defer・削除する。

## Boundary / Wire Contract

- producer: `src-tauri/tauri.conf.json`（`productName`・`identifier`・`app.windows[0].title`・`bundle.targets`・`bundle.windows.wix.upgradeCode`・`bundle.windows.wix.language`）。L3 の版 B・名前を変えた版だけ、build の時の `--config`（repo の外の JSON の file）で `version`・`productName` を上書きする。
- consumer: `tauri::generate_context!`（窓の題、`identifier` → `app_data_dir`・WebView の保存の folder）、tauri-plugin-single-instance（`identifier` → 二重起動の防ぎの名）、tauri-bundler の WiX（製品名 → MSI の file の名・入る folder・スタートメニュー、upgrade code）、Windows Installer（upgrade code が同じなら前の版を置き換える）。
- wire type: JSON の文字列（upgrade code は GUID の文字列、`bundle.targets` は文字列か配列）。
- internal type: Tauri の `Config`（tauri-cli 2.11.1 の `config.schema.json`）。
- precision/range: `productName` は `^[^/\\:*?"<>|]+$`（P8）。`identifier` は英数字・`-`・`.` だけ。
- round-trip path: 設定 → build → MSI → 入れる → スタートメニュー・「設定 → アプリ」・`%APPDATA%\{identifier}`。
- invalid input: schema に合わない値は build が拒む。upgrade code を変える変更は AC5 の test が拒む。
- compatibility: `identifier` を据え置けば（J2 = A）既存の開発・L3 のデータの folder と WebView の保存をそのまま使う。upgrade code は名前を変える前の既定の値なので、固定の前に作った雛形の名の MSI も置き換える。NSIS は作らなくなる（J3 = A）。
