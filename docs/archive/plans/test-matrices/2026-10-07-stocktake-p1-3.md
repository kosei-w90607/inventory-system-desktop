## Risk

Risk: R3

## Contracts Under Test

- SPEC-STK-TIME-D8-K1: `stocktake_items` の kind と証拠の組を table の CHECK が固定し、旧明細の分類はそれを満たす。
- SPEC-STK-TIME-D8 / 35 proposed「新方式の開始と明細のkind」: 新方式の start は header を版 1、明細を uncounted / auto_filled で作る。
- SPEC-STK-TIME-D1: begin は DB を書かずに context（版・資料の上限・DB 世代・開始時刻）を作る。保存は 1 商品 1 TX で、版・所有者・DB 世代を再検証し、不一致は書込み 0。`source_cursor` は begin の値のまま。observation_revision は保存 TX の最後の版。再送は request ID で照会して Replayed。
- SPEC-STK-TIME-D1-R1: begin・保存・確定の拒否の code と targets と message。
- SPEC-STK-TIME-D4: 保存で消す flag は `source_id <= source_cursor` だけ。未解消の flag か legacy の明細がある確定は force_fill でも拒否。
- SPEC-STK-TIME-D7: 独立再実測は append-only、N − L を即時に区分 recount で補正、確定済みの header と評価額を変えない。
- SPEC-STK-TIME-D8 / SPEC-STK-VAL: 確定は確定直前の在庫へ N − L を加え（区分 completion）、force_fill は N=L=`max(在庫,0)`、評価数量は `max(補正後の在庫,0)`、全商品の版を進め、header を版 1 にする。
- D-109 (2)(3): 新しい関数・型・module は `#[cfg(test)]` の中にあり、通常の起動の DB を変えない。

## Failure Modes

- FM1 確定が保存済みの N で在庫を上書きし、保存の後の入出庫を打ち消す（STK-1）。
- FM2 begin と保存の間の在庫の移動を見逃して保存する（版の検査が無い・比較を誤る）。保存の後の移動で保存済みの実測を失効させる。
- FM3 保存の時点で `source_cursor` を取り直す。保存で `source_id > source_cursor` の flag を消す、flag を消さない。
- FM4 拒否・失敗で数量・flag・版・movement・recount の一部が残る。begin が DB を書く。
- FM5 同じ要求の再送で補正を二重に行う。値の違う再送を通す。上書きされた古い token で新しく保存する。
- FM6 未解消の flag・legacy の明細を force_fill で迂回して確定する。force_fill が負の在庫を 0 へ書き換える。差 0 の商品の版を進めない。
- FM7 独立再実測が確定済みの header・明細・評価額を変える、前の recount を上書きする、差 0 で行を残さない、active 明細のある商品で通る。
- FM8 評価額を N や負の在庫で計算する、§20.5a と別の式で計算する。
- FM9 kind と証拠の組が壊れた行を書ける。旧明細の分類が CHECK で失敗する。
- FM10 新しい関数が production から呼べる。通常の起動で schema が変わる。
- FM11 拒否の code を取り違え、UI が行き先を選べない（失効と保存先の変更を 1 つにする）。

## Negative Paths

- missing input: context が None（C7 (c)、C10 の再送）、存在しない明細（C4）。
- invalid input: N が負・安全な整数を超える（C8）、kind と証拠の壊れた組（C1）。
- duplicate/ambiguous input: 同じ token の再送と値違い、request ID の二重（C10）。進行中が既にある start（C3）。
- unknown reference: 存在しない明細の begin（C4）。
- dependency missing: 該当なし（DB だけ）。
- permission/write failure: 保存 TX の故障（C9）。
- dry-run side effect: begin が DB を書かない（C4）。拒否が書込み 0（C7・C13・C14）。

## Boundary Checks

- threshold: `source_id <= source_cursor`（C5・C6）、N の 0 と安全な整数の上限（C8）。
- null/default: auto_filled の時刻 NULL、uncounted の数量 NULL（C1・C3・C13）。
- empty/non-empty: 資料が 0 件の begin は cursor 0（C18）、flag が 0 件の確定は通る（C12）。
- min/max: L が `i64::MIN + 1`（C8）、負の在庫の評価数量 0（C13）。
- status/policy enum: kind 4 値（C1）、purpose 2 値・回復の code 3 値・action 3 値（C4・C7・C14）。
- wire type: 該当なし（⑤）。
- internal type: 版・cursor は `i64`、DB 世代は `u64`（C4・C7）。
- producer/consumer: 保存が作る measured を ② の `find_latest_effective_observation` と `classify_stock_rows` が読む（C6・C17）。
- round-trip token: token = request ID（C10）。
- precision/range: 補正の checked（C8）、評価額の i128（§20.5a、C13）。
- cross-language parse: 該当なし（⑤）。

## Compatibility Checks

- old schema/input: 旧明細の分類が CHECK の下でも同じ（C1）。旧 header（版 0）の確定（C16）。
- new schema/input: 新方式の明細と header（C3）。
- output order: `recount_reasons` は 40 の順（C14）。
- optional field behavior: `recount_id` は進行中の保存で None、独立再実測で Some（C5・C11）。

## Data Safety Checks

- source-derived data: なし（合成だけ）。
- generated outputs: `docs/function-design/90-traceability.md` の再生成だけ。
- secrets: なし。
- local-only files: `.local/` は読むだけ。
- synthetic sample boundaries: 商品コード・数量・原価は合成。

## Main Wiring / Integration Checks

- helper connected to main path: 接続しないことが契約（C2）。
- output reaches manifest/report: 該当なし。
- effective config reaches runtime: 該当なし。
- CLI arg reaches implementation: 該当なし。

## Mutation-style Adequacy Questions

- 確定の在庫を「確定直前の在庫 + (N − L)」でなく N にすると C12 の 4 本が全て 10 になって落ちる。
- 保存の版の比較を外すと C7 (a) が落ちる。所有者の検査を版の検査より後にすると C7 (d) の code が count_context_invalid になって落ちる。
- 保存で `source_cursor` を保存時の最大 ID に差し替えると C6 が落ちる（② の Matrix の申し送り）。flag の削除を `<` にすると C5 の source 2 が残って落ち、条件を外すと source 3 が消えて落ちる。
- observation_revision を flag の削除や数量の更新の前の版にすると C5 が落ちる。
- 再送の照会を context の検査より後にすると C10 の「context が None の再送」が落ちる。
- 確定の flag・legacy の検査を force_fill のときに外すと C14 が落ちる。差 0 の商品の版の更新を外すと C15 が落ちる。
- 評価数量を N にすると C13 の `total_cost` が落ちる（N と補正後の在庫が違う fixture）。`max(…,0)` を外すと負の在庫の行で落ちる。
- 独立再実測で header の `total_cost` を再計算すると C11 が落ちる。差 0 で recount を作らないと C11 の 2 回目が落ちる。
- CHECK を外すと C1 と T19 の末尾が落ちる。列の非負の CHECK を外すと T1 の負の cursor の行が落ちる（他の 6 項目を揃えた形にしてあるので K1 では落ちない）。reader の measured の NULL の分岐を外すと T19 の `ignore_check_constraints` の後の assert が落ちる。
- 確定で `valuation_cost_price` を保存しないと C13 が落ちる。確定を商品ごとに commit すると C20 が落ちる。旧 active の明細の L を保存で取り直さないと C16 が 4 になって落ちる。確定の legacy の検査を商品の全明細に広げると C16 が拒否され続けて落ちる。
- save で `context.count_token` と引数の token を比べないと C7 (e) が落ちる。
- 各組合せに非空の期待を置く: C5（消える flag が 2 件・残る flag が 1 件）、C12（補正の movement が 1 件）、C14（理由が 2 つ）。
